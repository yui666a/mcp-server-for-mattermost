# i18n とタイムゾーンの設定

## 目的

mcp-server-for-mattermost を OSS として公開する。
今は、ツールの出力、エラーの文、同意画面、`docs/` が日本語で、時刻は JST に固定している。
日本以外の組織がそのまま導入できるように、言語とタイムゾーンを導入する組織が選べるようにする。
日本語と JST で運用している既存の導入は、設定を足せば今と同じ動作のまま更新できる。

## 目標

- 利用者や AI が目にする文を、すべて英語と日本語の両方で持ち、導入する組織が選べる。対象は、ツールの説明、ツールの出力、エラーの文、予約の失敗の理由、アップロードの応答、同意画面と認可のエラー画面
- 言語を選ばない導入では英語になる
- オフセットの無い時刻の解釈、検索の日付、出力の時刻を、設定したタイムゾーンで扱う
- `docs/` 以下の文書を、英語と日本語の両方で持つ
- 3 つ目の言語を足す人は、言語の表のファイルを 1 つ足せば済む

## 目標にしないもの

- 利用者ごとの言語とタイムゾーン（Mattermost のプロフィールに従う）。今回は作らないが、あとで足せる形にする（「将来の拡張」）
- ログの英語化。ログはすでに英語のイベント名と値で、文を持たない
- 起動時の設定のエラー（`PUBLIC_URL is required` など）。すでに英語で、運用者だけが読む
- Mattermost から返るエラーの文の翻訳。Mattermost の文はそのまま渡している箇所がある

## 失敗とみなすもの

- 既定の設定で、どこかに日本語の文が残る
- 日本語と JST で運用している導入が、更新の後に英語や UTC で動く（設定を足す前にデプロイした場合）
- 日本語の表と英語の表で、ある文の差し込む値や意味が食い違い、片方の言語でだけ AI が誤った行動をとる
- マルチバイトのデータ（日本語の投稿、ファイル名、Shift_JIS の CSV、書記素での切り詰め）の扱いが壊れる

## 制約

- 依存を足さない。Node.js の標準（`Intl`、`AsyncLocalStorage`）で足りる
- MCP サーバーは 1 プロセスで動く
- ツールの説明は AI が読むので、意味を変えずに訳す。安全のための案内（削除や curl の前の確認、既読にする範囲、上書きで失われるもの）は、両方の言語で同じ強さで書く
- 文の多くは、過去のレビューと実測で AI の行動に合わせて言い回しを決めた。訳でその意図を落とさない

## 検討した方法

言語とタイムゾーンをどこで決めるか。

| 方法 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. サーバー全体（採用） | 環境変数 `LOCALE` と `TIME_ZONE` で決める | 起動時に 1 回決めるだけで、言語を引数で持ち回らない | 同じサーバーで利用者ごとに言語を分けられない |
| B. 利用者ごと | Mattermost のプロフィールの `locale` と `timezone` で決める | 1 つのサーバーで言語を混ぜられる | 言語を全体に持ち回るか、要求ごとに文脈に持つ必要がある。プロフィールを変えたときの反映を作る必要がある。ログイン前の同意画面は別の決め方が要る |
| C. A を既定にして B で上書き | | いちばん柔軟 | A と B の両方の手間 |

A を採る。
導入する組織の多くは、1 つの言語で使う。
ツールの出力は AI が読み、AI は利用者の言語で答えるので、利用者ごとに分ける利点が小さい。
ただし C へ移れる形にする（「将来の拡張」）。

文の持ち方は、言語ごとに 1 ファイルの表にする。
呼び出し箇所に `{ en, ja }` を並べる書き方は、文が処理の横にあって読みやすいが、3 つ目の言語を足す人が全ファイルを触ることになるので採らない。
i18next などのライブラリは、依存を足すうえ、型で表の対応を保証できないので採らない。

## 設計

### 設定

| 名前 | 既定 | 内容 |
|---|---|---|
| `LOCALE` | `en` | `en` か `ja`。それ以外は起動時のエラー |
| `TIME_ZONE` | `UTC` | IANA のタイムゾーン名（`Asia/Tokyo` など）。`Intl.DateTimeFormat` が受け付けない名前は起動時のエラー |

どちらも `loadConfig` で読み、`Config` に持つ。

### 言語の表

- `src/i18n/en.ts` に英語の表を置く。ツールや機能ごとに入れ子にしたオブジェクトで、差し込む値のある文は引数を取る関数にする
- `src/i18n/ja.ts` に日本語の表を置き、型を `typeof en` から作った型に当てる。キーの抜け、余分なキー、関数の引数の違いは typecheck で落ちる
- `src/i18n/index.ts` が、今の言語の表を返す 1 つの入口（例 `msg()`）を持つ。起動時に `LOCALE` で表を決める
- モジュールの読み込み時に文を組み立てている定数（`RETRY`、`BODY_CUT_NOTE`、`scheduler.ts` の `UNKNOWN` など）は、使う時点で表から引く形に変える。読み込み時には言語がまだ決まっていないため
- ツールの説明も表に持つ。`buildServer` は要求ごとに呼ばれるので、登録の時点で表から引けばよい。日本語の説明は、今の英語の説明から訳す（英語の説明は、AI の行動を変えない文を削ったうえで英訳のレビューを通したもので、日本語の旧版とは中身が違うため）
- 管理コマンド（`src/admin.ts`）は `loadConfig` を通らないので、`LOCALE` を環境変数から直接読む
- ツールの出力に出る語のうち、AI に別のツールの引数として書き写させる固定の語（`next_cursor:`、`post_id:`、`file_id:` などの項目名）は訳さず、両方の言語で同じにする。ツールの説明がそれを名前で指すため

### 同意画面

- 文は表から引き、`<html lang>` を設定した言語にする
- ログイン前で利用者が分からないので、言語はサーバーの設定に従う。ブラウザの `Accept-Language` は見ない（A の方針。C に移るときに見る）

### 予約の失敗の理由

予約の失敗の理由は、今と同じく、失敗した時点の言語で文にして DB に保存する。
理由を識別子で保存して表示の時に訳す方法は、`LOCALE` を変えた後の古い行の言語がそろう利点があるが、Mattermost から返った文をそのまま保存する経路があり、識別子に直せない。
`LOCALE` を変えるのは導入の時くらいで、失敗の行は 7 日で消えるので、混ざっても害が小さい。
管理コマンドの `invalidate-scheduled` が書く理由も、そのときの `LOCALE` の言語にする。

### タイムゾーン

今 JST に固定している箇所を、`TIME_ZONE` に置き換える。

- **入力の時刻**：`parseWhen`（`src/mcp/when.ts`）で、オフセットの無い時刻を `TIME_ZONE` の現地時刻として読む。夏時間のある地域では、その時刻のオフセットを `Intl` で求める。現地時刻が存在しない（夏時間の開始で飛ぶ）ときと、2 回ある（終了で重なる）ときの扱いは、実装者が決めて説明とエラーの文に書く
- **検索の日付**：Mattermost の検索 API の `time_zone_offset`（秒の数 1 つ）には、呼んだ時点の `TIME_ZONE` のオフセットを渡す。夏時間をまたいだ日付の検索では 1 時間ずれうる（Mattermost の画面も、利用者の今のオフセットを渡している）。`get_mentions` の日付の計算（今の `jstDay`）も同じ規則で `TIME_ZONE` の日付にする
- **出力の時刻**：`formatTime` は、今の「UTC | JST」の併記を「UTC | `TIME_ZONE` の現地時刻（オフセット付き）」にする。`TIME_ZONE` が UTC なら UTC だけを出す。`format.ts` の `localTime` が同じ計算をしている
- **ツールの説明**：「JST if no offset」のような文は、設定したタイムゾーンの名前を差し込む

### docs

- `docs/` 以下の各文書を、英語の `<name>.md` と日本語の `<name>-ja.md` の組にする。README と同じ形
- 今の `docs/*.md` は日本語なので、`*-ja.md` に名前を変え、英語版を新しく書く。設計書（`docs/superpowers/specs/` 以下）も同じ。この設計書も、実装の中で英語版を作る
- 文書の中のリンクは、同じ言語の文書へ張る
- `deployment` の環境変数の表に `LOCALE` と `TIME_ZONE` を足す。`operations` の「MCP サーバーを更新するとき」に、この版へ上げる前に `LOCALE=ja` と `TIME_ZONE=Asia/Tokyo` を設定する手順を、日本語で運用している導入に向けて書く
- README と README-ja の「ツールの説明は英語、ほかは日本語」の注記を、`LOCALE` で選べることに書き換える

### テスト

- 単体テストと結合テストは、`LOCALE=en` で流す。今の日本語の文言の assertion は英語に書き換える。テストの土台（`test/unit/helpers.ts` と `test/int/helpers.ts`）で言語を決める
- テストのタイムゾーンは `Asia/Tokyo` にする。オフセットが 0 でないほうが、オフセットの扱いの誤りを見つけられ、今の時刻の assertion も活かせる
- 夏時間のある地域（`America/New_York` など）で、`parseWhen` と `formatTime` と検索の日付を確かめるテストを足す
- 日本語は次で確かめる
  - 日本語の表の型（上の「言語の表」）
  - `LOCALE=ja` で、同意画面と、代表的なツールの説明・出力・エラーが日本語になることを確かめる少数のテスト（切り替えの配線の確認）
  - マルチバイトのデータのテストは今のまま残す（日本語の投稿、ファイル名、Shift_JIS、書記素）
- 既定の設定で日本語の文が出ないことを、`LOCALE=en` で全ツールの説明と、テストで出した出力を走査して確かめる。`2026年10月*` のように、例として日本語を意図して含む文は除く

### 訳の確かめ方

文の多くは、AI の行動に合わせて言い回しを決めてある。
訳したら、ツールや機能のまとまりごとに、元の日本語・訳した英語・実装の 3 つを突き合わせるレビューを、訳した文脈から切り離して行う。
条件の欠け、範囲の変化、安全のための案内の弱まりを探す。

### 既存の導入の更新

日本語と JST で運用している導入は、この版をデプロイする前に、MCP サーバーの環境変数に `LOCALE=ja` と `TIME_ZONE=Asia/Tokyo` を足す。
Compose の `environment:` で変数を 1 つずつ渡している構成では、`.env` に足すだけではコンテナに届かないので、`environment:` に足す。
秘密の値ではないので、`${LOCALE}` で `.env` を参照せずに値のまま書いてよい。`.env` への足し忘れで黙って英語と UTC で起動することが無くなる。
足さずにデプロイすると、英語と UTC で動く。
古い版は知らない環境変数を無視するので、先に足しても害が無い。

`LOCALE` と `TIME_ZONE` が空の文字列のときは、ほかの省略できる変数（`MM_URL` など）と同じく既定値として扱う。
足し忘れに気づけるよう、起動のログ（`listening`）に `locale` と `time_zone` を出す。

## 将来の拡張（C へ移るとき）

- 文を引く入口を 1 つ（`msg()`）にしてあるので、言語の決め方はそこだけで変えられる。要求ごとの言語は `AsyncLocalStorage` に持てば、各関数の引数に足さずに済む
- そのときは、Mattermost のプロフィールの `locale` と `timezone` を、ログインの時点で取って保存し、`/users/me` を呼ぶ箇所で更新する
- 同意画面はログイン前なので、`Accept-Language` で決める
- 予約の失敗の理由は、行ごとに違う言語で残る。識別子で保存する形に変えるかを、そのときに決める

## 実装者に任せること

- 表の入れ子の分け方とキーの名前
- 夏時間で存在しない・2 回ある現地時刻の扱い（決めたら説明とエラーの文に書く）
- 英語の訳の言い回し（「訳の確かめ方」のレビューを通す）
- 作業の分け方と PR の分け方
