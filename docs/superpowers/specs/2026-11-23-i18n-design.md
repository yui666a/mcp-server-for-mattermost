# i18n and time zone settings

## Purpose

mcp-server-for-mattermost is going to be released as OSS.
Today, tool output, error messages, the consent screen and `docs/` are in Japanese, and times are fixed to JST.
So that organizations outside Japan can deploy it as it is, the deploying organization gets to choose the language and the time zone.
Existing deployments that run in Japanese and JST can upgrade with the same behavior by adding the settings.

## Goals

- Every sentence that users and AI see exists in both English and Japanese, and the deploying organization chooses. This covers tool descriptions, tool output, error messages, the reasons for scheduled message failures, upload responses, and the consent screen and the authorization error screen
- A deployment that chooses no language gets English
- Interpretation of times without an offset, search dates and output times are handled in the configured time zone
- The documents under `docs/` exist in both English and Japanese
- Someone adding a third language only has to add one language table file

## Non-goals

- Per-user language and time zone (following the Mattermost profile). Not built this time, but the design lets it be added later ("Future extension")
- Translating the logs. The logs already use English event names and values, and carry no sentences
- Startup configuration errors (`PUBLIC_URL is required` and so on). They are already in English, and only operators read them
- Translating error messages returned by Mattermost. Some places pass Mattermost's text through as it is

## What counts as a failure

- With the default settings, a Japanese sentence remains somewhere
- A deployment that runs in Japanese and JST runs in English or UTC after an update (if it is deployed before the settings are added)
- Between the Japanese table and the English table, the inserted values or the meaning of a sentence diverge, so the AI takes a wrong action in only one language
- Handling of multibyte data (Japanese posts, file names, Shift_JIS CSV, truncation by grapheme) breaks

## Constraints

- No new dependencies. The Node.js standard library (`Intl`, `AsyncLocalStorage`) is enough
- The MCP server runs as a single process
- Tool descriptions are read by the AI, so they are translated without changing meaning. Safety guidance (confirmation before deletion or curl, the range that gets marked read, what is lost by overwriting) is written with the same strength in both languages
- Many sentences had their wording decided to fit the AI's behavior, through past reviews and measurements. The translation must not lose that intent

## Methods considered

Where to decide the language and the time zone.

| Method | Content | Advantage | Disadvantage |
|---|---|---|---|
| A. Server-wide (adopted) | Decided with the environment variables `LOCALE` and `TIME_ZONE` | Decided once at startup, and the language is not passed around as an argument | The same server cannot use different languages per user |
| B. Per user | Decided by `locale` and `timezone` in the Mattermost profile | One server can mix languages | The language has to be passed everywhere or held in a per-request context. A mechanism for reflecting profile changes is needed. The consent screen before login needs a different way to decide |
| C. A as the default, overridden by B | | The most flexible | The effort of both A and B |

We adopt A.
Most deploying organizations use a single language.
The AI reads the tool output and answers in the user's language, so the benefit of splitting per user is small.
But the design lets us move to C ("Future extension").

Sentences are held in one table file per language.
Writing `{ en, ja }` at each call site keeps sentences next to the logic and is easy to read, but whoever adds a third language would have to touch every file, so we do not adopt it.
Libraries such as i18next add a dependency and cannot guarantee through types that the tables correspond, so we do not adopt them.

## Design

### Settings

| Name | Default | Content |
|---|---|---|
| `LOCALE` | `en` | `en` or `ja`. Anything else is a startup error |
| `TIME_ZONE` | `UTC` | An IANA time zone name (`Asia/Tokyo` and so on). A name that `Intl.DateTimeFormat` does not accept is a startup error |

Both are read in `loadConfig` and held in `Config`.

### Language tables

- The English table goes in `src/i18n/en.ts`. It is an object nested by tool or feature, and a sentence with inserted values is a function that takes arguments
- The Japanese table goes in `src/i18n/ja.ts`, and its type is a type made from `typeof en`. A missing key, an extra key or a different function argument fails typecheck
- `src/i18n/index.ts` has a single entry point (for example `msg()`) that returns the table of the current language. The table is chosen at startup from `LOCALE`
- Constants that build sentences at module load (`RETRY`, `BODY_CUT_NOTE`, `UNKNOWN` in `scheduler.ts` and so on) are changed to look up the table at the point of use, because the language is not yet decided at load time
- Tool descriptions are also held in the table. `buildServer` is called per request, so looking up the table at registration is enough. The Japanese descriptions are translated from the current English descriptions (the English descriptions went through review of the English wording after sentences that do not change the AI's behavior were removed, so their content differs from the older Japanese version)
- The admin command (`src/admin.ts`) does not go through `loadConfig`, so it reads `LOCALE` directly from the environment
- Among the words in tool output, the fixed words the AI is made to copy as arguments of other tools (field names such as `next_cursor:`, `post_id:` and `file_id:`) are not translated and are the same in both languages. This is because the tool descriptions refer to them by name

### Consent screen

- Sentences are looked up from the table, and `<html lang>` is set to the configured language
- It is before login and the user is not known, so the language follows the server setting. The browser's `Accept-Language` is not looked at (the policy of A. It will be looked at when moving to C)

### Scheduled message failure reasons

As today, the reason for a scheduled message failure is written as a sentence in the language at the time of the failure and stored in the DB.
Storing the reason as an identifier and translating it at display time has the advantage that old rows share one language after `LOCALE` changes, but there is a path that stores the text returned by Mattermost as it is, and it cannot be turned into an identifier.
`LOCALE` is changed about once, at deployment, and failure rows are deleted after 7 days, so mixing does little harm.
The reason that the admin command `invalidate-scheduled` writes is also in the language of `LOCALE` at that time.

### Time zone

The places that are fixed to JST today are replaced with `TIME_ZONE`.

- **Input times**: `parseWhen` (`src/mcp/when.ts`) reads a time without an offset as local time in `TIME_ZONE`. In regions with daylight saving time, the offset at that time is computed with `Intl`. How to treat a local time that does not exist (skipped at the start of daylight saving time) and one that occurs twice (repeated at its end) is decided by the implementer and written in the description and the error message
- **Search dates**: The `time_zone_offset` of the Mattermost search API (a single number of seconds) is given the offset of `TIME_ZONE` at the time of the call. A search over dates that span a daylight saving change can be off by 1 hour (the Mattermost UI also passes the user's current offset). The date calculation of `get_mentions` (today's `jstDay`) also uses the date in `TIME_ZONE` by the same rule
- **Output times**: `formatTime` changes today's combined "UTC | JST" into "UTC | local time in `TIME_ZONE` (with offset)". If `TIME_ZONE` is UTC, only UTC is shown. `localTime` in `format.ts` does the same calculation
- **Tool descriptions**: A sentence such as "JST if no offset" gets the name of the configured time zone inserted

### docs

- Each document under `docs/` becomes a pair of an English `<name>.md` and a Japanese `<name>-ja.md`. The same shape as README
- The current `docs/*.md` are Japanese, so they are renamed to `*-ja.md` and English versions are newly written. The design documents (under `docs/superpowers/specs/`) are the same. This design document also gets an English version during the implementation
- Links inside a document point to the document in the same language
- `LOCALE` and `TIME_ZONE` are added to the environment variable table of `deployment`. In "When updating the MCP server" of `operations`, a procedure for setting `LOCALE=ja` and `TIME_ZONE=Asia/Tokyo` before upgrading to this version is written, in Japanese, for deployments that run in Japanese
- The note "tool descriptions are in English, the rest in Japanese" in README and README-ja is rewritten to say that it can be chosen with `LOCALE`

### Tests

- Unit tests and integration tests run with `LOCALE=en`. The existing assertions on Japanese wording are rewritten in English. The language is decided in the test foundations (`test/unit/helpers.ts` and `test/int/helpers.ts`)
- The time zone for tests is `Asia/Tokyo`. A non-zero offset can find mistakes in offset handling, and the existing time assertions stay useful
- Tests are added that check `parseWhen`, `formatTime` and search dates in a region with daylight saving time (`America/New_York` and so on)
- Japanese is checked with the following
  - The type of the Japanese table ("Language tables" above)
  - A few tests that check, with `LOCALE=ja`, that the consent screen and representative tool descriptions, output and errors are in Japanese (a check of the switching wiring)
  - The tests for multibyte data are kept as they are (Japanese posts, file names, Shift_JIS, graphemes)
- That no Japanese sentence appears with the default settings is checked by scanning, with `LOCALE=en`, all tool descriptions and the output produced in tests. Sentences that intentionally contain Japanese as an example, such as `2026年10月*`, are excluded

### Checking the translation

Many sentences had their wording decided to fit the AI's behavior.
After translating, for each group of tools or features, a review that compares the original Japanese, the translated English and the implementation is done, separated from the context in which the translation was written.
It looks for missing conditions, changes in scope, and weakened safety guidance.

### Upgrading existing deployments

A deployment that runs in Japanese and JST adds `LOCALE=ja` and `TIME_ZONE=Asia/Tokyo` to the MCP server's environment variables before deploying this version.
In a setup that passes variables one by one with Compose's `environment:`, adding them to `.env` alone does not reach the container, so add them to `environment:`.
They are not secret, so they can be written as literal values instead of referencing `.env` with `${LOCALE}`; forgetting to add them to `.env` then cannot silently start the server in English and UTC.
If deployed without adding them, it runs in English and UTC.
Old versions ignore environment variables they do not know, so adding them first does no harm.

When `LOCALE` and `TIME_ZONE` are empty strings, they are treated as the default, the same as other optional variables (`MM_URL` and so on).
So that a forgotten addition can be noticed, the startup log (`listening`) includes `locale` and `time_zone`.

## Future extension (moving to C)

- Sentence lookup goes through a single entry point (`msg()`), so only that place changes how the language is decided. A per-request language can be held in `AsyncLocalStorage`, which avoids adding it to the arguments of every function
- At that point, the Mattermost profile's `locale` and `timezone` are fetched and stored at login time, and updated where `/users/me` is called
- The consent screen is before login, so it is decided with `Accept-Language`
- Scheduled message failure reasons remain in different languages per row. Whether to change to storing identifiers is decided then

## Left to the implementer

- How to split the table's nesting and the key names
- How to treat local times that do not exist or occur twice at daylight saving changes (write it in the description and the error message once decided)
- The wording of the English translation (it goes through the review in "Checking the translation")
- How to split the work and the PRs
