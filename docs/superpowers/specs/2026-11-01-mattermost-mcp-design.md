# Remote MCP Server for Mattermost: Design

## Purpose

Let Claude (claude.ai and the desktop app), Claude Code and Codex read and write Mattermost messages, in the same way as the Slack Connector.
A user starts using it just by adding the MCP server's URL (for example `https://mattermost.example.com/mcp`) as a connector and logging in with their Mattermost account.

Mattermost's official MCP server is part of the Agents plugin, and its HTTP endpoint for external MCP clients requires an Enterprise or higher license.
To make it usable with the free Team Edition too, this is built as an independent MCP server that runs outside Mattermost.

## Goals

- Connect from three clients, the claude.ai custom connector, Claude Code (`claude mcp add --transport http`) and Codex CLI, just by registering the URL and logging in with OAuth
- Each user acts with the permissions of their own Mattermost account. Channels and messages the user cannot see are not visible through MCP either
- The following operations are available
  - Searching messages
  - Reading a channel from its latest messages, from the first unread, or from a specified date and time range, and reading a thread
  - Reading a single post specified by a permalink URL or a post_id
  - Reading files attached to a post (an image as a downscaled image, a text file as its beginning) and searching files by name
  - Listing the posts the user saved (flagged)
  - Searching channels and users, and viewing user profiles
  - Viewing a user's time zone, local time and presence
  - Listing the channels the user has joined
  - Viewing a channel's type, purpose, header, member count and pinned posts
  - Listing the members of a channel the user may read (normally a channel the user has joined)
  - Listing the user's own unreads (channels and threads) and mentions of the user (which can also be limited to unread ones)
  - Marking the user's own channels and threads as read (up to the posts the AI has read)
  - Listing followed threads, and following and unfollowing threads
  - Posting to channels and threads (including attaching small files)
  - Adding and removing the user's own reactions on posts
  - Saving (flagging) and pinning or unpinning posts in joined channels (unsaving works regardless of membership)
  - Searching, by name, the custom emoji used for reactions and custom statuses
  - Changing the user's own presence and custom status
  - Editing and deleting the user's own posts
  - Saving a draft as the user's own Mattermost draft (the user sends it on screen)
  - Scheduling a post to a channel or thread at a specified time, and listing, changing and cancelling scheduled posts
- Once logged in, the user can keep using it without logging in again until they revoke it, as long as they keep using it (tokens are renewed with refresh tokens)

## Non-goals

- Editing or deleting other people's posts, creating channels and managing members
- System administration operations (user management, changing settings)
- Notifying MCP clients of Mattermost events (subscriptions, notifications)
- Supporting multiple Mattermost servers

## What to avoid

- Mattermost being operated through the MCP server with permissions other than the user's own
- A user's Mattermost permissions being handed to an MCP client the user did not intend
- Posting to an unintended channel
- Mattermost itself going down or slowing down. Failures or overload of the MCP server must not spread to the use of Mattermost
- Mattermost access tokens or message bodies remaining in logs

## Architecture

### Approach: the MCP server has its own authorization server and delegates login to Mattermost

Under the MCP specification (2025-06-18 and later), an MCP server must accept only tokens issued for itself, and passing a received token straight through to a downstream API (token passthrough) is prohibited.
Mattermost v11.7.8 has an implementation that receives and records the RFC 8707 `resource`, but it could not be confirmed that the REST API validates the audience of a token.
If an MCP client were given a Mattermost token directly, that MCP client could call all of Mattermost's APIs as the user.

So the MCP server takes on two roles.

1. **Authorization server for MCP clients**: it handles MCP client registration (Dynamic Client Registration), authorization and token issuance itself. The tokens it issues are addressed to the MCP server and cannot be used with Mattermost's API
2. **OAuth client of Mattermost**: it registers with Mattermost as just one confidential client and leaves the user's login to Mattermost's authorization screen. It stores the Mattermost tokens it obtains on the server side, encrypted, and does not hand them to MCP clients

```text
MCP client ──(MCP token)──> MCP server ──(Mattermost token)──> Mattermost API
       │                                   │
       └─ Authorization: the MCP server's /authorize ──> consent screen ──> Mattermost's /oauth/authorize (login)
```

### URLs and metadata

`/.well-known/oauth-authorization-server` directly under the domain is used by Mattermost's own metadata, so the MCP server's authorization server includes a path in its issuer and publishes its metadata in the path-insertion form of RFC 8414.

| Item | Value |
|---|---|
| MCP endpoint (resource) | `https://mattermost.example.com/mcp` (no trailing slash) |
| Protected Resource Metadata (RFC 9728) | `https://mattermost.example.com/.well-known/oauth-protected-resource/mcp` |
| Authorization server issuer | `https://mattermost.example.com/mcp` |
| Authorization Server Metadata | `https://mattermost.example.com/.well-known/oauth-authorization-server/mcp` |
| Endpoints for authorization, tokens, registration, the callback from Mattermost and so on | Under `https://mattermost.example.com/mcp/oauth/`. The implementer decides the concrete paths |

The metadata must include the following.

- Protected Resource Metadata: `resource` must exactly match the URL of the MCP endpoint (claude.ai requires an exact match including the path). `authorization_servers` is just the one issuer
- Authorization Server Metadata: `issuer`, `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]` (clients registered through DCR are public clients), `scopes_supported: ["mattermost"]`
- Also put `scopes_supported: ["mattermost"]` in the Protected Resource Metadata, and add `scope="mattermost"` to the `WWW-Authenticate` of the `401`

There is only one scope, `mattermost`, which means "use the tools as this user's Mattermost account".
Scopes are not split between reading and writing. Confirmation before a write is left to MCP clients that look at the tool annotation (`readOnlyHint`) ([Tools](#tools)).

- When `scope` is omitted from an authorization request, `mattermost` is given. If any scope other than `mattermost` is included, the request is rejected with `invalid_scope`
- The scope is bound to the authorization code, the grant, the access token and the refresh token, so that it cannot be widened by a refresh

The `resource` parameter is required in authorization requests and token requests, and is rejected with `invalid_target` if it is missing or does not exactly match the URL of the MCP endpoint.
The authorization codes and tokens issued can be used only for this one resource.
All three target clients send `resource` in the authorization request and the code exchange (["Client compatibility"](../../measurements.md#client-compatibility) in `docs/measurements.md`).

This form follows the discovery procedures of RFC 8414 and the MCP specification, and it was confirmed by measurement that the three clients can find metadata in this form and connect (["Client compatibility"](../../measurements.md#client-compatibility) in `docs/measurements.md`).

### Authorization flow

1. When an MCP client accesses `/mcp` without a token, the MCP server returns `401` and `WWW-Authenticate: Bearer resource_metadata="…"`
2. The MCP client learns the authorization server from the Protected Resource Metadata and fetches the Authorization Server Metadata
3. The MCP client registers itself with DCR (RFC 7591)
4. The MCP client sends the user to the MCP server's authorization endpoint with PKCE (`S256` required). The MCP server validates `client_id`, `redirect_uri`, PKCE and `resource`
5. The MCP server shows a consent screen
6. When the user allows it, the MCP server redirects to Mattermost's `/oauth/authorize`. For this authorization from the MCP server to Mattermost too, it attaches a PKCE (`S256`) generated separately from the MCP client's
7. The user logs in to Mattermost and allows it
8. When Mattermost returns to the callback, the MCP server checks `state`, obtains and stores the Mattermost tokens, and returns an authorization code to the MCP client
9. The MCP client exchanges the authorization code for MCP tokens (an access token and a refresh token) at the MCP server's token endpoint

### Authorization codes issued to MCP clients

To meet the authorization code requirements of OAuth 2.1 (draft-13 §4.1.2–4.1.3), the following is observed.

- The authorization code is a random value of sufficient length, and only its hash is stored on the server side. Its lifetime is about 1 minute
- The Mattermost user, `client_id`, the `redirect_uri` of the authorization request, the PKCE `code_challenge` (`S256`) and `resource` are bound to the authorization code and stored
- In a token request, it is checked that `client_id` and `redirect_uri` match the stored values and that `code_verifier` matches `code_challenge`. If any one does not match, the request is rejected with `invalid_grant`. A missing or mismatching `resource` is rejected with `invalid_target`
- Consuming the authorization code and issuing the tokens are done in a single transaction, so the same code cannot be used twice. If a used code is presented again, the tokens issued from that code are revoked
- The `state` received from the MCP client is stored separately from the `state` sent to Mattermost, and is returned to the MCP client unchanged, on success and on error alike

### Consent screen

The OAuth app on the Mattermost side is a single fixed client ID, and anyone can register a client with DCR.
Without a consent screen, a confused deputy attack succeeds in which the authorization of a user already logged in to Mattermost flows automatically to the redirect destination of a client the attacker registered.
Following the MCP Security Best Practices, the consent screen satisfies the following.

- It is always shown for every authorization request, before redirecting to Mattermost. It is not skipped by remembering consent, because the user authorizes only when adding a client, so showing it every time is no burden
- It shows the client name, the whole of the registered redirect URI, and the requested permission (the meaning of the scope `mattermost`: "read and write messages as your Mattermost account"). The client name can be set freely by the registrant, so the redirect URI is made more prominent than the name
- For a client whose redirect URI is a loopback (`localhost`, `127.0.0.1`), an additional warning is shown that says "this hands permissions to an app on this machine; allow it only if you yourself started connecting Claude Code or Codex" (Localhost Redirect URI Risks of MCP 2025-11-25)
- The allow form carries a CSRF token. The response carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`, so that other sites cannot embed it in an iframe
- The `state` sent to Mattermost is generated at the moment the user allows. The server-side record of the authorization in progress stores together the browser cookie, the `state` and PKCE sent to Mattermost, and the MCP client's `client_id`, `redirect_uri`, PKCE, `state` and `resource`. This record can be used only once and expires in about 10 minutes. At the callback, the request is rejected unless the `state` and the cookie match the record
- The client name and redirect URI registered with DCR are treated as untrusted values the registrant decided freely
  - Upper limits on length are set at registration, and values containing control characters are rejected
  - On the consent screen and error pages they are shown only through an auto-escaping template or as text nodes, and are never interpreted as HTML
  - External resources such as DCR's `logo_uri` are not loaded
  - Next to the client name, "the name is self-declared by the registrant and has not been verified" is shown
- The responses of the consent screen and error pages carry the equivalent of `Content-Security-Policy: default-src 'none'; style-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, so that no script runs at all. The consent screen is an HTML form that works without scripts
- An automated test checks that, when a client is registered with a malicious client name or redirect URI (an HTML tag, control characters, an extremely long value), no script runs on the consent screen and the display is not broken
- The cookie has a name starting with `__Host-`, carries `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`, and has no `Domain` (the Confused Deputy countermeasure of the MCP Security Best Practices). Its value is a random session ID, and the contents are held on the server side

### Redirect URIs

The redirect URIs accepted for registration with DCR are limited to the following.
A registration request that matches none of them is rejected with `invalid_redirect_uri`.

- `https://claude.ai/api/mcp/auth_callback` and `https://claude.com/api/mcp/auth_callback` (claude.ai and the desktop app. The current [Authentication for connectors](https://claude.com/docs/connectors/building/authentication#callback-urls) specifies only the `claude.ai` one, but Anthropic's old help center article (no longer published) recommended allowing both, because the callback might change to the `claude.com` side in the future. Adding one more Anthropic-managed domain with an exact match costs little, so both are allowed)
- Loopback (`http://localhost:<any port>/<any path>`, `http://127.0.0.1:<any port>/<any path>`) (Claude Code, Codex CLI)

Allowed patterns can be added through an environment variable.

The `redirect_uri` of an authorization request must exactly match a URI registered for that `client_id`.
The only exception is the port number of a loopback (RFC 8252, RFC 9700); the scheme, host, path and query must match.
When the `client_id` is unknown or the `redirect_uri` does not match, the error is not returned by redirect, and the MCP server's own error page is shown.

### MCP tokens

- The access token is short-lived (about 1 hour). The refresh token expires about 90 days after it was last used, and each rotation extends the expiry. There is no absolute expiry from issuance. As long as the user keeps using it, no re-login is needed, and only a user who did not use it for 90 days logs in again. The implementer decides the exact values
- Tokens are random opaque strings, and only their hashes are stored on the server side
- Refresh tokens are rotated (RFC 9700 §4.14.2). The series of tokens that continues from one authorization (a grant) is recorded, and a refresh records the used token and issues the new token in a single transaction. If a used refresh token is presented again, it is regarded as stolen, and all the access tokens and refresh tokens of that grant are revoked
- When the user revokes the MCP server's app from Mattermost's "Settings > Security > OAuth 2.0 Apps", all of that user's grants are revoked by the flow described below

### Mattermost tokens

Mattermost gives only one set of tokens to a pair of user and app, so the Mattermost tokens are stored as just one set per Mattermost user, and referenced from all of that user's grants.
If a copy were kept for each MCP client, the other copies would become invalid the moment any one of them refreshed.

- The access token and refresh token are stored encrypted with a key passed through an environment variable. Changing the key makes the stored tokens unreadable, and everyone logs in again
- When Mattermost's API returns `401`, the latest stored token is read again first. If another request has already refreshed, the request is retried once with that token
- Refreshing is done one at a time per user (requests that arrive at the same time wait for the result of one refresh). The new access token and refresh token are written in a single transaction
- Only when Mattermost returns `invalid_grant` to a refresh, or when the user has been deactivated, are that user's Mattermost tokens and MCP grants all revoked, and `401` is returned to the MCP client to prompt a re-login
- Mattermost rejects a request with an invalid session with `401` before calling the API handler (`web/handlers.go` in v11.7). So if a single call has received only `401`, it is treated as having made Mattermost process nothing. Even when a re-login becomes necessary, a post or an upload is "not sent", not "unknown whether sent". If a response other than `401` was received even once, or if the connection was lost after it was established, it is treated as possibly processed. This assumption does not hold for APIs where the server itself returns `401` (`deleteChannel`, `deleteUser` and so on), so review it when using them
- On temporary failures such as timeouts, connection failures and `5xx`, the stored information is left unchanged and a temporary tool error is returned

### Storage

The MCP server runs as just one process, so storage is a SQLite file placed on a volume.
What is stored is the registered MCP clients, the state of authorizations in progress, MCP grants and tokens, Mattermost tokens, the records for preventing duplicate `send_message` posts, and scheduled posts.

Of these, the DCR registration is done by each client just once per connection, and the `client_id` obtained is used from then on.
If the registration disappears, that client gets `invalid_client` and does not recover by logging in again (the connector has to be deleted and added again).
On the other hand, the DCR registration endpoint is public without authentication, so a third party can pile up registrations.
So registrations are handled in two kinds.

- **Authorized registrations** (registrations for which a user has completed authorization at least once): never deleted automatically. Authorization needs a Mattermost account, so a third party cannot increase them, and no limit is set on the total
- **Unauthorized registrations**: given a dedicated limit (a few hundred) and a lifetime (about 7 days). Those past the lifetime are deleted. When the limit is reached, a new registration is not rejected; the oldest unauthorized registration is deleted to make room. Even if a third party piles up registrations, legitimate users can still newly connect
- A client whose unauthorized registration was deleted is limited to cases such as leaving it for 7 days or more after starting authorization, and in that case the connector is added again
- A per-IP rate limit is also applied to the registration endpoint ("Limiting the load on Mattermost"). A warning log is written when unauthorized registrations approach the limit

No backup mechanism dedicated to the MCP server is provided.
The directory of the SQLite file and the encryption key are included in the deployment site's backup (a file copy or a disk snapshot).
If the SQLite file is lost, the SQLite file is restored from the latest backup by the following procedure, and the DCR registrations are brought back.
Clients registered after the backup do not come back, so those users are asked to add the connector again.

Restoring from an old backup puts the records of used refresh tokens and revoked grants back to a past state, and rotated old tokens may become valid again.
So restoring from a backup is limited to the following procedure.

1. Before starting the MCP server with the restored SQLite file, run the MCP server image's admin command in a standalone container with no network (mounting the whole directory, including SQLite's `-wal` and `-shm`) (`docker run --rm --network none -v <SQLite directory>:/data <image> <delete command>`), and delete all of the state of authorizations in progress, authorization codes, grants, MCP tokens, Mattermost tokens and the records for preventing duplicate `send_message` posts. The registered MCP clients (DCR registrations) are not deleted
   Then fail all waiting and posting scheduled posts ("Restore" in [Scheduled posts](#scheduled-posts))
2. Only after that, start the MCP server. When restoring in a form where the MCP server starts automatically on restore, such as a disk snapshot, finish step 1 before the automatic start, so that there is no route by which requests can reach the rolled-back MCP server

Because the DCR registrations are kept, each client does not need to add the connector again, and recovers just by the usual re-login after the refresh token it holds is rejected with `invalid_grant`.
DCR registrations hold no user permissions, so there is no real harm if they are rolled back.
The encryption key is not regenerated. The Mattermost tokens are deleted, but the bodies of the scheduled posts that were failed stay encrypted with the same key for 7 days from the update, and regenerating the key would make the bodies unreadable in the list.
This procedure is written in the operations manual (`docs/operations.md`).

The approach of adding a DB to Mattermost's PostgreSQL is not adopted.
It would share Mattermost's DB and its operations (dump, restore, major version updates), and we do not want to create situations where the MCP server's needs require touching Mattermost's DB.

### MCP transport

Streamable HTTP is provided at `/mcp`.
It is in stateless mode with no sessions, and notification subscriptions are not provided.
The old HTTP+SSE transport is not provided (all three target clients support Streamable HTTP).

Following the MCP Streamable HTTP specification, a request with an `Origin` header is rejected with `403` unless the origin is in an allowlist (by default `https://claude.ai` and `https://claude.com`, more can be added through an environment variable).
A request without an `Origin` header (from a CLI or server-to-server communication) is accepted with only bearer token validation.

### Tools

Every tool calls the Mattermost REST API v4 with the Mattermost token of the user who made the call.
The MCP server itself has no admin token or bot account.

| Tool | Description |
|---|---|
| `search_posts` | Searches messages in the teams the user belongs to. Mattermost search syntax (`from:`, `in:`, `before:`, `after:`, etc.) can be passed through as is. `in:` accepts a channel specification (below). It does not create DMs. Mattermost's standard database search does not match the contents of message attachments, so the tool description says so and urges the client to read with `read_channel` when looking for such contents |
| `read_channel` | Reads the latest messages of a channel, newest first, with the number of messages specified. With `from: "unread"`, it reads from the start of the unread messages, oldest first. When `since` (and `until`) is passed, it reads the posts in that date range, oldest first. Paging is supported. Reading does not mark the channel as read |
| `read_thread` | Reads the root post and replies of a thread, oldest first. Paging is supported |
| `get_post` | Reads one post, specified by a permalink URL or a post_id, together with its channel, team and reply count. For a reply, it shows the post_id of the parent; for a root post that has replies, it shows that the rest can be read with `read_thread` |
| `get_file` | Reads a file attached to a post by `file_id`. For an image, it returns the Mattermost preview (a reduced version no wider than 1920px) as MCP image content. It does not return the original size. For text (UTF-8, or Shift_JIS or EUC-JP with the extension csv, tsv, txt or log), it returns the contents up to the first 10,000 characters. For anything else, such as a PDF, it returns only the name, type and size |
| `search_files` | Searches attached files in the channels the user belongs to (archived ones only when given to `in:` by channel ID), DMs and group DMs, by name and Mattermost search syntax (`from:`, `in:`, `ext:`, `before:`, etc.). For each file, it returns the `file_id` and, if there is a post, the `post_id` and permalink, so that the client can continue with `get_file` and `get_post` |
| `list_saved_posts` | Lists, newest first, the posts the user saved (flagged) that are in channels the user belongs to. It also includes posts in archived channels, and shows "archived" after the name on that channel's line (so that the channel is not chosen as a destination). Saves are added and removed with `save_post` / `unsave_post` |
| `search_channels` | Searches channels by name (public channels, and the private channels, DMs and group DMs the user belongs to) |
| `list_my_channels` | Lists the channels the user belongs to (public, private, DM, group DM), newest last post first. Can be filtered by type. Archived channels are not included |
| `get_channel` | Reads a channel's type, purpose, header, member count and pinned posts. The member list is read with `list_channel_members`. Pins are added and removed with `pin_post` / `unpin_post` |
| `list_channel_members` | Lists the members (excluding deactivated users) of a channel the user has permission to read (normally a channel the user belongs to), in username order |
| `search_users` | Searches users by name or username |
| `get_user` | Reads a user's profile, with the time zone, the local time at the moment of the call, and the presence (online, away, do not disturb, offline, out of office) |
| `get_unreads` | Lists the channels with unread messages (unread count, mention count) and, if collapsed reply threads (CRT) are enabled, the threads with unread replies. It does not mark anything as read |
| `get_mentions` | Lists mentions of the user (`@username` and the keywords in the notification settings), newest first. It covers all teams and DMs. With `unread_only`, only unread mentions are listed |
| `list_followed_threads` | Lists the threads the user follows, newest last reply first. It covers all teams and DMs. It cannot be used by a user who has collapsed reply threads (CRT) disabled |
| `follow_thread` | Follows a thread. Does nothing if the thread is already followed |
| `unfollow_thread` | Unfollows a thread |
| `mark_as_read` | Marks the user's own channels and threads as read. A channel that has a post by someone other than the user after `last_post_id` (the newest of the posts that were read) is not marked as read, and a thread is marked as read up to that post. Up to 20 items in total |
| `send_message` | Posts to a channel. Passing `root_id` makes it a reply to a thread. `files` attaches 1 to 5 files, up to 128KiB in total contents. `file_ids` attaches 1 to 5 files uploaded through `prepare_upload`. If a draft with the same text exists for the same destination, it is deleted after posting (a draft with attachments is not deleted) |
| `prepare_upload` | Issues a single-use upload URL with which the MCP client sends, using `curl`, a file on the user's PC |
| `add_reaction` | Adds the user's own reaction to a post. The emoji is specified by its Mattermost emoji name, and surrounding colons are removed on input. Aliases (such as `thumbsup` and `+1`) are not merged, because Mattermost itself treats them as separate reactions. The argument description and the error for an unknown name tell the client to look up the name of a custom emoji with `search_emoji` |
| `remove_reaction` | Removes the user's own reaction from a post. It does not remove other people's reactions. Mattermost returns success even for a reaction that was not there, so whether anything was removed is not distinguished. How the emoji name is accepted and the pointer to `search_emoji` are the same as for `add_reaction` (an emoji with a name that does not exist also succeeds, so the pointer appears only when a name containing characters that cannot be used in a name is passed) |
| `save_post` | Adds a post to the user's own saved posts. It handles only posts in channels the user belongs to. Mattermost can also save a post in a public channel the user does not belong to, but such a save appears neither in `list_saved_posts` nor in the saved posts screen of Mattermost, so the tool refuses, to avoid the mismatch of reporting that it saved a post that then cannot be found. It succeeds even if the post is already saved |
| `unsave_post` | Removes a post from the user's own saved posts. It checks neither the post nor the membership of the channel. This is so that a save left over after the user left the channel can also be removed (when a post is deleted, Mattermost also deletes the saves of that post, but when the root post of a thread is deleted, the saves of its replies remain, and a save may also be left undeleted by mistake; these can be removed too). Whether anything was removed is not distinguished. It succeeds even if the post was not saved |
| `pin_post` | Pins a post to the channel. It only puts a channel-level mark on the post without changing its text, so it is not the non-goal "editing other people's posts". It handles only posts in channels the user belongs to. Mattermost allows it even in a public channel the user does not belong to, but because the mark is visible to everyone in the channel, the tool does not change it in a channel the user does not belong to. For a post past the server's edit time limit (`ServiceSettings.PostEditTimeLimit`), Mattermost also refuses to add or remove a pin. It succeeds even if the post is already pinned |
| `unpin_post` | Removes the pin from a post. Mattermost does not record who pinned a post, so another person's pin is removed as well. It handles only posts in channels the user belongs to. It succeeds even if the post was not pinned |

Changing from out of office makes Mattermost stop the automatic replies, and the MCP cannot restore them, so the annotation is `destructiveHint: true` |

- Any tool that is passed a key not in its arguments (inputSchema) fails with an error, without running, and the error returns the names of the keys it does not accept. The MCP SDK by default silently drops unknown arguments, so passing a misnamed argument (for example `file_id` for `file_ids`) would post or change things as if it were absent. The registration of tools is wrapped in one place (`buildServer`), which makes the argument definition of each tool strict. For this reason, a new argument added to a tool must always be written in its inputSchema. A tool that accepts no arguments also writes `{}` as its inputSchema (a tool without an inputSchema is not covered by the wrapper). A tool that is passed a zod schema directly makes it strict itself. Keys inside nested objects are not covered (the elements of `channels` and `threads` in `mark_as_read` are an exception; see the section "Marking as read")
- Read tools get the MCP tool annotation `readOnlyHint: true`, and write tools (`send_message`, `prepare_upload`, `add_reaction`, `remove_reaction`, `save_post`, `unsave_post`, `pin_post`, `unpin_post`, `edit_message`, `delete_message`, `save_draft`, `schedule_message`, `update_scheduled_message`, `cancel_scheduled_message`, `mark_as_read`, `set_status`, `set_custom_status`, `clear_custom_status`, `follow_thread`, `unfollow_thread`) do not. This is so that the MCP client can ask the user for confirmation before a write
- The annotations of `save_post`, `unsave_post`, `pin_post` and `unpin_post` are `readOnlyHint: false`, `destructiveHint: false` and `idempotentHint: true`. The removing side also leaves a state that the user can see and that can be restored by adding again (except for the pin of a post past the edit time limit. Who pinned a post is not recorded, so another person's pin can also be added again. A save of a post in a channel the user has left cannot be added again until the user rejoins, but that save appears neither in the saved posts screen of Mattermost nor in `list_saved_posts`. Deleting the root post of a thread also deletes its replies together, and only the saves of the replies remain. Such a save cannot be added again, but it likewise does not appear in the list). In the MCP definition, `destructiveHint: false` refers only to additive updates, but this server, as with `mark_as_read`, sets it by whether the change can be undone
- The output is text that is easy for an LLM to read, and includes, for each post, the author's username, the date and time, the text and the permalink (`https://mattermost.example.com/<team>/pl/<post_id>`). The output of read tools also includes the IDs and names of the channel and team, so that the LLM can use the IDs in later calls
  - The channel line of a post or file and the team of a permalink are looked up from the list of joined channels. `search_posts`, `get_mentions` and `search_files` fetch a list that does not include archived channels (because a search returns archived channels only when they are given to `in:`), and `list_saved_posts` fetches a list that includes them (because there are saved posts in archived channels too). Only the channel_ids that are not in the list (channels archived after the search, and the archived channels given to `in:`) are looked up one by one, without duplicates, with `GET /channels/{id}`. Unlike `list_followed_threads`, these are called only rarely apart from when archived channels are given to `in:` (`in:` accepts up to 20, so at most 20 calls), so one at a time is enough. The number of calls is capped by the number of distinct channel_ids on the one displayed page (at most 50, the maximum of limit), which is small compared with the server's own limit (300 per minute per user) for these lookups. Approaching 50 happens only in one-off situations, such as the user leaving a team between fetching the posts or files and fetching the channel list, and the next page does not show those posts or files, so it does not accumulate as pages are advanced (this differs from the archived threads of `list_followed_threads`, which keep appearing on every page). The archived channels given to `in:` appear on every page, so they are looked up again on every page, and are looked up twice in one search together with the lookups made when resolving `in:`; but `in:` is limited to 20 channels per page, a search is cut off at 100 results so the number of pages is also bounded, and the total fits within the estimate for one search (about 275 calls), so no mechanism for carrying the result of the resolution over to the output is built. If the user left the team, that line falls under the 403/404 handling below. On 403/404, the line is the channel_id and the permalink uses the user's first team. Any other error fails the tool (an exception to the DM naming rule, which gives up a lookup made only for the output). This is so as not to silently show the permalink of a different team
  - The output is one item per line, and items are told apart by the form of the start of the line. Values the user can write (a channel's display name, a file name, a user's full name, nickname, position and email address) are put on one line by turning line breaks (including control characters that some displays treat as line breaks) into spaces. Mattermost does not reject line breaks in these, and they could be used to forge a line start. A channel's purpose and header contain Markdown tables and lists, so they are not put on one line, and the second and later lines are indented by 4 characters. In the attachment (`file_id: …, type: …, size, name: …`) and channel (`Channel: channel_id: …, name: …, display name: …`) lines, the ID is placed first and the file name or display name last, even within the same line. Where a channel and a team are joined on one line with ` | `, the team comes first and the display name is placed at the end of the line. The parentheses in the channel and user lists (`search_channels`, `list_my_channels`, `get_unreads`, `search_users`, `list_channel_members`), the "Destination:" of sending and scheduling, the "Channel:" of `edit_message` and `delete_message`, and the channel in the result of `mark_as_read` also place channel_id and user_id first and the display name, full name, nickname and position last. The start of the line of a channel whose team is unknown is the name, not the display name (the display name of a group DM is the list of members, which the user cannot rewrite, so it is shown at the start of the line). No fixed sentence of the tool (a result, a count, a pointer) follows a value the user can write. The result of `mark_as_read` and the channel lines of `get_unreads` put the display name at the end of the line; the note for when root_id is in another channel puts the display name inside the parentheses at the end of the sentence; and the candidates shown when a channel specified by ID is missing are each at the end of a line beginning with "Candidate". If a sentence could follow a value, the result or the target could be forged. For an archived channel, the mark is shown on the ID side (`name: …, archived, display name: …`), not attached to the display name, because writing "(archived)" in a display name could forge it. Likewise, writing "(file_id: …)" in a name would make a fake ID appear before the real ID. The tools that read a specified channel (read_channel, get_channel, list_channel_members), read_thread and get_post, which show the channel of a post, and mark_as_read, which shows channels in its result, also show the mark by the channel's `delete_at` (a mark_as_read line has no name, so the mark is placed after channel_id. For read_channel and the others, an archived channel is returned only when specified by ID. read_thread and get_post look up the channel of the post by ID, so it does not depend on how the channel was specified)
- A channel is specified in one of the following ways. If two or more candidates are found from a name, the tool fails with an error instead of choosing one, and returns the team names, channel names and channel IDs of the candidates. Whitespace and format characters (Unicode Cf: zero-width characters, direction marks, soft hyphens, etc.) around the specification are removed before it is interpreted. They easily slip in through copying, and channel names, team names, usernames and IDs are ASCII only, so removing them cannot match something else. Arguments that accept only an ID (`post_id`, `root_id`, `file_id`, `file_ids`, scheduled message IDs) are also checked after the same removal
  - A channel ID (26 alphanumeric characters). The ID is lowercased from the start before it is looked up (Mattermost IDs are lowercase only, so an ID written in uppercase is just a different way of writing the same ID). If there is no channel with that ID (404) and there is a channel whose name is the same string lowercased, the tool returns an error that tells the client to specify it in the `team/channel` form. This is because channel names are lowercase only and a name of 26 alphanumeric characters is possible (if there is none even for a lowercase ID, a mistyped name is likely). A channel found by name is not used in place of an ID. This is so that, when a user ID or a post ID is passed by mistake, the tool does not write into a channel whose name is that string (anyone can create one). A 403 shows that a channel with that ID exists, so the name is not looked up
  - `team/channel`
  - A channel name only (searched for in the teams the user belongs to)
    - When it is not found, the 403/404 of each team are combined into "not found", with a pointer to check the name with search_channels, a note that private channels the user has not joined and archived channels cannot be found by name (an archived channel cannot be written to, but to only read it, it can be specified by ID), and advice to retry and to check with the administrator. This sentence appears in every tool that specifies a channel by name. In the `in:` of a search, however, an archived channel can be searched by giving it to `in:` by ID, so if the user was a member, the message tells the client to ask the user for the ID and specify it by ID in `in:` (an archived public channel the user did not belong to gives 0 results even by ID)
  - `@username` (the DM with that person). If it is the user's own username, it means the DM with oneself (the same channel as the self-addressed notes in the UI). The tools that create DMs under the rule below also create the DM with oneself if it does not exist. Mattermost formally supports the DM with oneself (`POST /channels/direct` creates it as the DM with oneself when only the user's own ID remains after removing duplicates), and it can be used as a place for notes and drafts, so the server does not refuse it
  - `@a,b` (a group DM with members other than the user). Each element may or may not have a `@`, and the order does not matter. Uppercase is lowercased, duplicate names are merged into one, and the user's own name is dropped. An empty element is an error
    - A specification that uses a Japanese comma (、) or a full-width comma (，) as the separator, where every part it separates (excluding empty parts) can be used as a username, gets an error urging the client to write it with a half-width comma. A trailing Japanese comma (`@bob、`) is treated the same. This is judged before the empty-element error
    - It is an error unless there are 2 to 7 people other than the user. This is because a Mattermost group DM has 3 to 8 people including the user. For one person, the error urges the client to use `@username`
    - Users are looked up in one call with `POST /users/usernames`, and the names that are not found are listed in the error
    - A group DM is looked up with, as its name, the sha1 of the member IDs including the user, sorted and concatenated (the same as Mattermost's `GetGroupNameFromUserIds`). `POST /channels/group` creates the channel if it does not exist, so it is not used for reading
    - In the output destination, the members other than the user are listed as `@a, @b`
- A DM or group DM specified by channel ID also gets its name in the output aligned to `@username` and `@a, @b` (the members other than the user, sorted). This is because Mattermost leaves the display name of a DM empty and lists, in the display name of a group DM, the names at creation time including the user. If fetching the names (one call) fails with a Mattermost error or an outage (no response, abort, 5xx), the output continues with Mattermost's display name (re-authorization, rate limits and cancellation of the call by the user are thrown; after cancellation nobody is reading the output). This is so that a fetch made only for the output does not fail the tool itself. A DM that does not include the user (such as an administrator reading someone else's DM) and a group DM with no one other than the user also keep Mattermost's display name. The destination in the scheduled message list (`list_scheduled_messages`) is named the same way. The list is where a failure of a scheduled message is learned of, so even if fetching the names fails because of re-authorization or a rate limit, the list does not fail, and shows Mattermost's display name (for a DM, whose display name is empty, the channel name) (cancellation of the call by the user is thrown)
- The team name and channel name in a channel specification are lowercased before they are looked up. Mattermost names are lowercase only, and a name containing uppercase is rejected with 400. The error message shows the uppercase/lowercase form the user wrote
- When the DM for `@username` or the group DM for `@a,b` does not exist, only `send_message`, `save_draft`, `prepare_upload` and `schedule_message` among the write tools create it (`POST /channels/direct`, `POST /channels/group`). Read tools and `mark_as_read` do not create it. This is so as not to leave behind, merely by reading, a DM the user has not opened
  - `prepare_upload` creates it because the uploaded file is tied to the destination `channel_id`
  - An existing DM is looked up first. This is so that even a user without permission to create can write to a DM that already exists
  - When `root_id` or `file_ids` is passed, it is not created. A DM that does not exist yet has neither a parent post nor uploaded files, so the call would certainly fail right after creating it and leave only an empty DM
    - When `file_ids` is passed and the DM does not exist yet, the error in the files (not in the records, in another channel, duplicates) is returned before the fact that the DM does not exist. A file in a DM that does not exist yet is impossible, and the real mistake is in the file specification
  - A failure that can be known without asking Mattermost about the DM is checked before resolving the destination (creating the DM). These are the limit counts of `prepare_upload` and `schedule_message` (for `schedule_message`, only when a DM could be created, that is, for a specification beginning with `@` with neither `root_id` nor `file_ids`; otherwise an error in the channel name or files is returned first, and the limit is checked when the row of the scheduled message is created), and, for `save_draft`, draft sync being disabled (for a specification beginning with `@` without `root_id`, the draft list is fetched before resolution; with `root_id` no DM is created, so, as for a channel destination, an error in `root_id` is returned first. This list is used only for the check of whether sync is disabled and whether there are teams; the matching with an existing draft is done with a list fetched again just before saving, serialized with the deletion after `send_message` ("Deleting the draft after `send_message`"))
  - When `send_message` with `files` could create a DM (a specification beginning with `@` with neither `root_id` nor `file_ids`), and for a specification of `prepare_upload` beginning with `@`, as an exception to the rule above, the destination is first resolved without creating the DM. If the DM exists, it is used and the settings are not read. This is so that nothing is left empty, and so that a retry of a send that created the DM can proceed to the judgment on the records for preventing duplicate posts. Only when the DM does not exist, the client settings (`GET /config/client`) are read, and if attachments are disabled (`EnableFileAttachments`), or, for `send_message`, any file exceeds `MaxFileSize`, the call is refused without creating the DM. If it passes, the DM is created. `MaxFileSize` is a per-file limit, and is not checked unless it is digits only. A mistake in the destination that is known before looking for the DM, such as a user not being found, is returned before the settings are read. The other party being deactivated and a lack of permission to create the DM are known only when creating the DM, so they are returned after the settings check. The number of pixels of an image, the permission to upload, restricted DMs and rejection by plugins cannot be known from the settings, so if the call is refused for these, an empty DM is left
  - A DM is not created with a deactivated user (for a group DM, not if even one person is included). Mattermost can create it, but the other party cannot read it and only an empty DM remains
  - Creating a group DM is accepted at the same level as a DM, including the risk that a typo in a name matches a real different person. The specification is a list of names that the user or the AI stated explicitly, and there is no ground to demand more confirmation than for a DM
  - Even if a call fails after creating (when the limit is reached by a concurrent request between the earlier check and the later check, or when Mattermost refuses `files` of `send_message` for a reason that cannot be known from the settings), the DM that was created is not deleted. Mattermost's API cannot delete a DM (`DELETE /channels/{id}` refuses a DM). It is the same as opening a DM in the UI: an empty DM just appears in the list
- The `in:` of `search_posts` and `search_files` (including `-in:` and `channel:`) is passed to Mattermost after the MCP server replaces the channel specification with the channel ID. In a search across all teams, Mattermost looks up channel names without a team, so names do not work, and passing `in:@username` would create a DM
  - When two or more candidates are found from a name, as an exception to the rule above, it does not fail with an error but searches in all of the candidates and adds a note about this to the output. For `-in:`, all of the candidates are excluded and no note is added. `in:` is a condition that narrows the search, and each post in the output carries its team name, so they can be told apart
  - A group DM (`@a,b`) is also replaced. The same normalization as for a channel specification takes effect, and a user that is not found is an error. If this were left to Mattermost, it would look up each name as it is, so the search would silently return 0 results unless everyone including the user were written in lowercase
  - For a counterpart without a DM, `in:` gives an error and `-in:` drops the condition. The same applies when the group DM (`@a,b`) does not exist yet. In neither case is a DM or group DM created
  - `in:` and `channel:` are limited to 20 per search (including exclusions such as `-in:`), and when exceeded the call fails with an error without looking anything up. The limit is not written in the tool description (because the error message upon exceeding it also explains how to split), and the error message urges, for `in:`, splitting the search and re-attaching the exclusions to each split search (each search also up to 20), and, if there are many exclusions, reducing their number (an exclusion that does not overlap with `in:` has no effect, so it can be removed. If there is no `in:` and the channels to be searched are fewer, list them with `in:`. In that case it also notes that the search scope becomes only the channels listed) (because if the exclusions are split across searches, they do not take effect in the other search). Within the resolution of `in:` in one search, the same GET (the list of joined teams, a channel) is not repeated (it is looked up again for the output lines; see the item "The channel line of a post or file" above), and GETs not used in the output (the team name of a channel specified by ID, and the names of the counterparts of DMs and group DMs) are not called. Each name is looked up once per joined team (a specification in the form of an ID, once more if it is not found by ID), so with 10 teams the worst case is 221 calls, and adding the search itself (`POST /posts/search` or `POST /files/search`) and 3 calls for the output (`GET /users/me/channels`, `GET /users/me/teams`, `POST /users/ids`; in `search_posts`, if the authors and the people who reacted together exceed 1,000, `POST /users/ids` increases by 1 per 1,000) gives 225 calls, and adding the individual fetches of channels not in the list (the item "The channel line of a post or file" above; up to the display limit of 50; in practice nearly 0 except when archived channels are given to `in:`) gives about 275 calls. With 10 or fewer joined teams and no other calls in the same minute, this fits within the limit of 300 per minute per user. A user with more teams, or a time when the server-wide limit of 600 per minute is close, can hit a rate limit error in the middle of a search, but it appears as an error (with a retry hint) and results never change silently, so this is accepted
  - A channel or user that is not found is an error even for `-in:`, and the search is not run. The channel error is distinguished by the form of the specification and the response. When it is not found by name (channel name only, team/channel), it is the name message above (for searches); a 404 by ID gives a message about a mistaken ID (it does not recommend retrying, because an ID that does not exist will not be found by waiting); a 403 gives a message that the user has no permission to see it, with retrying and checking with the administrator (a 403 for "team/channel" occurs for a channel of a team the user does not belong to, or for a user without permission to see public channels such as a guest. A private channel the user has not joined gives a 404 by name); and when the team does not exist, a message about a mistaken team name. If a channel specified by ID is archived, `in:` searches including archived channels (`include_deleted_channels: true`. The search is limited to the channels given to `in:` and the narrowing to joined channels remains, so other archived channels and channels the user has not joined are not mixed in). `-in:` is passed as is (it also takes effect as an exclusion when another `in:` searches including archived channels)
  - Mattermost first looks up the value of `in:` as a channel name, and when it cannot, writes a warning to the server log (error getting channel id by name from in filter) and uses the value as is as the condition. For each `in:` or `-in:` value replaced with a channel_id, this warning and the lookup by channel name (one DB reference) occur (twice if ordinary terms and hashtags are mixed, because Mattermost then splits the conditions into 2 sets). The search results are correct (the later stage compares with IDs). There is no other way to pass it as an ID, so this is accepted
  - Search terms are split into words by whitespace, so no whitespace is allowed before or after the comma of `@a,b`. If there is, it is an error. When there is whitespace before the comma, a Japanese comma (、) or a full-width comma (，) after the whitespace is regarded as a comma only when what follows is empty or consists only of characters usable in usernames and separators. This is because some search terms begin with a Japanese comma or a full-width comma, such as `、議事録` or `，議事録`
- `send_message` always fails with an error when the destination is not uniquely determined. When `root_id` is passed, it checks that the post is a root post (not a reply) in the specified channel (the same check as `save_draft` and `schedule_message`). Mattermost refuses a post whose parent is a reply with a generic 400, so the tool refuses first with a message that states the reason
- A user is specified by user ID or `@username`. Surrounding whitespace and format characters are removed before it is interpreted, as with a channel specification
  - A user ID is also lowercased before it is looked up. Mattermost IDs are lowercase only, and an ID written in uppercase gives a 404
  - When, for the `@username` of a channel specification, looking up the user returns 400, 403 or 404, the tool fails with an error as a user that was not found. For a user with a restriction on viewing users, Mattermost returns 403 even for a name that does not exist, and returns 400 for reserved words such as `@all`
  - A username is lowercased before it is looked up. Mattermost usernames are lowercase only, and a name containing uppercase is rejected with 400
- The URL that `get_post` accepts is only one of the form `…/<team name>/pl/<post_id>` whose origin and base path match the Mattermost URL (`MM_BROWSER_URL`) and that contains no userinfo. This is so as not to misread the post_id of a permalink on another host as a post of this Mattermost. The team name in the URL is not used, and the permalink in the output is built from the post's actual team
- For `get_post` and `read_thread`, the 403 of the API that fetches the post and the 403 of the API that fetches the channel afterwards (for `read_thread`, also the 403 of the API that fetches the thread) get a message that does not assert that the cause is not being a member, and advises retrying if the user should be a member, and checking with the administrator if it continues (because a temporary failure or a permission setting also causes a 403). A 404 states that the post or channel was not found. The 403 when a post is fetched before saving, pinning, marking as read or following a thread gets the same message. The 403 of the file in `get_file` and the 403 of `pin_post` / `unpin_post` are also judged by Mattermost on the permission to read, so they likewise advise retrying and checking with the administrator (a 403 where a plugin refused the preview gets a different message)
- To keep one response from becoming too large, limits are set on the number of items and the length of the text. The concrete values are decided by the implementer
- A tool that shows posts shows, for each attached file, a line with the `file_id`, name, type, size and, for an image, the width and height. For a post that has no `metadata.files` and only `file_ids` (what the thread API returns), it shows only the count and that it can be checked with `get_post`. In a channel where an ABAC permission policy does not allow the user to download, Mattermost removes `metadata.files` and `file_ids` and puts the count in `metadata.redacted_file_count`, so the tool shows that count and that the files can be neither shown nor downloaded because of ABAC (so that it does not look as if there were no attachments). However, on a server with an ABAC permission policy enabled, when Mattermost temporarily cannot get the user's own information, it removes them in every channel without giving a count, so such a post looks as if it had no attachments (a known limit of "Posts with attached files")
- A tool that shows posts shows `props.attachments` (message attachments; notifications from bots and webhooks often leave the text empty and put the content here) after the text, one by one, under the heading `Message attachment (formatted display, e.g. from a bot) n/total:`. The items are, in order, the author, pretext, title (link), text, `fields`, footer, and the names of buttons and menus (noting that they cannot be operated from the MCP), and items whose value is empty are not shown. An attachment with no item to show also shows only the heading, so that the count is known
  - `fallback` is shown as a summary only when none of the pretext, title or its link, text and `fields` exist. It is a plain-text summary of the same content as the other items
  - Colors, images, icons and author links are not shown. They cannot be opened from the MCP and do not help understanding the content
  - Attachments can be written freely by the poster, so their types are not trusted. Attachments and elements that are not objects are skipped, and only strings, numbers and booleans are shown as values. All item lines are indented by 2 characters, and after a line break in a value (including control characters that some displays treat as line breaks) by 4 characters, so that a line inside an attachment does not take the same form as a post separator or a file line
  - The attachments, including headings and indentation, get a length limit of the same size as the text's, separate from the text. If they were summed with the text, the attachments would vanish entirely in a post with a long text. When cut, a note line is shown from the start of the line at the cut position
- A tool that shows posts indents each line of the text by 2 characters (line breaks are judged the same way as for attachments; the indentation is applied after cutting by the length limit, and an empty text shows one empty line). The guess can be wrong, so when it is Shift_JIS or EUC-JP, the output says that it is a guess and that, if the text is garbled, it may be another character encoding. Latin-1 (Windows-1252) is not made a candidate, because it accepts almost every byte sequence and would make even non-text files readable

Whether the whole was fetched is decided by whether the number of bytes fetched is less than 40,000 bytes (the end of the body was reached), or is exactly that and equal to the size in the information. The size in the information can differ from the actual content

The order is newest last reply first, and paging, as in `get_unreads`, shows the threads that had replies after the previous page in a section before the body. Threads of archived channels are not removed. A follow can be removed, so this can be used for cleanup. The channel list is fetched with `include_deleted=true`, and the channel and team lines are also shown for archived channels, with "archived" shown after the name on the channel line (to show that replying is impossible). This list always returns all channels the user was a member of at the time of archiving, but the approach of looking up, one by one with `GET /channels/{id}`, only the channels of the threads shown on the page is not adopted. If there are many followed threads in archived channels, it would add up to 50 calls per page, and advancing pages in succession would use up the MCP server's per-user limit (300 per minute) in a few pages. `POST /teams/{team_id}/channels/ids`, which can look up in bulk, returns only public channels that are not archived, so it cannot be used. With the current approach, one call is enough regardless of the number of archived channels. A root post that has no replies yet is not returned by Mattermost until its first reply, even if followed
- `follow_thread` and `unfollow_thread` accept the post_id of any post in the thread, and convert it to the root post before passing it to Mattermost. Mattermost returns success even for the ID of a reply, and a follow that takes effect neither on the list nor on notifications would remain. The team is the channel's team (for DMs and group DMs, the first team the user belongs to). The follow API does not depend on the team
  - `follow_thread` refuses a thread in a channel the user has not joined. Mattermost returns success, but the follow shows up neither in the list nor in notifications. If the thread is already followed, the follow API is not called. Mattermost marks the thread as read on every follow, so calling again would mark as read even replies the user has not read. Whether it is followed is looked at by fetching the thread's state, but for a root post without replies (`reply_count` is 0; this includes a thread whose replies were all deleted) that has never had a reply, Mattermost does not create the thread's state until the first reply, so even if it is followed the fetch gives 404. So only when the state fetch gives 404 and `reply_count` is 0, it is looked at with `is_following` of the thread fetch (`GET /posts/{id}/thread?collapsedThreads=true`). A thread with replies can be judged from the state fetch, so the calls do not increase. For a thread that was not followed, the replies up to the time of following are marked as read. The read position before that cannot be read through the API, so it is not restored. When newly followed, only for a root post without replies, the state is fetched again after the follow. If that gives 404, the thread's state does not exist yet, and the message adds that it does not show in the list until the first reply. A thread whose replies were all deleted still has its thread state even if `reply_count` is 0, so the re-fetch gives 200 and it also shows in the list, so nothing is added. Even if the re-fetch fails, the follow is already done, so the tool does not fail and only omits the addition. The only call added by the re-fetch is one, when newly following a root post without replies. In a configuration that uses a read replica, the re-fetch may read the stale state right after the PUT and give 404, and the addition may be made even for a thread whose replies were all deleted
  - `unfollow_thread` unfollows without a prior check. Unfollowing does not change the read state. Even after unfollowing, if the user is mentioned in that thread or replies to it, Mattermost follows it again. The output says so
  - In a thread in a DM or group DM, Mattermost treats every reply from the other party as a mention of the user, so even after unfollowing, one reply from the other party makes the user follow it again, and notifications also arrive. If unfollowed, the thread disappears from `list_followed_threads` until the next reply, so it does not refuse and unfollows, and the output says that the notifications do not stop
- `search_users` and `list_channel_members` do not add presence. It would add API calls per user, and calling `get_user` after choosing someone from the list is enough
- `search_files`, like `search_posts`, calls the all-teams search API once, interprets dates in JST, and cuts out the page from the 100 results with a cursor. `in:` (including `-in:` and `channel:`) is replaced with the channel_id and then passed, under the same rule as `search_posts` (the item above, "The `in:` of `search_posts` and `search_files`"). The approach of calling the per-team API in turn is not adopted, because the calls would increase by the number of teams and the creation of DMs could not be prevented either. Names match by the unit of words of the full-text search, and Japanese names are not split by whitespace, so they match only by the whole name or by prefix from the start (`*`). The tool description says so. When the file search is disabled by the server setting, the tool returns that fact and that the files can be looked for with `search_posts`. When resolving `in:` or building the search terms afterwards fails, it queries with only the search term `*` to find out whether the search is disabled, and then answers. Mattermost looks at the setting before converting channel names, and with only `*` it searches nothing. That it is found to be disabled only after the resolution is because the setting does not appear in the client settings (`/config/client`)
- The count of `list_saved_posts` is 20 by default and at most 50. Mattermost's saved posts API treats `page` as a number of items to skip, so a save or unsave between pages shifts the position. It also sorts by creation time only, so the order among posts with the same time can change from query to query. So the first query reads count + 21 items, and later ones 200 at a time, overlapping the last 20 of the previous query, reading from the start up to 1000. The overlapping 20 are shared between posts of the same time that straddle the boundary of queries and the shift of positions due to unsaving within one call. When posts of the same time that straddle a boundary exceed 21, or when, together with the shift caused by unsaving, the overlap is used up, a post can rarely be missed. When the first small query is empty, it reads again with 200 in case all of them were posts that cannot be read. The posts read are sorted newest first (by post_id if equal), and the `create_at` and post_id of the last post shown, and a rough position of the row that received that post, are put in the cursor. It stops reading when the page is satisfied. When it stops at 1000, it reads only 20 beyond that, and if any remain, says so (if all of those 20 are posts that cannot be read, it does not). The first query is kept small so that, on the frequently used first page, Mattermost is not made to build the metadata of 200 items. The continuation of a cursor reads count + 41 items from 20 before the rough position (cut at the 1000th; if 20 before is at the start or at the 980th or later, the rough position is not used). The rough position shifts because of a save or unsave between pages, and because Mattermost drops posts after counting or reorders within the same time, so it is used only when the items read include a post strictly newer than the cursor's post (all rows before that are newer than the cursor), and otherwise the tool re-reads from the start
- `list_channel_members` makes the member list readable, because the member count alone cannot answer who is in a channel and whom to ask. It is made an independent tool, not an option of `get_channel`. `get_channel` pages the pinned posts with a cursor, and one cursor cannot page two lists. It is also so as not to enlarge the output of `get_channel` for a channel with hundreds of members. The count is 50 by default and at most 200, and the page in Mattermost's username order is passed on as is. If members increase or decrease between pages, misses or duplicates can occur, but the username order does not change as often as posts do, so it is accepted. For a channel the user has not joined, Mattermost does not return members even for a public channel, so the tool says so. Mattermost judges by the permission to read (normally being a member of the channel), and returns the same 403 for a temporary failure and, very rarely, for a deletion right after fetching the channel, so the message does not assert the cause, and adds that, if the user should be a member, the client should wait and retry, and, if it continues, ask the administrator to check whether the user was removed from the channel or the permission to read was removed by the server's permission settings
- The cursor also contains the count and the type filter of `list_my_channels`, and when a cursor is passed, the argument side is ignored. This is so that the population does not change in the middle of the pages
