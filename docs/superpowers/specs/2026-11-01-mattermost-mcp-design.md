# Remote MCP Server for Mattermost: Design

## Purpose

Let Claude (claude.ai and the desktop app), Claude Code and Codex read and write Mattermost messages, in the same way as the Slack Connector.
A user starts using it just by adding the MCP server's URL (for example `https://mattermost.example.com/mcp`) as a connector and logging in with their Mattermost account.

Mattermost's official MCP server is part of the Agents plugin, and its HTTP endpoint for external MCP clients requires an Enterprise or higher license.
To make it usable with the free Team Edition too, this is built as an independent MCP server that runs outside Mattermost.

## Goals

- Connect from three clients, the claude.ai custom connector, Claude Code (`claude mcp add --transport http`) and Codex CLI, just by registering the URL and logging in with OAuth
- Each user acts with the permissions of their own Mattermost account. Channels and messages the user cannot see are not visible through MCP either
- The following operations are available
  - Searching messages
  - Reading a channel from its latest messages, from the first unread, or from a specified date and time range, and reading a thread
  - Reading a single post specified by a permalink URL or a post_id
  - Reading files attached to a post (an image as a downscaled image, a text file as its beginning) and searching files by name
  - Listing the posts the user saved (flagged)
  - Searching channels and users, and viewing user profiles
  - Viewing a user's time zone, local time and presence
  - Listing the channels the user has joined
  - Viewing a channel's type, purpose, header, member count and pinned posts
  - Listing the members of a channel the user may read (normally a channel the user has joined)
  - Listing the user's own unreads (channels and threads) and mentions of the user (which can also be limited to unread ones)
  - Marking the user's own channels and threads as read (up to the posts the AI has read)
  - Listing followed threads, and following and unfollowing threads
  - Posting to channels and threads (including attaching small files)
  - Adding and removing the user's own reactions on posts
  - Saving (flagging) and pinning or unpinning posts in joined channels (unsaving works regardless of membership)
  - Searching, by name, the custom emoji used for reactions and custom statuses
  - Changing the user's own presence and custom status
  - Editing and deleting the user's own posts
  - Saving a draft as the user's own Mattermost draft (the user sends it on screen)
  - Scheduling a post to a channel or thread at a specified time, and listing, changing and cancelling scheduled posts
- Once logged in, the user can keep using it without logging in again until they revoke it, as long as they keep using it (tokens are renewed with refresh tokens)

## Non-goals

- Editing or deleting other people's posts, creating channels and managing members
- System administration operations (user management, changing settings)
- Notifying MCP clients of Mattermost events (subscriptions, notifications)
- Supporting multiple Mattermost servers

## What to avoid

- Mattermost being operated through the MCP server with permissions other than the user's own
- A user's Mattermost permissions being handed to an MCP client the user did not intend
- Posting to an unintended channel
- Mattermost itself going down or slowing down. Failures or overload of the MCP server must not spread to the use of Mattermost
- Mattermost access tokens or message bodies remaining in logs

## Architecture

### Approach: the MCP server has its own authorization server and delegates login to Mattermost

Under the MCP specification (2025-06-18 and later), an MCP server must accept only tokens issued for itself, and passing a received token straight through to a downstream API (token passthrough) is prohibited.
Mattermost v11.7.8 has an implementation that receives and records the RFC 8707 `resource`, but it could not be confirmed that the REST API validates the audience of a token.
If an MCP client were given a Mattermost token directly, that MCP client could call all of Mattermost's APIs as the user.

So the MCP server takes on two roles.

1. **Authorization server for MCP clients**: it handles MCP client registration (Dynamic Client Registration), authorization and token issuance itself. The tokens it issues are addressed to the MCP server and cannot be used with Mattermost's API
2. **OAuth client of Mattermost**: it registers with Mattermost as just one confidential client and leaves the user's login to Mattermost's authorization screen. It stores the Mattermost tokens it obtains on the server side, encrypted, and does not hand them to MCP clients

```text
MCP client ──(MCP token)──> MCP server ──(Mattermost token)──> Mattermost API
       │                                   │
       └─ Authorization: the MCP server's /authorize ──> consent screen ──> Mattermost's /oauth/authorize (login)
```

### URLs and metadata

`/.well-known/oauth-authorization-server` directly under the domain is used by Mattermost's own metadata, so the MCP server's authorization server includes a path in its issuer and publishes its metadata in the path-insertion form of RFC 8414.

| Item | Value |
|---|---|
| MCP endpoint (resource) | `https://mattermost.example.com/mcp` (no trailing slash) |
| Protected Resource Metadata (RFC 9728) | `https://mattermost.example.com/.well-known/oauth-protected-resource/mcp` |
| Authorization server issuer | `https://mattermost.example.com/mcp` |
| Authorization Server Metadata | `https://mattermost.example.com/.well-known/oauth-authorization-server/mcp` |
| Endpoints for authorization, tokens, registration, the callback from Mattermost and so on | Under `https://mattermost.example.com/mcp/oauth/`. The implementer decides the concrete paths |

The metadata must include the following.

- Protected Resource Metadata: `resource` must exactly match the URL of the MCP endpoint (claude.ai requires an exact match including the path). `authorization_servers` is just the one issuer
- Authorization Server Metadata: `issuer`, `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]` (clients registered through DCR are public clients), `scopes_supported: ["mattermost"]`
- Also put `scopes_supported: ["mattermost"]` in the Protected Resource Metadata, and add `scope="mattermost"` to the `WWW-Authenticate` of the `401`

There is only one scope, `mattermost`, which means "use the tools as this user's Mattermost account".
Scopes are not split between reading and writing. Confirmation before a write is left to MCP clients that look at the tool annotation (`readOnlyHint`) ([Tools](#tools)).

- When `scope` is omitted from an authorization request, `mattermost` is given. If any scope other than `mattermost` is included, the request is rejected with `invalid_scope`
- The scope is bound to the authorization code, the grant, the access token and the refresh token, so that it cannot be widened by a refresh

The `resource` parameter is required in authorization requests and token requests, and is rejected with `invalid_target` if it is missing or does not exactly match the URL of the MCP endpoint.
The authorization codes and tokens issued can be used only for this one resource.
All three target clients send `resource` in the authorization request and the code exchange (["Client compatibility"](../../measurements.md#client-compatibility) in `docs/measurements.md`).

This form follows the discovery procedures of RFC 8414 and the MCP specification, and it was confirmed by measurement that the three clients can find metadata in this form and connect (["Client compatibility"](../../measurements.md#client-compatibility) in `docs/measurements.md`).

### Authorization flow

1. When an MCP client accesses `/mcp` without a token, the MCP server returns `401` and `WWW-Authenticate: Bearer resource_metadata="…"`
2. The MCP client learns the authorization server from the Protected Resource Metadata and fetches the Authorization Server Metadata
3. The MCP client registers itself with DCR (RFC 7591)
4. The MCP client sends the user to the MCP server's authorization endpoint with PKCE (`S256` required). The MCP server validates `client_id`, `redirect_uri`, PKCE and `resource`
5. The MCP server shows a consent screen
6. When the user allows it, the MCP server redirects to Mattermost's `/oauth/authorize`. For this authorization from the MCP server to Mattermost too, it attaches a PKCE (`S256`) generated separately from the MCP client's
7. The user logs in to Mattermost and allows it
8. When Mattermost returns to the callback, the MCP server checks `state`, obtains and stores the Mattermost tokens, and returns an authorization code to the MCP client
9. The MCP client exchanges the authorization code for MCP tokens (an access token and a refresh token) at the MCP server's token endpoint

### Authorization codes issued to MCP clients

To meet the authorization code requirements of OAuth 2.1 (draft-13 §4.1.2–4.1.3), the following is observed.

- The authorization code is a random value of sufficient length, and only its hash is stored on the server side. Its lifetime is about 1 minute
- The Mattermost user, `client_id`, the `redirect_uri` of the authorization request, the PKCE `code_challenge` (`S256`) and `resource` are bound to the authorization code and stored
- In a token request, it is checked that `client_id` and `redirect_uri` match the stored values and that `code_verifier` matches `code_challenge`. If any one does not match, the request is rejected with `invalid_grant`. A missing or mismatching `resource` is rejected with `invalid_target`
- Consuming the authorization code and issuing the tokens are done in a single transaction, so the same code cannot be used twice. If a used code is presented again, the tokens issued from that code are revoked
- The `state` received from the MCP client is stored separately from the `state` sent to Mattermost, and is returned to the MCP client unchanged, on success and on error alike

### Consent screen

The OAuth app on the Mattermost side is a single fixed client ID, and anyone can register a client with DCR.
Without a consent screen, a confused deputy attack succeeds in which the authorization of a user already logged in to Mattermost flows automatically to the redirect destination of a client the attacker registered.
Following the MCP Security Best Practices, the consent screen satisfies the following.

- It is always shown for every authorization request, before redirecting to Mattermost. It is not skipped by remembering consent, because the user authorizes only when adding a client, so showing it every time is no burden
- It shows the client name, the whole of the registered redirect URI, and the requested permission (the meaning of the scope `mattermost`: "read and write messages as your Mattermost account"). The client name can be set freely by the registrant, so the redirect URI is made more prominent than the name
- For a client whose redirect URI is a loopback (`localhost`, `127.0.0.1`), an additional warning is shown that says "this hands permissions to an app on this machine; allow it only if you yourself started connecting Claude Code or Codex" (Localhost Redirect URI Risks of MCP 2025-11-25)
- The allow form carries a CSRF token. The response carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`, so that other sites cannot embed it in an iframe
- The `state` sent to Mattermost is generated at the moment the user allows. The server-side record of the authorization in progress stores together the browser cookie, the `state` and PKCE sent to Mattermost, and the MCP client's `client_id`, `redirect_uri`, PKCE, `state` and `resource`. This record can be used only once and expires in about 10 minutes. At the callback, the request is rejected unless the `state` and the cookie match the record
- The client name and redirect URI registered with DCR are treated as untrusted values the registrant decided freely
  - Upper limits on length are set at registration, and values containing control characters are rejected
  - On the consent screen and error pages they are shown only through an auto-escaping template or as text nodes, and are never interpreted as HTML
  - External resources such as DCR's `logo_uri` are not loaded
  - Next to the client name, "the name is self-declared by the registrant and has not been verified" is shown
- The responses of the consent screen and error pages carry the equivalent of `Content-Security-Policy: default-src 'none'; style-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, so that no script runs at all. The consent screen is an HTML form that works without scripts
- An automated test checks that, when a client is registered with a malicious client name or redirect URI (an HTML tag, control characters, an extremely long value), no script runs on the consent screen and the display is not broken
- The cookie has a name starting with `__Host-`, carries `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`, and has no `Domain` (the Confused Deputy countermeasure of the MCP Security Best Practices). Its value is a random session ID, and the contents are held on the server side

### Redirect URIs

The redirect URIs accepted for registration with DCR are limited to the following.
A registration request that matches none of them is rejected with `invalid_redirect_uri`.

- `https://claude.ai/api/mcp/auth_callback` and `https://claude.com/api/mcp/auth_callback` (claude.ai and the desktop app. The current [Authentication for connectors](https://claude.com/docs/connectors/building/authentication#callback-urls) specifies only the `claude.ai` one, but Anthropic's old help center article (no longer published) recommended allowing both, because the callback might change to the `claude.com` side in the future. Adding one more Anthropic-managed domain with an exact match costs little, so both are allowed)
- Loopback (`http://localhost:<any port>/<any path>`, `http://127.0.0.1:<any port>/<any path>`) (Claude Code, Codex CLI)

Allowed patterns can be added through an environment variable.

The `redirect_uri` of an authorization request must exactly match a URI registered for that `client_id`.
The only exception is the port number of a loopback (RFC 8252, RFC 9700); the scheme, host, path and query must match.
When the `client_id` is unknown or the `redirect_uri` does not match, the error is not returned by redirect, and the MCP server's own error page is shown.

### MCP tokens

- The access token is short-lived (about 1 hour). The refresh token expires about 90 days after it was last used, and each rotation extends the expiry. There is no absolute expiry from issuance. As long as the user keeps using it, no re-login is needed, and only a user who did not use it for 90 days logs in again. The implementer decides the exact values
- Tokens are random opaque strings, and only their hashes are stored on the server side
- Refresh tokens are rotated (RFC 9700 §4.14.2). The series of tokens that continues from one authorization (a grant) is recorded, and a refresh records the used token and issues the new token in a single transaction. If a used refresh token is presented again, it is regarded as stolen, and all the access tokens and refresh tokens of that grant are revoked
- When the user revokes the MCP server's app from Mattermost's "Settings > Security > OAuth 2.0 Apps", all of that user's grants are revoked by the flow described below

### Mattermost tokens

Mattermost gives only one set of tokens to a pair of user and app, so the Mattermost tokens are stored as just one set per Mattermost user, and referenced from all of that user's grants.
If a copy were kept for each MCP client, the other copies would become invalid the moment any one of them refreshed.

- The access token and refresh token are stored encrypted with a key passed through an environment variable. Changing the key makes the stored tokens unreadable, and everyone logs in again
- When Mattermost's API returns `401`, the latest stored token is read again first. If another request has already refreshed, the request is retried once with that token
- Refreshing is done one at a time per user (requests that arrive at the same time wait for the result of one refresh). The new access token and refresh token are written in a single transaction
- Only when Mattermost returns `invalid_grant` to a refresh, or when the user has been deactivated, are that user's Mattermost tokens and MCP grants all revoked, and `401` is returned to the MCP client to prompt a re-login
- Mattermost rejects a request with an invalid session with `401` before calling the API handler (`web/handlers.go` in v11.7). So if a single call has received only `401`, it is treated as having made Mattermost process nothing. Even when a re-login becomes necessary, a post or an upload is "not sent", not "unknown whether sent". If a response other than `401` was received even once, or if the connection was lost after it was established, it is treated as possibly processed. This assumption does not hold for APIs where the server itself returns `401` (`deleteChannel`, `deleteUser` and so on), so review it when using them
- On temporary failures such as timeouts, connection failures and `5xx`, the stored information is left unchanged and a temporary tool error is returned

### Storage

The MCP server runs as just one process, so storage is a SQLite file placed on a volume.
What is stored is the registered MCP clients, the state of authorizations in progress, MCP grants and tokens, Mattermost tokens, the records for preventing duplicate `send_message` posts, and scheduled posts.

Of these, the DCR registration is done by each client just once per connection, and the `client_id` obtained is used from then on.
If the registration disappears, that client gets `invalid_client` and does not recover by logging in again (the connector has to be deleted and added again).
On the other hand, the DCR registration endpoint is public without authentication, so a third party can pile up registrations.
So registrations are handled in two kinds.

- **Authorized registrations** (registrations for which a user has completed authorization at least once): never deleted automatically. Authorization needs a Mattermost account, so a third party cannot increase them, and no limit is set on the total
- **Unauthorized registrations**: given a dedicated limit (a few hundred) and a lifetime (about 7 days). Those past the lifetime are deleted. When the limit is reached, a new registration is not rejected; the oldest unauthorized registration is deleted to make room. Even if a third party piles up registrations, legitimate users can still newly connect
- A client whose unauthorized registration was deleted is limited to cases such as leaving it for 7 days or more after starting authorization, and in that case the connector is added again
- A per-IP rate limit is also applied to the registration endpoint ("Limiting the load on Mattermost"). A warning log is written when unauthorized registrations approach the limit

No backup mechanism dedicated to the MCP server is provided.
The directory of the SQLite file and the encryption key are included in the deployment site's backup (a file copy or a disk snapshot).
If the SQLite file is lost, the SQLite file is restored from the latest backup by the following procedure, and the DCR registrations are brought back.
Clients registered after the backup do not come back, so those users are asked to add the connector again.

Restoring from an old backup puts the records of used refresh tokens and revoked grants back to a past state, and rotated old tokens may become valid again.
So restoring from a backup is limited to the following procedure.

1. Before starting the MCP server with the restored SQLite file, run the MCP server image's admin command in a standalone container with no network (mounting the whole directory, including SQLite's `-wal` and `-shm`) (`docker run --rm --network none -v <SQLite directory>:/data <image> <delete command>`), and delete all of the state of authorizations in progress, authorization codes, grants, MCP tokens, Mattermost tokens and the records for preventing duplicate `send_message` posts. The registered MCP clients (DCR registrations) are not deleted
   Then fail all waiting and posting scheduled posts ("Restore" in [Scheduled posts](#scheduled-posts))
2. Only after that, start the MCP server. When restoring in a form where the MCP server starts automatically on restore, such as a disk snapshot, finish step 1 before the automatic start, so that there is no route by which requests can reach the rolled-back MCP server

Because the DCR registrations are kept, each client does not need to add the connector again, and recovers just by the usual re-login after the refresh token it holds is rejected with `invalid_grant`.
DCR registrations hold no user permissions, so there is no real harm if they are rolled back.
The encryption key is not regenerated. The Mattermost tokens are deleted, but the bodies of the scheduled posts that were failed stay encrypted with the same key for 7 days from the update, and regenerating the key would make the bodies unreadable in the list.
This procedure is written in the operations manual (`docs/operations.md`).

The approach of adding a DB to Mattermost's PostgreSQL is not adopted.
It would share Mattermost's DB and its operations (dump, restore, major version updates), and we do not want to create situations where the MCP server's needs require touching Mattermost's DB.

### MCP transport

Streamable HTTP is provided at `/mcp`.
It is in stateless mode with no sessions, and notification subscriptions are not provided.
The old HTTP+SSE transport is not provided (all three target clients support Streamable HTTP).

Following the MCP Streamable HTTP specification, a request with an `Origin` header is rejected with `403` unless the origin is in an allowlist (by default `https://claude.ai` and `https://claude.com`, more can be added through an environment variable).
A request without an `Origin` header (from a CLI or server-to-server communication) is accepted with only bearer token validation.

### Tools

Every tool calls the Mattermost REST API v4 with the Mattermost token of the user who made the call.
The MCP server itself has no admin token or bot account.

| Tool | Description |
|---|---|
| `search_posts` | Searches messages in the teams the user belongs to. Mattermost search syntax (`from:`, `in:`, `before:`, `after:`, etc.) can be passed through as is. `in:` accepts a channel specification (below). It does not create DMs. Mattermost's standard database search does not match the contents of message attachments, so the tool description says so and urges the client to read with `read_channel` when looking for such contents |
| `read_channel` | Reads the latest messages of a channel, newest first, with the number of messages specified. With `from: "unread"`, it reads from the start of the unread messages, oldest first. When `since` (and `until`) is passed, it reads the posts in that date range, oldest first. Paging is supported. Reading does not mark the channel as read |
| `read_thread` | Reads the root post and replies of a thread, oldest first. Paging is supported |
| `get_post` | Reads one post, specified by a permalink URL or a post_id, together with its channel, team and reply count. For a reply, it shows the post_id of the parent; for a root post that has replies, it shows that the rest can be read with `read_thread` |
| `get_file` | Reads a file attached to a post by `file_id`. For an image, it returns the Mattermost preview (a reduced version no wider than 1920px) as MCP image content. It does not return the original size. For text (UTF-8, or Shift_JIS or EUC-JP with the extension csv, tsv, txt or log), it returns the contents up to the first 10,000 characters. For anything else, such as a PDF, it returns only the name, type and size |
| `search_files` | Searches attached files in the channels the user belongs to (archived ones only when given to `in:` by channel ID), DMs and group DMs, by name and Mattermost search syntax (`from:`, `in:`, `ext:`, `before:`, etc.). For each file, it returns the `file_id` and, if there is a post, the `post_id` and permalink, so that the client can continue with `get_file` and `get_post` |
| `list_saved_posts` | Lists, newest first, the posts the user saved (flagged) that are in channels the user belongs to. It also includes posts in archived channels, and shows "archived" after the name on that channel's line (so that the channel is not chosen as a destination). Saves are added and removed with `save_post` / `unsave_post` |
| `search_channels` | Searches channels by name (public channels, and the private channels, DMs and group DMs the user belongs to) |
| `list_my_channels` | Lists the channels the user belongs to (public, private, DM, group DM), newest last post first. Can be filtered by type. Archived channels are not included |
| `get_channel` | Reads a channel's type, purpose, header, member count and pinned posts. The member list is read with `list_channel_members`. Pins are added and removed with `pin_post` / `unpin_post` |
| `list_channel_members` | Lists the members (excluding deactivated users) of a channel the user has permission to read (normally a channel the user belongs to), in username order |
| `search_users` | Searches users by name or username |
| `get_user` | Reads a user's profile, with the time zone, the local time at the moment of the call, and the presence (online, away, do not disturb, offline, out of office) |
| `get_unreads` | Lists the channels with unread messages (unread count, mention count) and, if collapsed reply threads (CRT) are enabled, the threads with unread replies. It does not mark anything as read |
| `get_mentions` | Lists mentions of the user (`@username` and the keywords in the notification settings), newest first. It covers all teams and DMs. With `unread_only`, only unread mentions are listed |
| `list_followed_threads` | Lists the threads the user follows, newest last reply first. It covers all teams and DMs. It cannot be used by a user who has collapsed reply threads (CRT) disabled |
| `follow_thread` | Follows a thread. Does nothing if the thread is already followed |
| `unfollow_thread` | Unfollows a thread |
| `mark_as_read` | Marks the user's own channels and threads as read. A channel that has a post by someone other than the user after `last_post_id` (the newest of the posts that were read) is not marked as read, and a thread is marked as read up to that post. Up to 20 items in total |
| `send_message` | Posts to a channel. Passing `root_id` makes it a reply to a thread. `files` attaches 1 to 5 files, up to 128KiB in total contents. `file_ids` attaches 1 to 5 files uploaded through `prepare_upload`. If a draft with the same text exists for the same destination, it is deleted after posting (a draft with attachments is not deleted) |
| `prepare_upload` | Issues a single-use upload URL with which the MCP client sends, using `curl`, a file on the user's PC |
| `add_reaction` | Adds the user's own reaction to a post. The emoji is specified by its Mattermost emoji name, and surrounding colons are removed on input. Aliases (such as `thumbsup` and `+1`) are not merged, because Mattermost itself treats them as separate reactions. The argument description and the error for an unknown name tell the client to look up the name of a custom emoji with `search_emoji` |
| `remove_reaction` | Removes the user's own reaction from a post. It does not remove other people's reactions. Mattermost returns success even for a reaction that was not there, so whether anything was removed is not distinguished. How the emoji name is accepted and the pointer to `search_emoji` are the same as for `add_reaction` (an emoji with a name that does not exist also succeeds, so the pointer appears only when a name containing characters that cannot be used in a name is passed) |
| `save_post` | Adds a post to the user's own saved posts. It handles only posts in channels the user belongs to. Mattermost can also save a post in a public channel the user does not belong to, but such a save appears neither in `list_saved_posts` nor in the saved posts screen of Mattermost, so the tool refuses, to avoid the mismatch of reporting that it saved a post that then cannot be found. It succeeds even if the post is already saved |
| `unsave_post` | Removes a post from the user's own saved posts. It checks neither the post nor the membership of the channel. This is so that a save left over after the user left the channel can also be removed (when a post is deleted, Mattermost also deletes the saves of that post, but when the root post of a thread is deleted, the saves of its replies remain, and a save may also be left undeleted by mistake; these can be removed too). Whether anything was removed is not distinguished. It succeeds even if the post was not saved |
| `pin_post` | Pins a post to the channel. It only puts a channel-level mark on the post without changing its text, so it is not the non-goal "editing other people's posts". It handles only posts in channels the user belongs to. Mattermost allows it even in a public channel the user does not belong to, but because the mark is visible to everyone in the channel, the tool does not change it in a channel the user does not belong to. For a post past the server's edit time limit (`ServiceSettings.PostEditTimeLimit`), Mattermost also refuses to add or remove a pin. It succeeds even if the post is already pinned |
| `unpin_post` | Removes the pin from a post. Mattermost does not record who pinned a post, so another person's pin is removed as well. It handles only posts in channels the user belongs to. It succeeds even if the post was not pinned |

Changing from out of office makes Mattermost stop the automatic replies, and the MCP cannot restore them, so the annotation is `destructiveHint: true` |

- Any tool that is passed a key not in its arguments (inputSchema) fails with an error, without running, and the error returns the names of the keys it does not accept. The MCP SDK by default silently drops unknown arguments, so passing a misnamed argument (for example `file_id` for `file_ids`) would post or change things as if it were absent. The registration of tools is wrapped in one place (`buildServer`), which makes the argument definition of each tool strict. For this reason, a new argument added to a tool must always be written in its inputSchema. A tool that accepts no arguments also writes `{}` as its inputSchema (a tool without an inputSchema is not covered by the wrapper). A tool that is passed a zod schema directly makes it strict itself. Keys inside nested objects are not covered (the elements of `channels` and `threads` in `mark_as_read` are an exception; see the section "Marking as read")
- Read tools get the MCP tool annotation `readOnlyHint: true`, and write tools (`send_message`, `prepare_upload`, `add_reaction`, `remove_reaction`, `save_post`, `unsave_post`, `pin_post`, `unpin_post`, `edit_message`, `delete_message`, `save_draft`, `schedule_message`, `update_scheduled_message`, `cancel_scheduled_message`, `mark_as_read`, `set_status`, `set_custom_status`, `clear_custom_status`, `follow_thread`, `unfollow_thread`) do not. This is so that the MCP client can ask the user for confirmation before a write
- The annotations of `save_post`, `unsave_post`, `pin_post` and `unpin_post` are `readOnlyHint: false`, `destructiveHint: false` and `idempotentHint: true`. The removing side also leaves a state that the user can see and that can be restored by adding again (except for the pin of a post past the edit time limit. Who pinned a post is not recorded, so another person's pin can also be added again. A save of a post in a channel the user has left cannot be added again until the user rejoins, but that save appears neither in the saved posts screen of Mattermost nor in `list_saved_posts`. Deleting the root post of a thread also deletes its replies together, and only the saves of the replies remain. Such a save cannot be added again, but it likewise does not appear in the list). In the MCP definition, `destructiveHint: false` refers only to additive updates, but this server, as with `mark_as_read`, sets it by whether the change can be undone
- The output is text that is easy for an LLM to read, and includes, for each post, the author's username, the date and time, the text and the permalink (`https://mattermost.example.com/<team>/pl/<post_id>`). The output of read tools also includes the IDs and names of the channel and team, so that the LLM can use the IDs in later calls
  - The channel line of a post or file and the team of a permalink are looked up from the list of joined channels. `search_posts`, `get_mentions` and `search_files` fetch a list that does not include archived channels (because a search returns archived channels only when they are given to `in:`), and `list_saved_posts` fetches a list that includes them (because there are saved posts in archived channels too). Only the channel_ids that are not in the list (channels archived after the search, and the archived channels given to `in:`) are looked up one by one, without duplicates, with `GET /channels/{id}`. Unlike `list_followed_threads`, these are called only rarely apart from when archived channels are given to `in:` (`in:` accepts up to 20, so at most 20 calls), so one at a time is enough. The number of calls is capped by the number of distinct channel_ids on the one displayed page (at most 50, the maximum of limit), which is small compared with the server's own limit (300 per minute per user) for these lookups. Approaching 50 happens only in one-off situations, such as the user leaving a team between fetching the posts or files and fetching the channel list, and the next page does not show those posts or files, so it does not accumulate as pages are advanced (this differs from the archived threads of `list_followed_threads`, which keep appearing on every page). The archived channels given to `in:` appear on every page, so they are looked up again on every page, and are looked up twice in one search together with the lookups made when resolving `in:`; but `in:` is limited to 20 channels per page, a search is cut off at 100 results so the number of pages is also bounded, and the total fits within the estimate for one search (about 275 calls), so no mechanism for carrying the result of the resolution over to the output is built. If the user left the team, that line falls under the 403/404 handling below. On 403/404, the line is the channel_id and the permalink uses the user's first team. Any other error fails the tool (an exception to the DM naming rule, which gives up a lookup made only for the output). This is so as not to silently show the permalink of a different team
  - The output is one item per line, and items are told apart by the form of the start of the line. Values the user can write (a channel's display name, a file name, a user's full name, nickname, position and email address) are put on one line by turning line breaks (including control characters that some displays treat as line breaks) into spaces. Mattermost does not reject line breaks in these, and they could be used to forge a line start. A channel's purpose and header contain Markdown tables and lists, so they are not put on one line, and the second and later lines are indented by 4 characters. In the attachment (`file_id: …, type: …, size, name: …`) and channel (`Channel: channel_id: …, name: …, display name: …`) lines, the ID is placed first and the file name or display name last, even within the same line. Where a channel and a team are joined on one line with ` | `, the team comes first and the display name is placed at the end of the line. The parentheses in the channel and user lists (`search_channels`, `list_my_channels`, `get_unreads`, `search_users`, `list_channel_members`), the "Destination:" of sending and scheduling, the "Channel:" of `edit_message` and `delete_message`, and the channel in the result of `mark_as_read` also place channel_id and user_id first and the display name, full name, nickname and position last. The start of the line of a channel whose team is unknown is the name, not the display name (the display name of a group DM is the list of members, which the user cannot rewrite, so it is shown at the start of the line). No fixed sentence of the tool (a result, a count, a pointer) follows a value the user can write. The result of `mark_as_read` and the channel lines of `get_unreads` put the display name at the end of the line; the note for when root_id is in another channel puts the display name inside the parentheses at the end of the sentence; and the candidates shown when a channel specified by ID is missing are each at the end of a line beginning with "Candidate". If a sentence could follow a value, the result or the target could be forged. For an archived channel, the mark is shown on the ID side (`name: …, archived, display name: …`), not attached to the display name, because writing "(archived)" in a display name could forge it. Likewise, writing "(file_id: …)" in a name would make a fake ID appear before the real ID. The tools that read a specified channel (read_channel, get_channel, list_channel_members), read_thread and get_post, which show the channel of a post, and mark_as_read, which shows channels in its result, also show the mark by the channel's `delete_at` (a mark_as_read line has no name, so the mark is placed after channel_id. For read_channel and the others, an archived channel is returned only when specified by ID. read_thread and get_post look up the channel of the post by ID, so it does not depend on how the channel was specified)
- A channel is specified in one of the following ways. If two or more candidates are found from a name, the tool fails with an error instead of choosing one, and returns the team names, channel names and channel IDs of the candidates. Whitespace and format characters (Unicode Cf: zero-width characters, direction marks, soft hyphens, etc.) around the specification are removed before it is interpreted. They easily slip in through copying, and channel names, team names, usernames and IDs are ASCII only, so removing them cannot match something else. Arguments that accept only an ID (`post_id`, `root_id`, `file_id`, `file_ids`, scheduled message IDs) are also checked after the same removal
  - A channel ID (26 alphanumeric characters). The ID is lowercased from the start before it is looked up (Mattermost IDs are lowercase only, so an ID written in uppercase is just a different way of writing the same ID). If there is no channel with that ID (404) and there is a channel whose name is the same string lowercased, the tool returns an error that tells the client to specify it in the `team/channel` form. This is because channel names are lowercase only and a name of 26 alphanumeric characters is possible (if there is none even for a lowercase ID, a mistyped name is likely). A channel found by name is not used in place of an ID. This is so that, when a user ID or a post ID is passed by mistake, the tool does not write into a channel whose name is that string (anyone can create one). A 403 shows that a channel with that ID exists, so the name is not looked up
  - `team/channel`
  - A channel name only (searched for in the teams the user belongs to)
    - When it is not found, the 403/404 of each team are combined into "not found", with a pointer to check the name with search_channels, a note that private channels the user has not joined and archived channels cannot be found by name (an archived channel cannot be written to, but to only read it, it can be specified by ID), and advice to retry and to check with the administrator. This sentence appears in every tool that specifies a channel by name. In the `in:` of a search, however, an archived channel can be searched by giving it to `in:` by ID, so if the user was a member, the message tells the client to ask the user for the ID and specify it by ID in `in:` (an archived public channel the user did not belong to gives 0 results even by ID)
  - `@username` (the DM with that person). If it is the user's own username, it means the DM with oneself (the same channel as the self-addressed notes in the UI). The tools that create DMs under the rule below also create the DM with oneself if it does not exist. Mattermost formally supports the DM with oneself (`POST /channels/direct` creates it as the DM with oneself when only the user's own ID remains after removing duplicates), and it can be used as a place for notes and drafts, so the server does not refuse it
  - `@a,b` (a group DM with members other than the user). Each element may or may not have a `@`, and the order does not matter. Uppercase is lowercased, duplicate names are merged into one, and the user's own name is dropped. An empty element is an error
    - A specification that uses a Japanese comma (、) or a full-width comma (，) as the separator, where every part it separates (excluding empty parts) can be used as a username, gets an error urging the client to write it with a half-width comma. A trailing Japanese comma (`@bob、`) is treated the same. This is judged before the empty-element error
    - It is an error unless there are 2 to 7 people other than the user. This is because a Mattermost group DM has 3 to 8 people including the user. For one person, the error urges the client to use `@username`
    - Users are looked up in one call with `POST /users/usernames`, and the names that are not found are listed in the error
    - A group DM is looked up with, as its name, the sha1 of the member IDs including the user, sorted and concatenated (the same as Mattermost's `GetGroupNameFromUserIds`). `POST /channels/group` creates the channel if it does not exist, so it is not used for reading
    - In the output destination, the members other than the user are listed as `@a, @b`
- A DM or group DM specified by channel ID also gets its name in the output aligned to `@username` and `@a, @b` (the members other than the user, sorted). This is because Mattermost leaves the display name of a DM empty and lists, in the display name of a group DM, the names at creation time including the user. If fetching the names (one call) fails with a Mattermost error or an outage (no response, abort, 5xx), the output continues with Mattermost's display name (re-authorization, rate limits and cancellation of the call by the user are thrown; after cancellation nobody is reading the output). This is so that a fetch made only for the output does not fail the tool itself. A DM that does not include the user (such as an administrator reading someone else's DM) and a group DM with no one other than the user also keep Mattermost's display name. The destination in the scheduled message list (`list_scheduled_messages`) is named the same way. The list is where a failure of a scheduled message is learned of, so even if fetching the names fails because of re-authorization or a rate limit, the list does not fail, and shows Mattermost's display name (for a DM, whose display name is empty, the channel name) (cancellation of the call by the user is thrown)
- The team name and channel name in a channel specification are lowercased before they are looked up. Mattermost names are lowercase only, and a name containing uppercase is rejected with 400. The error message shows the uppercase/lowercase form the user wrote
- When the DM for `@username` or the group DM for `@a,b` does not exist, only `send_message`, `save_draft`, `prepare_upload` and `schedule_message` among the write tools create it (`POST /channels/direct`, `POST /channels/group`). Read tools and `mark_as_read` do not create it. This is so as not to leave behind, merely by reading, a DM the user has not opened
  - `prepare_upload` creates it because the uploaded file is tied to the destination `channel_id`
  - An existing DM is looked up first. This is so that even a user without permission to create can write to a DM that already exists
  - When `root_id` or `file_ids` is passed, it is not created. A DM that does not exist yet has neither a parent post nor uploaded files, so the call would certainly fail right after creating it and leave only an empty DM
    - When `file_ids` is passed and the DM does not exist yet, the error in the files (not in the records, in another channel, duplicates) is returned before the fact that the DM does not exist. A file in a DM that does not exist yet is impossible, and the real mistake is in the file specification
  - A failure that can be known without asking Mattermost about the DM is checked before resolving the destination (creating the DM). These are the limit counts of `prepare_upload` and `schedule_message` (for `schedule_message`, only when a DM could be created, that is, for a specification beginning with `@` with neither `root_id` nor `file_ids`; otherwise an error in the channel name or files is returned first, and the limit is checked when the row of the scheduled message is created), and, for `save_draft`, draft sync being disabled (for a specification beginning with `@` without `root_id`, the draft list is fetched before resolution; with `root_id` no DM is created, so, as for a channel destination, an error in `root_id` is returned first. This list is used only for the check of whether sync is disabled and whether there are teams; the matching with an existing draft is done with a list fetched again just before saving, serialized with the deletion after `send_message` ("Deleting the draft after `send_message`"))
  - When `send_message` with `files` could create a DM (a specification beginning with `@` with neither `root_id` nor `file_ids`), and for a specification of `prepare_upload` beginning with `@`, as an exception to the rule above, the destination is first resolved without creating the DM. If the DM exists, it is used and the settings are not read. This is so that nothing is left empty, and so that a retry of a send that created the DM can proceed to the judgment on the records for preventing duplicate posts. Only when the DM does not exist, the client settings (`GET /config/client`) are read, and if attachments are disabled (`EnableFileAttachments`), or, for `send_message`, any file exceeds `MaxFileSize`, the call is refused without creating the DM. If it passes, the DM is created. `MaxFileSize` is a per-file limit, and is not checked unless it is digits only. A mistake in the destination that is known before looking for the DM, such as a user not being found, is returned before the settings are read. The other party being deactivated and a lack of permission to create the DM are known only when creating the DM, so they are returned after the settings check. The number of pixels of an image, the permission to upload, restricted DMs and rejection by plugins cannot be known from the settings, so if the call is refused for these, an empty DM is left
  - A DM is not created with a deactivated user (for a group DM, not if even one person is included). Mattermost can create it, but the other party cannot read it and only an empty DM remains
  - Creating a group DM is accepted at the same level as a DM, including the risk that a typo in a name matches a real different person. The specification is a list of names that the user or the AI stated explicitly, and there is no ground to demand more confirmation than for a DM
  - Even if a call fails after creating (when the limit is reached by a concurrent request between the earlier check and the later check, or when Mattermost refuses `files` of `send_message` for a reason that cannot be known from the settings), the DM that was created is not deleted. Mattermost's API cannot delete a DM (`DELETE /channels/{id}` refuses a DM). It is the same as opening a DM in the UI: an empty DM just appears in the list
- The `in:` of `search_posts` and `search_files` (including `-in:` and `channel:`) is passed to Mattermost after the MCP server replaces the channel specification with the channel ID. In a search across all teams, Mattermost looks up channel names without a team, so names do not work, and passing `in:@username` would create a DM
  - When two or more candidates are found from a name, as an exception to the rule above, it does not fail with an error but searches in all of the candidates and adds a note about this to the output. For `-in:`, all of the candidates are excluded and no note is added. `in:` is a condition that narrows the search, and each post in the output carries its team name, so they can be told apart
  - A group DM (`@a,b`) is also replaced. The same normalization as for a channel specification takes effect, and a user that is not found is an error. If this were left to Mattermost, it would look up each name as it is, so the search would silently return 0 results unless everyone including the user were written in lowercase
  - For a counterpart without a DM, `in:` gives an error and `-in:` drops the condition. The same applies when the group DM (`@a,b`) does not exist yet. In neither case is a DM or group DM created
  - `in:` and `channel:` are limited to 20 per search (including exclusions such as `-in:`), and when exceeded the call fails with an error without looking anything up. The limit is not written in the tool description (because the error message upon exceeding it also explains how to split), and the error message urges, for `in:`, splitting the search and re-attaching the exclusions to each split search (each search also up to 20), and, if there are many exclusions, reducing their number (an exclusion that does not overlap with `in:` has no effect, so it can be removed. If there is no `in:` and the channels to be searched are fewer, list them with `in:`. In that case it also notes that the search scope becomes only the channels listed) (because if the exclusions are split across searches, they do not take effect in the other search). Within the resolution of `in:` in one search, the same GET (the list of joined teams, a channel) is not repeated (it is looked up again for the output lines; see the item "The channel line of a post or file" above), and GETs not used in the output (the team name of a channel specified by ID, and the names of the counterparts of DMs and group DMs) are not called. Each name is looked up once per joined team (a specification in the form of an ID, once more if it is not found by ID), so with 10 teams the worst case is 221 calls, and adding the search itself (`POST /posts/search` or `POST /files/search`) and 3 calls for the output (`GET /users/me/channels`, `GET /users/me/teams`, `POST /users/ids`; in `search_posts`, if the authors and the people who reacted together exceed 1,000, `POST /users/ids` increases by 1 per 1,000) gives 225 calls, and adding the individual fetches of channels not in the list (the item "The channel line of a post or file" above; up to the display limit of 50; in practice nearly 0 except when archived channels are given to `in:`) gives about 275 calls. With 10 or fewer joined teams and no other calls in the same minute, this fits within the limit of 300 per minute per user. A user with more teams, or a time when the server-wide limit of 600 per minute is close, can hit a rate limit error in the middle of a search, but it appears as an error (with a retry hint) and results never change silently, so this is accepted
  - A channel or user that is not found is an error even for `-in:`, and the search is not run. The channel error is distinguished by the form of the specification and the response. When it is not found by name (channel name only, team/channel), it is the name message above (for searches); a 404 by ID gives a message about a mistaken ID (it does not recommend retrying, because an ID that does not exist will not be found by waiting); a 403 gives a message that the user has no permission to see it, with retrying and checking with the administrator (a 403 for "team/channel" occurs for a channel of a team the user does not belong to, or for a user without permission to see public channels such as a guest. A private channel the user has not joined gives a 404 by name); and when the team does not exist, a message about a mistaken team name. If a channel specified by ID is archived, `in:` searches including archived channels (`include_deleted_channels: true`. The search is limited to the channels given to `in:` and the narrowing to joined channels remains, so other archived channels and channels the user has not joined are not mixed in). `-in:` is passed as is (it also takes effect as an exclusion when another `in:` searches including archived channels)
  - Mattermost first looks up the value of `in:` as a channel name, and when it cannot, writes a warning to the server log (error getting channel id by name from in filter) and uses the value as is as the condition. For each `in:` or `-in:` value replaced with a channel_id, this warning and the lookup by channel name (one DB reference) occur (twice if ordinary terms and hashtags are mixed, because Mattermost then splits the conditions into 2 sets). The search results are correct (the later stage compares with IDs). There is no other way to pass it as an ID, so this is accepted
  - Search terms are split into words by whitespace, so no whitespace is allowed before or after the comma of `@a,b`. If there is, it is an error. When there is whitespace before the comma, a Japanese comma (、) or a full-width comma (，) after the whitespace is regarded as a comma only when what follows is empty or consists only of characters usable in usernames and separators. This is because some search terms begin with a Japanese comma or a full-width comma, such as `、議事録` or `，議事録`
- `send_message` always fails with an error when the destination is not uniquely determined. When `root_id` is passed, it checks that the post is a root post (not a reply) in the specified channel (the same check as `save_draft` and `schedule_message`). Mattermost refuses a post whose parent is a reply with a generic 400, so the tool refuses first with a message that states the reason
- A user is specified by user ID or `@username`. Surrounding whitespace and format characters are removed before it is interpreted, as with a channel specification
  - A user ID is also lowercased before it is looked up. Mattermost IDs are lowercase only, and an ID written in uppercase gives a 404
  - When, for the `@username` of a channel specification, looking up the user returns 400, 403 or 404, the tool fails with an error as a user that was not found. For a user with a restriction on viewing users, Mattermost returns 403 even for a name that does not exist, and returns 400 for reserved words such as `@all`
  - A username is lowercased before it is looked up. Mattermost usernames are lowercase only, and a name containing uppercase is rejected with 400
- The URL that `get_post` accepts is only one of the form `…/<team name>/pl/<post_id>` whose origin and base path match the Mattermost URL (`MM_BROWSER_URL`) and that contains no userinfo. This is so as not to misread the post_id of a permalink on another host as a post of this Mattermost. The team name in the URL is not used, and the permalink in the output is built from the post's actual team
- For `get_post` and `read_thread`, the 403 of the API that fetches the post and the 403 of the API that fetches the channel afterwards (for `read_thread`, also the 403 of the API that fetches the thread) get a message that does not assert that the cause is not being a member, and advises retrying if the user should be a member, and checking with the administrator if it continues (because a temporary failure or a permission setting also causes a 403). A 404 states that the post or channel was not found. The 403 when a post is fetched before saving, pinning, marking as read or following a thread gets the same message. The 403 of the file in `get_file` and the 403 of `pin_post` / `unpin_post` are also judged by Mattermost on the permission to read, so they likewise advise retrying and checking with the administrator (a 403 where a plugin refused the preview gets a different message)
- To keep one response from becoming too large, limits are set on the number of items and the length of the text. The concrete values are decided by the implementer
- A tool that shows posts shows, for each attached file, a line with the `file_id`, name, type, size and, for an image, the width and height. For a post that has no `metadata.files` and only `file_ids` (what the thread API returns), it shows only the count and that it can be checked with `get_post`. In a channel where an ABAC permission policy does not allow the user to download, Mattermost removes `metadata.files` and `file_ids` and puts the count in `metadata.redacted_file_count`, so the tool shows that count and that the files can be neither shown nor downloaded because of ABAC (so that it does not look as if there were no attachments). However, on a server with an ABAC permission policy enabled, when Mattermost temporarily cannot get the user's own information, it removes them in every channel without giving a count, so such a post looks as if it had no attachments (a known limit of "Posts with attached files")
- A tool that shows posts shows `props.attachments` (message attachments; notifications from bots and webhooks often leave the text empty and put the content here) after the text, one by one, under the heading `Message attachment (formatted display, e.g. from a bot) n/total:`. The items are, in order, the author, pretext, title (link), text, `fields`, footer, and the names of buttons and menus (noting that they cannot be operated from the MCP), and items whose value is empty are not shown. An attachment with no item to show also shows only the heading, so that the count is known
  - `fallback` is shown as a summary only when none of the pretext, title or its link, text and `fields` exist. It is a plain-text summary of the same content as the other items
  - Colors, images, icons and author links are not shown. They cannot be opened from the MCP and do not help understanding the content
  - Attachments can be written freely by the poster, so their types are not trusted. Attachments and elements that are not objects are skipped, and only strings, numbers and booleans are shown as values. All item lines are indented by 2 characters, and after a line break in a value (including control characters that some displays treat as line breaks) by 4 characters, so that a line inside an attachment does not take the same form as a post separator or a file line
  - The attachments, including headings and indentation, get a length limit of the same size as the text's, separate from the text. If they were summed with the text, the attachments would vanish entirely in a post with a long text. When cut, a note line is shown from the start of the line at the cut position
- A tool that shows posts indents each line of the text by 2 characters (line breaks are judged the same way as for attachments; the indentation is applied after cutting by the length limit, and an empty text shows one empty line). The guess can be wrong, so when it is Shift_JIS or EUC-JP, the output says that it is a guess and that, if the text is garbled, it may be another character encoding. Latin-1 (Windows-1252) is not made a candidate, because it accepts almost every byte sequence and would make even non-text files readable

Whether the whole was fetched is decided by whether the number of bytes fetched is less than 40,000 bytes (the end of the body was reached), or is exactly that and equal to the size in the information. The size in the information can differ from the actual content

The order is newest last reply first, and paging, as in `get_unreads`, shows the threads that had replies after the previous page in a section before the body. Threads of archived channels are not removed. A follow can be removed, so this can be used for cleanup. The channel list is fetched with `include_deleted=true`, and the channel and team lines are also shown for archived channels, with "archived" shown after the name on the channel line (to show that replying is impossible). This list always returns all channels the user was a member of at the time of archiving, but the approach of looking up, one by one with `GET /channels/{id}`, only the channels of the threads shown on the page is not adopted. If there are many followed threads in archived channels, it would add up to 50 calls per page, and advancing pages in succession would use up the MCP server's per-user limit (300 per minute) in a few pages. `POST /teams/{team_id}/channels/ids`, which can look up in bulk, returns only public channels that are not archived, so it cannot be used. With the current approach, one call is enough regardless of the number of archived channels. A root post that has no replies yet is not returned by Mattermost until its first reply, even if followed
- `follow_thread` and `unfollow_thread` accept the post_id of any post in the thread, and convert it to the root post before passing it to Mattermost. Mattermost returns success even for the ID of a reply, and a follow that takes effect neither on the list nor on notifications would remain. The team is the channel's team (for DMs and group DMs, the first team the user belongs to). The follow API does not depend on the team
  - `follow_thread` refuses a thread in a channel the user has not joined. Mattermost returns success, but the follow shows up neither in the list nor in notifications. If the thread is already followed, the follow API is not called. Mattermost marks the thread as read on every follow, so calling again would mark as read even replies the user has not read. Whether it is followed is looked at by fetching the thread's state, but for a root post without replies (`reply_count` is 0; this includes a thread whose replies were all deleted) that has never had a reply, Mattermost does not create the thread's state until the first reply, so even if it is followed the fetch gives 404. So only when the state fetch gives 404 and `reply_count` is 0, it is looked at with `is_following` of the thread fetch (`GET /posts/{id}/thread?collapsedThreads=true`). A thread with replies can be judged from the state fetch, so the calls do not increase. For a thread that was not followed, the replies up to the time of following are marked as read. The read position before that cannot be read through the API, so it is not restored. When newly followed, only for a root post without replies, the state is fetched again after the follow. If that gives 404, the thread's state does not exist yet, and the message adds that it does not show in the list until the first reply. A thread whose replies were all deleted still has its thread state even if `reply_count` is 0, so the re-fetch gives 200 and it also shows in the list, so nothing is added. Even if the re-fetch fails, the follow is already done, so the tool does not fail and only omits the addition. The only call added by the re-fetch is one, when newly following a root post without replies. In a configuration that uses a read replica, the re-fetch may read the stale state right after the PUT and give 404, and the addition may be made even for a thread whose replies were all deleted
  - `unfollow_thread` unfollows without a prior check. Unfollowing does not change the read state. Even after unfollowing, if the user is mentioned in that thread or replies to it, Mattermost follows it again. The output says so
  - In a thread in a DM or group DM, Mattermost treats every reply from the other party as a mention of the user, so even after unfollowing, one reply from the other party makes the user follow it again, and notifications also arrive. If unfollowed, the thread disappears from `list_followed_threads` until the next reply, so it does not refuse and unfollows, and the output says that the notifications do not stop
- `search_users` and `list_channel_members` do not add presence. It would add API calls per user, and calling `get_user` after choosing someone from the list is enough
- `search_files`, like `search_posts`, calls the all-teams search API once, interprets dates in JST, and cuts out the page from the 100 results with a cursor. `in:` (including `-in:` and `channel:`) is replaced with the channel_id and then passed, under the same rule as `search_posts` (the item above, "The `in:` of `search_posts` and `search_files`"). The approach of calling the per-team API in turn is not adopted, because the calls would increase by the number of teams and the creation of DMs could not be prevented either. Names match by the unit of words of the full-text search, and Japanese names are not split by whitespace, so they match only by the whole name or by prefix from the start (`*`). The tool description says so. When the file search is disabled by the server setting, the tool returns that fact and that the files can be looked for with `search_posts`. When resolving `in:` or building the search terms afterwards fails, it queries with only the search term `*` to find out whether the search is disabled, and then answers. Mattermost looks at the setting before converting channel names, and with only `*` it searches nothing. That it is found to be disabled only after the resolution is because the setting does not appear in the client settings (`/config/client`)
- The count of `list_saved_posts` is 20 by default and at most 50. Mattermost's saved posts API treats `page` as a number of items to skip, so a save or unsave between pages shifts the position. It also sorts by creation time only, so the order among posts with the same time can change from query to query. So the first query reads count + 21 items, and later ones 200 at a time, overlapping the last 20 of the previous query, reading from the start up to 1000. The overlapping 20 are shared between posts of the same time that straddle the boundary of queries and the shift of positions due to unsaving within one call. When posts of the same time that straddle a boundary exceed 21, or when, together with the shift caused by unsaving, the overlap is used up, a post can rarely be missed. When the first small query is empty, it reads again with 200 in case all of them were posts that cannot be read. The posts read are sorted newest first (by post_id if equal), and the `create_at` and post_id of the last post shown, and a rough position of the row that received that post, are put in the cursor. It stops reading when the page is satisfied. When it stops at 1000, it reads only 20 beyond that, and if any remain, says so (if all of those 20 are posts that cannot be read, it does not). The first query is kept small so that, on the frequently used first page, Mattermost is not made to build the metadata of 200 items. The continuation of a cursor reads count + 41 items from 20 before the rough position (cut at the 1000th; if 20 before is at the start or at the 980th or later, the rough position is not used). The rough position shifts because of a save or unsave between pages, and because Mattermost drops posts after counting or reorders within the same time, so it is used only when the items read include a post strictly newer than the cursor's post (all rows before that are newer than the cursor), and otherwise the tool re-reads from the start
- `list_channel_members` makes the member list readable, because the member count alone cannot answer who is in a channel and whom to ask. It is made an independent tool, not an option of `get_channel`. `get_channel` pages the pinned posts with a cursor, and one cursor cannot page two lists. It is also so as not to enlarge the output of `get_channel` for a channel with hundreds of members. The count is 50 by default and at most 200, and the page in Mattermost's username order is passed on as is. If members increase or decrease between pages, misses or duplicates can occur, but the username order does not change as often as posts do, so it is accepted. For a channel the user has not joined, Mattermost does not return members even for a public channel, so the tool says so. Mattermost judges by the permission to read (normally being a member of the channel), and returns the same 403 for a temporary failure and, very rarely, for a deletion right after fetching the channel, so the message does not assert the cause, and adds that, if the user should be a member, the client should wait and retry, and, if it continues, ask the administrator to check whether the user was removed from the channel or the permission to read was removed by the server's permission settings
- The cursor also contains the count and the type filter of `list_my_channels`, and when a cursor is passed, the argument side is ignored. This is so that the population does not change in the middle of the pages

### Marking as read

`mark_as_read` is made an independent write tool, not an option of a read tool. Mixing a side effect into reading would make it impossible to attach `readOnlyHint`. If it marked everything read as of the time of the call, it would also mark posts the AI has not read, so for each item it takes the newest of the posts that were read (`last_post_id`). In a channel it marks all posts before that as read, so the tool description asks the caller, when clearing unread messages, to read them to the end with `from: "unread"` of `read_channel` before passing the value. When it is omitted, everything up to the time of the call is marked read.

- Channel: if there are neither unread posts nor mentions (counted by root posts if CRT is enabled), it is reported as "Already read". When the user makes a root post, the server marks the channel as read, so in the flow "read → reply → mark as read", "Already read" is returned (the server does not mark it as read for posts by a webhook or a Bot, nor for a reply to a thread while CRT is enabled)
  - A channel the user has not joined is an input error. This is because Mattermost's `mark_read` returns success even when the user has not joined
  - If there is a post by someone other than the user after `last_post_id`, the channel is not marked read. Posts by a webhook or a Bot that the user created are not counted as the user's own posts, and join/leave notices, which Mattermost does not count as unread, are not counted
  - If the 200 posts after `last_post_id` are all the user's own (including join/leave notices), what lies beyond cannot be checked, so the channel is not marked read
  - The channel is marked read with `POST /channels/members/{user_id}/mark_read`, called right after checking each channel. If it were called once for all channels after checking all of them, the interval between checking and marking as read would stretch to the whole execution time of the tool (more than ten seconds for 20 items), and posts that arrived in that interval would be marked read
  - An item that specifies the same channel twice is an input error. If one is refused and the other marks it as read, the rows of the result contradict each other
  - It is not compared with the channel's `last_post_at`. That value advances with edits and pinning and does not go back with deletion, so it would keep refusing even when there is no new post
  - `/channels/members/{user_id}/view` is not used. It switches the channel the user has open and affects notifications
  - A position is not specified with `set_unread`. It moves the read state backward, and specifying a reply for a user whose CRT is disabled makes the user follow the thread
  - Posts that arrive between checking and marking as read are marked read. This is because Mattermost's `mark_read` has no way to specify a position. A post by someone else in the same millisecond as `last_post_id` is also missed, because the narrowing is by comparison of `create_at`
  - In a setup that departs from the assumption (the row "Number of Mattermost nodes") and uses a read replica (a license is required), this interval stretches by the replica's lag. This is because the check of later posts reads the replica, while Mattermost's `mark_read` reads the time of the last post from the master
- Thread: the position to write is 1 millisecond after the time of `last_post_id` (if omitted, the time of the thread's last reply). Mattermost counts unread replies after the position and mentions at or after the position, so if the time of the post itself were used, that post's mention would remain. In exchange, replies by others in the same millisecond as `last_post_id` and in the millisecond after it are marked read without being read. It does not write a position before the current one, because the thread API also moves the position backward. For a user whose CRT is disabled, the read state of a thread does not appear on the screen, so the thread is not marked read, and the reply tells the caller to mark the channel read
  - A reply exactly at the written position is not counted as an unread reply, but it is counted as a mention. If, in the response after writing, there is no unread reply but a mention remains, that mention belongs to the reply exactly at the position, so the tool writes 1 more millisecond ahead. There is no reply after the position, so this does not increase the replies that are marked read without being read. The same applies when the current position is at or after the position to write and a mention remains with no unread reply: it writes 1 millisecond ahead for the same reason
  - If the current position is at or after the position to write and no mention remains, it does not write
  - If the current position is at or after the position to write and there is an unread reply after the current position, it does not write even if a mention remains. Writing the same position would not change the count, and when the user reads the later reply, Mattermost recounts
  - If only the write that clears the mention of the reply exactly at the position (1 more millisecond ahead, or, when the current position is at or after the position to write, 1 millisecond ahead) fails, the item is written in the result as marked read, with a note that the mention could not be cleared and that running this thread again with `last_post_id` may clear it. This is because the current position is already at or after the position to write. Running the call again as is, without `last_post_id`, is not recommended (it would mark as read even replies that arrived in between). When this write fails because of re-login, 429 or a Mattermost outage (and an unexpected failure), the item is also written as marked read, with a note that it was interrupted before the mention was cleared, and then the interruption below begins
  - If the user reads ahead between getting the state and writing, the position goes back to the written position. This cannot be avoided because the thread API has no conditional write. In a setup that departs from the assumption (the row "Number of Mattermost nodes") and uses a read replica, the getting of the state and the recount of mentions also read the replica, so this interval stretches by the replica's lag, and a mention that arrived during the lag can be left out of the recount and cleared
  - When there is no state for the thread (it is not followed, it has no replies, or the user has not joined the channel), it is not marked read. If it is not followed, `follow_thread` is suggested. For a thread in a public channel the user has not joined, the post can be read, so it gets this far, but `follow_thread` refuses, so it is not suggested. Joining is checked only for a thread with no state and with replies, and the calls on the path that can mark it read are not increased. For a root post with no replies, no state is created even if it is followed until the first reply, so it is not suggested
- For an item that omitted `last_post_id`, the row of the result says that everything up to the time of the call was marked read ("Marked everything up to the time of this call as read."). This is so that a mark as read the user did not ask for (for example, when an instruction planted in the body of a post was followed) can be noticed afterwards
- An input error or a Mattermost error for one item is written as that item's result, and the other items continue. Only when there is neither an item marked read nor an item already read is it a tool error. Re-login, 429 and a Mattermost outage (and an unexpected failure) also concern the other items, so processing of the remaining items stops there (interruption). When interrupted, it is a tool error even if some items were marked read, and it lists the result rows so far, the row of the interrupted item ("it was not marked read" for a failure or 429 that is known to have stopped before the write or before sending, "it is unknown whether it was marked read" if the write was already sent), the failure message, and the items not yet processed, so that only the interrupted item and the unprocessed items are passed again; unless the user asked for everything to be marked read, it adds that an item that omitted `last_post_id` should be read and given one before being passed again. This is because redoing the whole call would mark as read, for an item that omitted `last_post_id`, even posts that arrived in between. When there is no result before the interruption and the interrupted item cannot have been marked read either (the case that becomes "it was not marked read" by the distinction above), only the failure message is returned. A call with `last_post_id` is idempotent, so it may be rerun as is after a failure. When, after losing the race of the refresh after a 401, the resend becomes a `4xx`, the tool answers that even an item whose write may have been completed was neither marked read nor had its mentions cleared (a known limit of "Scheduled posts")
- The annotations are `destructiveHint: false` (it can be undone with "Mark as unread" on the screen) and `idempotentHint: false`. A call that omits `last_post_id` advances the read state even for posts that arrived between reruns
- Unknown keys in the elements of `channels` and `threads` are refused at the argument validation stage, and no item is marked read (it does not become a per-item result). If they were dropped, as is the default of zod's `z.object`, a misspelled `last_post_id` would be treated as absent and everything up to the latest would be marked read. The only way to undo that is for the user to operate "Mark as unread" on the screen for each item

### Preventing duplicate posts in `send_message`

If the response to the MCP client is cut off after Mattermost has accepted a post, the client or the LLM does not know whether it succeeded and repeats the same call, and the same post is made twice.
Because it is the LLM that repeats the call, even if the LLM is made to generate a key for preventing duplicates, there is no guarantee that it uses the same key when it repeats.
So on the MCP server side, if the same user tries to post the same body to the same destination (channel and `root_id`) within a short time (about 10 minutes), it is regarded as a repeat of the same post.

Mattermost v11.7.8 has a deduplication that groups requests with the same `pending_post_id` of a post for 30 seconds ([`deduplicateCreatePost` in `post.go`](https://github.com/mattermost/mattermost/blob/v11.7.8/server/channels/app/post.go). It is not written in the public API documentation).
This alone cannot prevent a repeat after more than 30 seconds, so it is combined with a record on the MCP server side.

- A record with a unique constraint on the combination of user, destination and hash of the body is kept in SQLite. The record holds the `pending_post_id` generated at that time and a state (posting, succeeded)
- The record is created before posting. If a record for the same combination already exists, a new record is not created. The post to Mattermost is always made with the record's `pending_post_id`
- On success, the post ID is recorded. If Mattermost clearly rejects it (`4xx`), the record is deleted
- If there is a "succeeded" record for the same combination, the tool does not post, returns the previous post ID and permalink, and states in the output that it did not post because it was a repeat
- If there is a "posting" record for the same combination and the Mattermost API timeout (several tens of seconds) has not passed since it was created, the earlier request is regarded as still being processed, the tool does not post, and returns an error saying that the same post is being processed, so wait a little and check the result
- A "posting" record past the timeout is regarded as having ended with the result of the earlier request unknown. A repeating request first takes the right to retry by atomically rewriting the record's update time (only one of the requests that arrive at the same time can take it, and a request that could not is treated as being processed, as in the previous item). The request that took the right searches Mattermost for a post by that user whose body matches exactly, made in that channel (and `root_id`) at or after the record's creation time, and if one is found, records it as a success and returns it. If none is found, it posts with the same `pending_post_id`
  - `pending_post_id` is not stored in the DB, so it cannot be used as a search condition. The search uses not the full-text search API but the API that fetches the posts of a channel narrowed by time (`GET /api/v4/channels/{id}/posts?since=`). This is so that word segmentation of the full-text search or a delay of the index does not make it miss a matching post
  - The grace before "posting" is regarded as having an unknown result is the MCP side's API timeout plus a margin. Even so, a duplicate post when Mattermost's processing completes later than the grace cannot be prevented, and it is a known limit
  - In matching for a repeat, the posts recorded by the same user's other records for preventing duplicate posts and by scheduled posts are excluded (the exclusion of other records' posts). This is so that a post made with the same body by another send or scheduled post inside the matching window is not mistaken for a post before this send. If all the posts found are excluded, the tool does not post, returns an error saying that it is unknown whether this send was posted, and keeps the record. The post_id of another record can include one that was estimated by matching and recorded, so an excluded post may be the post of the previous attempt of this send, and posting again would make a duplicate post. The user who has confirmed that it was not posted is told to send again with `allow_duplicate: true`. The same resend gets this error or "being processed" during the record's window (10 minutes). A post made with `allow_duplicate`, a post whose record was deleted after the window, and a post made from the screen are not in the records, so they cannot be excluded and can be mistaken. A post made while another send is waiting for the response of a post (before its post_id is recorded) also cannot be excluded. A send with an inline attachment mistakes one only when its size also matches, or when the sizes cannot be compared (the known limit below)
  - The posts found are sorted by creation time, oldest first (by post_id if equal), and the first one after the exclusion of other records' posts is regarded as the previous post. The previous attempt posts right after creating the record and finishing the upload, so it is often older than a post sent later with the same body. The matching of the sweep of scheduled posts follows the same order
- For cases where the user intends to repeatedly post the same body, `send_message` has an argument (`allow_duplicate`) that turns off the prevention of duplicates
- When there are attached files, the decision uses the hash of the body plus the name and the SHA-256 of the contents of each file, in order (the JSON `[body, [[name, SHA-256], ...]]`). If they were joined with a delimiter, another input with the boundaries between body, names and contents shifted would give the same hash. When searching for an existing post in a repeat, in addition to the body, the number of files attached to the post (the number of `file_ids` of the post in the list) must also match the number of attachments
  - `files` (inline attachments) are uploaded again on every repeat, so they cannot be matched by `file_id`. So it is also a condition that the multiset of the sizes in `metadata.files` of the list (excluding the part of the `file_ids` of the user's own `prepare_upload`) matches the byte counts of the contents of `files`. Names are not compared. Mattermost tidies up file names when it stores them, and a plugin may also rename them. When `metadata.files` is absent or its count differs from the post's `file_ids` (hidden by ABAC, or failed to fetch), the comparison uses the count alone
  - A post that differs only in size is regarded neither as the previous post nor as another post. It may be another send with different contents, or it may be the user's own previous post on a server that has a plugin that rewrites uploads (`FileWillBeUploaded`), and either way of regarding it can be wrong (posting again makes a duplicate post in the latter case, and regarding it as the previous post leaves the body unposted in the former case). If only such posts remain (after the exclusion of other records' posts), the tool does not post, returns an error saying that it is unknown whether this send was posted, and keeps the record. On a server that has the plugin, a repeat of a send with `files` gets this error if the previous attempt had posted
- The upload of attachments can exceed the grace (30 seconds). If a repeat that arrives meanwhile takes the right to retry, both of the two requests may post. So right before posting, the tool rewrites the update time and takes the right again, on the condition that the record's update time is still as it was when it took it. If it cannot take it again, it does not post and returns it as being processed
- When there are `file_ids`, the decision uses the hash of the JSON `[body, [[name, SHA-256], ...], [file_id, ...]]`. The hash when there are no `file_ids` is not changed. This is because a record taken before an update would no longer match a repeat after the update. The count used when searching for an existing post is the sum of `files` and `file_ids`, and it is also a condition that all the passed `file_ids` are attached. If a post with the same body and count but with other files attached were mistaken, a file that was not posted would be recorded as used for the post
  - In a channel where the ABAC permission policy of Enterprise Advanced does not allow the user to download files, Mattermost empties `file_ids` in the list of posts and puts the number of attached files in `metadata.redacted_file_count`. Then `file_id` cannot be matched, so a post is regarded as the same only by the match of the count (the repeat in the sweep of scheduled posts is the same). A mistake happens when another post with the same body and the same count was sent separately in the same time period and it does not remain in the other records (the "exclusion of other records' posts" above). It is rare, so it is accepted
- Automated tests cause a failure that cuts the response after Mattermost has accepted a post, simultaneous requests for the same post, and a repeat after more than 30 seconds, and confirm that no duplicate post is made. The deduplication by `pending_post_id` is behavior that is not in the public documentation, so this test is also run when Mattermost is updated

### Deleting the draft after `send_message`

Mattermost's server does not delete the corresponding draft when it creates a post (only the webapp's send handling and the deletion of a post delete a draft).
So if a draft saved with `save_draft` is sent with `send_message`, the draft remains, and if the user sends it as it is, the same post is made twice.
So after posting, `send_message` deletes a draft in the same destination (channel and `root_id`) whose body matches exactly. A draft with a different body may be the user's work in progress, so it is not deleted.

- As with `save_draft`, the draft is looked for in the list of the destination's team (the first team the user belongs to, for a DM or group DM). If the user belongs to no team, nothing is done. Drafts are listed per team, so such a draft does not appear on the screen either
- It is deleted not only when the tool actually posted but also when it did not post because it regarded the call as a repeat. This is so that, even if the deletion in the previous attempt failed, it can be deleted by the repeat. When the state is "being processed", whether the post succeeded is unknown, so it is not deleted
- A draft with attachments is not deleted, and the output says so. Deleting it would lose the files the user attached on the screen
- If the user has turned off draft sync, the draft is not deleted, and the output says so. Deleting would deliver the WebSocket `draft_deleted`, and the webapp empties that channel's draft in the store without looking at the sync setting, so it would delete a work in progress with a different body that exists only in the browser. The sync check is made only when there was a matching draft. The mobile app does not handle the draft WebSocket events (they are not in `app/constants/websocket.ts` of mattermost-mobile)
- A draft with a priority is deleted, and the output adds that the priority was not attached to this post
- A draft with burn-on-read (its `type` is `burn_on_read`; the webapp attaches it only when the feature is enabled on Enterprise Advanced or higher) is also deleted, and the output adds that it was not attached to this post, so the post does not disappear and remains. If it remained, the user would send it from the screen and the same post would be made twice
- The "list → save" of `save_draft` and the "list → delete" of the deletion are serialized, one at a time per destination (the combination of user, channel and `root_id`) inside the MCP server. This is so that the deletion does not delete a draft that `save_draft` saved after the deletion read the list. A race happens only between the list of one draft and the write, so processing for another destination is not made to wait. The lock is a per-destination queue inside the process, and the next one proceeds even if the previous one failed. `save_draft` resolves the destination outside the lock (one call can take several tens of seconds, and this avoids the deletion behind it expiring every time). The deletion includes the time of waiting for the lock in its 5-second deadline, and when the deadline comes it stops waiting and reports a failure. The queue slot remains until the previous processing finishes, and when its turn comes it releases without doing anything (if it were released immediately, the processing behind it would run overlapping with the previous processing)
- A failure of checking or deleting the draft (a Mattermost error, a rate limit, a communication failure, an expired deadline) does not spoil the success of the post. The result of the post stays a success, the output says that the draft may remain, and it is logged. If draft sync is disabled on the server (`501`), a draft cannot exist, so nothing is written. If re-login to Mattermost becomes necessary along the way, the output says so and tells the user to reconnect. When the client cancelled the request, it is written neither in the output nor in the log (a cancellation is not a failure of the deletion, and there is nobody to receive the response). The log includes the destination's `channel_id`
- The whole deletion is cut off at 5 seconds, and the remaining calls are also stopped. The deadline of one call is several tens of seconds and up to 4 calls are made in order, so waiting would delay the response of the post's success and it would look like a failure through the client's timeout. If it only stopped waiting, the deletion could arrive after the response was returned and delete a draft that the user rewrote in the meantime. However, a DELETE that has been sent is processed to the end by Mattermost and cannot be cancelled
- The draft is not deleted for the post of a scheduled post (`schedule_message`). `send_message` makes the deletion safe by the body remaining in the input field, by the priority and burn-on-read not being attached, and by telling the failure of the deletion in the output, but a scheduled post is posted by the sweep when its time comes, so there is nobody to tell. Also, the time of the post has nothing to do with the user's operation, so if the user happens to be writing in exactly that channel, it easily hits the race window below. The draft with the same body remains, and if the user sends it, the same post is made twice
- The annotation `destructiveHint` is left `false`. What is deleted is only the draft that is the same as the body that was sent, and a work in progress with a different body or an attachment can be lost only inside the race window below. The priority and burn-on-read are lost, but the output tells so
- Known limits
  - If the user rewrites and saves the draft on the screen between the reading of the list of drafts and the deletion, that work in progress can be deleted. Mattermost has no conditional deletion. The webapp saves when leaving a channel, so this window is narrow
  - If a DELETE or `POST /drafts` that has been sent is cut off by the deadline or a cancellation, the lock is released, but the processing continues in Mattermost. The order of processing with the later saving of `save_draft` and the later list and DELETE of the deletion is then not determined, and a new draft can be deleted
  - When a deletion call is refused by this MCP's Limiter (the upper limit of concurrent execution, or the per-minute upper limit that frees up within 1 second), it waits 100ms and tries again. The lock of drafts is per destination, so cleanups of the same user run in parallel and can temporarily fill the user's concurrent-execution slots. It does not wait for Mattermost's `429` or for an upper limit that takes longer than 1 second to free up (waiting would use most of the 4 seconds, which is 5 seconds minus the 1 second kept before the deletion, and leave no time for the list and the deletion). It waits only until the deadline and the client's cancellation. For a DELETE, the judgment of the remaining time below is checked again before sending, each time it retries
  - Right before sending a DELETE, if the remaining time of the 5-second deadline is less than 1 second, the deletion does not send it and reports that it could not be confirmed. This is to narrow the window in which the deadline comes in the middle of a DELETE. However, 1 second is only a guide, and with a slow Mattermost the deadline can come in the middle. A resend after the DELETE got a 401 and the token was refreshed does not pass through this check
  - If the user has that channel (thread) open on the screen, the body remains in the open input field even after the draft is deleted. This is because the webapp's editor does not reread the store until the channel or thread is switched. The output at the time of deletion adds that, if it is open, the user should clear the body of the input field without sending it

### Posts with attached files

- Each element of `files` of `send_message` has a name and exactly one of `content_text` (attached as it is as UTF-8 text) or `content_base64` (a small binary). Formats the LLM can write as body text, such as SVG, CSV, Markdown and code, are passed as `content_text`
- The count is 1 to 5, and the name is 1 to 100 characters and does not contain `/`, `\` or control characters. The total of the contents (after decoding for base64) is up to 128KiB. The MCP server and the reverse proxy limit a request to the MCP path to 1MB, and the value was chosen so that, even if the text expands up to 6 times through JSON escaping, it fits together with the longest body. To raise the limit, change both settings
- `content_base64` accepts only standard base64 whose length is a multiple of 4 and that returns to the original when decoded and encoded again. If it were decoded with a data URL prefix or line breaks left on, it would silently attach broken contents
- Each file is uploaded one at a time with `POST /files?channel_id=&filename=`, with the contents as the body as they are, and the returned `file_ids` are attached to the post. If it fails after uploading and before posting, that file cannot be deleted and remains (Mattermost has neither an API that deletes a file nor a job that deletes files that were not used). So all the checks, including the resolution of the destination and the record for preventing duplicate posts, are finished before the upload
- When the upload of attachments (or a check before posting) fails, the record for preventing duplicate posts is deleted regardless of the kind of failure. This is because `POST /posts` has not been sent yet, so nothing was posted by this attempt. Even for a failure where it is unknown whether the file arrived, such as a rate limit after a request whose response was lost and that may have been processed first, what remains is only a file that is not used for a post, and keeping the record would prevent nothing. It is also deleted when the upload after matching in a repeat fails (the known limit below). When it is refused because of the number of pixels or the size, the message is made user-facing with the file name added
- Mattermost silently drops `file_ids` that cannot be used, without making it an error. If the count of `file_ids` in the post's response differs from the number uploaded, the post has been made, so the output states that some were dropped. When files were hidden by ABAC (the response's `file_ids` is empty and there is a `metadata.redacted_file_count`), the judgment uses that count, and the output adds that which were dropped is unknown. For the `file_ids` of `prepare_upload`, if the dropped ones were left unused, they would pass the check on the next post and be silently dropped, so all of them are recorded as used for the post
- The check of the kind and size of images is left to Mattermost
- Known limits
  - The arguments of a tool are the model's output tokens, so the binary that can actually be sent is up to several tens of KB, and a large image cannot be attached
  - When it fails before posting, or when another request posted first in a repeat, the uploaded file remains in Mattermost without being used for a post. A person who can read that channel can fetch it if they know the `file_id`
  - If Mattermost silently dropped files in the previous post, the number of `file_ids` does not match when searching for an existing post in a repeat, and a duplicate post can result
  - In a channel where files were hidden by ABAC, matching can be done only by count, so a post that is not in the records and has the same body and the same count (a post made with `allow_duplicate`, a post whose record was deleted after the window, a post made from the screen, or a post of another send before its post_id was recorded) can be mistaken for the user's own previous post. Then `send_message` does not post and records that it used its own `file_ids` for a post (those files are attached to no post and cannot be used in the next post)
  - Even with matching by the size of inline attachments, the following posts, which are not in the records (the same as the ABAC item above), can be mistaken for the user's own previous post. A post with inline attachments of different sizes when `metadata.files` is absent (hidden by ABAC, or failed to fetch). For a send with only inline attachments, a post of another send that attached a file of the same size by a `file_id` from `prepare_upload`. A post of a send whose size is also the same and only whose contents differ. If mistaken, it returns a success saying that a post with the same body already existed, without posting the body
  - On a server with the ABAC permission policy enabled, when Mattermost (`sanitizeFileAttachmentsForUser` in v11.7.15) cannot temporarily get the user's information, it empties `file_ids` in any channel without adding `metadata.redacted_file_count`. If the response of a post has this form, `send_message` tells that all the files were dropped and does not record the `file_ids` of `prepare_upload` as used for the post. Those `file_ids` pass the check of the next post and are dropped by Mattermost. If the list for matching in a repeat has this form, the files do not match and it may send again (the duplicate-post side)
  - When it failed in the upload after matching in a repeat and the record was deleted, if the previous attempt's post appears late after the matching, the next send does not match and posts anew, so a duplicate can occur. At the time of matching the previous post did not exist, and it is rare, so it is accepted

### Attaching files on the user's PC

A file of several MB, such as a screenshot, a PDF or a photo, cannot be written out and passed by the AI as an argument of a tool.
So an MCP client that can run commands on the user's PC (Claude Code, Codex CLI and so on) is made to upload the file directly to the MCP server. The contents of the file do not pass through the AI's output.

1. The AI passes the destination channel to `prepare_upload`. The MCP server returns a single-use upload URL (`<PUBLIC_URL>/mcp/upload/<token>`) tied to that user and channel, and a command in the form `curl -sS -F 'file=@<file path>' <URL>`
2. The AI runs that command on the user's PC. The MCP server streams the file it received to `POST /files?channel_id=&filename=` with the user's own Mattermost token, and returns the `file_id`
3. The AI passes the body and `file_ids` to `send_message` to post. To schedule, it passes them to `schedule_message` ("Attached files" in "Scheduled posts")

A client that cannot run commands on the PC, such as claude.ai, cannot touch files on the user's PC and so cannot be used. The description of `prepare_upload` makes it tell the user, in that case, to save the body as a draft with `save_draft` and attach the file from Mattermost's screen. The code execution of claude.ai has a setting that reaches an external network (on personal plans only approved package-management services, and on Team and Enterprise the owner can allow any domain), and it may be able to send a file attached to the chat from the sandbox to the upload URL with `curl`, but this path is not recommended. Whether it can reach out is decided by the user's or the organization's settings and cannot be confirmed from the tool description, and when it could not send, it is hard for the user to find out the cause.
The description of the argument `files` of `send_message` writes how to choose between the two by whether the contents can be read and whether they fit in 128KiB, and leaves to the description of `prepare_upload` where files that cannot be read, files that do not fit, and other files on the PC should go. For a file on the PC, passing it as `content_base64` would enlarge the tool's arguments and press on the conversation's context, and it cannot be sent when the total of the contents exceeds 128KiB, so it directs to `prepare_upload`. However, it writes that, on a client that cannot run commands on the PC (such as a combination of Claude Desktop and an MCP that reads files), a text file on the PC may also be sent with `content_text` if it can be read and fits. This is because on that client `prepare_upload` cannot be used, and a small text file would fit both guidances and cause hesitation. Together with that, it writes that, when `�` or garbled characters can be seen in the contents, and when the original character encoding or a BOM seems necessary, as with a CSV made in Excel, the file goes to the guidance of `prepare_upload`. This is because `content_text` is attached as a UTF-8 byte sequence, so a Shift_JIS CSV or a file with a BOM differs from the original byte sequence at the point where the tool that reads the file turned it into a string (garbled, converted to UTF-8, or the BOM dropped). It does not write "limited to UTF-8 files". If the tool guesses the character encoding and converts, the model cannot see whether the original was UTF-8, and it would be an instruction that cannot be judged. It is not extended to binaries such as images, because the model sees an image as an image but cannot read it as a byte sequence, and might pass a guessed byte sequence to `content_base64`. For a file attached to the chat, it writes that it can be sent with `content_base64` only when its contents can be read by code execution. This is so as not to block the path of sending a small file attached to the chat in claude.ai with code execution enabled, and to prevent the model of a client without code execution from trying to pass an image's contents to `content_base64` without being able to read them as a byte sequence. The error when the limit is exceeded also tells the caller to follow the guidance of the description of `prepare_upload`. The description of `prepare_upload` is divided by whether commands can be run on the PC, and for a file whose path is unknown (such as an image pasted into Claude Code) it adds that the AI should ask the user for the path and, if there is none, follow the guidance of `save_draft`.

Descriptions of tools are put in the client's context in every conversation, so the guidance on choosing an attachment is placed in one place each. The conditions under which a file can be sent with `files`, and the guidance that directs everything else to `prepare_upload`, are in the description of the argument `files`; the guidance for claude.ai and similar clients, the handling of files whose path is unknown, and the confirmation before `curl` are in the description of `prepare_upload`; and the descriptions of `send_message` and `schedule_message` name only the route of attachment (the reason `schedule_message` does not accept `files` is in "Attached files" in "Scheduled posts").

- The upload URL is valid for 10 minutes and for one request only. The URL remains in the record of the conversation, and anyone who knows it can upload once as that user. The token is a 32-byte random number, and only its hash is kept in the DB. Unused URLs are limited to 5 per user
- `/mcp/upload/` checks neither a bearer token nor `Origin`. `curl` on the PC has no MCP token, so the URL itself serves as the credential
- One request can send up to 5 files in the field named `file`, and up to `UPLOAD_MAX_BYTES` (default 10MiB) for the whole body including the multipart framing. File names are checked by the same rules as `files` of `send_message`. Mattermost's `FileSettings.MaxFileSize` applies separately, and Mattermost refuses a file that exceeds it
- The MCP server puts the body and the files of the request in memory before sending them to Mattermost. Copies of the body and the files overlap, and one upload uses about 8 times the body in memory, so only one upload is processed at a time across everything. A request beyond that is returned with 429 without using up the URL
- A response returned before the body has been fully read (a 404 for an invalid URL, a 429 for being processed, a 413 for exceeding the limit) is returned after reading and discarding the body up to the limit plus 1MiB. This is because, if the connection is closed before the reverse proxy has finished sending the body, the reverse proxy returns 502 as a failure of the send, and the MCP server's explanation does not reach the user. The amount read is counted including what was read before the 413. A body larger than that is not read and the connection is closed, and the reverse proxy's body limit (the limit plus 1MiB) is made to refuse it
- If no data comes for 15 seconds while waiting for the body, the tool cuts off, returns 408, and returns the URL to unused. The same applies while discarding, and then it stops discarding and returns the response. Only one upload is processed at a time, so this is so that a client that stopped sending does not stop the uploads of all users until Node's request deadline (300 seconds)
- In a failure in which not even one file has reached Mattermost, such as the body exceeding the limit, a wrong format, the connection being cut in the middle of the body, the sending of the body stopping, or Mattermost clearly refusing, the URL is returned to unused so that it can be sent again to the same URL. After even one file has arrived, in a failure where it is unknown whether it arrived (a timeout, or a rate limit after a request that may have been processed first), and in an unexpected failure, it is not returned. This is because sending again could upload the same file twice. The `file_id` of the files that arrived is also listed in the error response. `Retry-After` is attached to the rate-limit response only when the URL was returned. If it were attached when the URL was not returned, it would show a time as if waiting would allow sending to the same URL. The status stays 429, so a client that sends again by status alone, like curl's `--retry`, would send again to the same URL even without `Retry-After` and get a 404. The command that `prepare_upload` shows does not add `--retry`, and a double upload does not happen even with the 404, so the status is not changed. When re-login becomes necessary, all of that user's URLs disappear, so they are issued again
- The MCP server records the `file_id`, the user and the channel of the files that were uploaded. `send_message` accepts `file_ids` only if they are in this record, were uploaded by the user, are within 24 hours, are in the same channel as the destination, and have not yet been used for a post. Mattermost silently drops `file_ids` that cannot be used, so the tool refuses with a reason before they would be dropped. It also refuses files that a scheduled post holds ("Attached files" in "Scheduled posts"). When the post is made, the post ID is recorded for those `file_ids`
- If two `send_message` calls with different bodies use the same `file_id` at the same time, both pass the check. Mattermost attaches the file only to the earlier post, so the later post has it stated in the output as a dropped file. Only the files that remain in the `file_ids` of the post's response are recorded as used for the post. A dropped file may be attached to another post. Conversely, if a file that remained were not recorded, it would pass the check on the next post and be silently dropped by Mattermost. A recorded post ID is not overwritten
- For the files to be sent, the output of `prepare_upload` and the tool description ask the AI to show the user the file path and the destination and get confirmation before running `curl`. Which file is sent is decided by the client running on the user's PC, and the MCP server cannot confirm it
- The log shows the user, the result, the count, the total size and the time, and does not show file names, contents or tokens. The log of Mattermost's API shows only the path, with the query string that contains the file name dropped
- Known limits
  - A file that was uploaded but not used for a post remains in Mattermost (there is no API that deletes files). The MCP server's record is deleted after 24 hours
  - The URL also remains in the reverse proxy's access log. Being usable only once and for only 10 minutes limits the impact if it leaks
  - The 15-second deadline is counted by the length of time during which no data comes, so if a client keeps sending a little at a time at intervals shorter than 15 seconds, it can keep holding the processing slot until Node's request deadline (300 seconds). Only someone who holds a valid URL can do this, and it does not happen in a setup where the reverse proxy finishes receiving the body before sending it to the MCP server (nginx's `proxy_request_buffering on`)

### Editing and deleting posts

By Mattermost's permissions, a team administrator can delete other people's posts, and a system administrator can also edit them. From MCP, only the user's own posts are handled.

- The post is read first, and the tool refuses one whose `user_id` is not the user's own, one with `props.from_webhook` or `props.from_bot` attached, and one whose `type` is not empty (such as a system message). The `user_id` of a post by an incoming webhook is the webhook's creator, so it cannot be judged by `user_id` alone
- `props.from_oauth_app` is not looked at. It is also attached to posts that this MCP made with `send_message`, so refusing on it would make it impossible to fix a wrong post by the AI
- Editing sends only the body to `PUT /posts/{id}/patch`. `PUT /posts/{id}` is not used, because it removes an `is_pinned` that was omitted
- The parent post of a thread with replies is not deleted. When Mattermost deletes a parent, it also deletes other people's replies together. Whether it is a parent is judged by whether `root_id` is empty, and if `reply_count` is not returned as a number, the tool refuses as though there are replies. The post of a reply also carries the `reply_count` of the whole thread, so it cannot be judged by `reply_count` alone
- Known limits
  - A reply that was added between checking for replies and deleting is deleted together with the parent. This cannot be prevented because Mattermost has no conditional deletion
  - Even if a parent post with no replies is deleted, other users' drafts for that thread are deleted. This is Mattermost's deletion behavior, and there is no means to prevent it

### Saving drafts

A draft is one per combination of user, channel and `root_id`, and saving is an overwrite (upsert). So as not to delete the user's work in progress, the existing draft is checked before saving.

- If the body of the existing draft differs, the tool does not save unless `overwrite: true` is given, and refuses with the existing body added (if it is 200 characters or fewer, it shows the whole text under the heading "Existing draft (whole)"; if it is longer, it shows the first 200 characters under the heading "Existing draft (first 200 characters)". Characters are counted in graphemes and, as in the list of scheduled posts, it does not cut in the middle of an emoji). When it exceeds 200 characters, it adds that only the beginning was shown, and that copying it would lose the rest, so the user should be told to append in Mattermost's screen. If the body is the same, it does not save again. An overwrite also replaces the attached files, the priority and burn-on-read (the draft's `type`) and cannot be undone, so the annotation is `destructiveHint: true`
- `root_id` is checked to be a post in the same channel that is not a reply. Mattermost saves even for the ID of a nonexistent post or of a reply, and a draft that appears in no thread on the screen would remain
- If the user has turned off draft sync in "Settings > Advanced" (the preference `advanced_settings/sync_drafts` is `false`), the tool refuses without saving. A webapp with sync turned off does not load drafts saved while it was closed, and the user's work in progress exists only in the browser, so it cannot be seen by the check of the existing draft. When the preference is absent, sync is treated as enabled
- Known limits
  - A draft that the user wrote on the screen between checking the existing draft and saving can be overwritten
  - If the user has that channel open in the webapp when it is saved, it is not reflected in the open input field. If the user then writes as it is and switches channels, the webapp overwrites the server's draft, and the saved draft is lost without a warning. This is the webapp's behavior and cannot be prevented, so the output adds that the user should reopen before editing
  - It has not been confirmed how the draft of a reply appears in the right-hand panel. So the output for the draft of a reply does not say that it is in the input field
  - Even if the same body is sent with `send_message`, a draft with attachments, a draft of a user who turned off draft sync, and a draft whose check or deletion failed remain, and if sent as it is, the same post is made twice. The output of `send_message` tells this ("Deleting the draft after `send_message`"). When the same body is sent as a scheduled post, the draft also remains

### Scheduled posts

Mattermost's scheduled post API cannot be used on Team Edition (400 `api.scheduled_posts.license_error`), and a future `create_at` in `POST /posts` is silently replaced with the current time.
So the MCP server stores the schedule in SQLite and, when the time comes, posts with the user's own Mattermost token.

**Relation to "What to avoid"**: A scheduled post is posted at a time when the user is not operating the MCP. To avoid "posting to an unintended channel", it works as follows.

- The user specifies the destination at the time of scheduling, and it is fixed as `channel_id`. The name is not resolved again when the time comes. If the DM with `@username` or the group DM with `@a,b` does not exist, it is created at the time of scheduling. `root_id` is also checked at the time of scheduling to be a parent post in the same channel
- The user can check the body and the destination in the output at the time of scheduling and in `list_scheduled_messages`, and can cancel
- The permission to post is judged again by Mattermost with the user's permissions when the time comes
- A schedule that was changed, a schedule that was cancelled, and a schedule whose time has passed are not posted ("Execution" below)

**Storage**

- A schedule is tied to a Mattermost user. Listing, changing and cancelling are limited to the user's own schedules, and another user's schedule ID gets "not found". The schedule ID is a random value that cannot be guessed
- The body is encrypted with the same key as the Mattermost tokens and stored, and is not written to the log
  - If the key is changed, the body can no longer be decrypted. A pending schedule is not posted and is made a failure with the reason "Not posted because the body cannot be decrypted. Schedule the message again." If posting has already been attempted, the reason is "It is unknown whether this was posted"
- Schedules that are posted or failed are deleted 7 days after the update
- Changing and cancelling are done only on schedules that are pending and for which posting has never been attempted, with a conditional single-statement update. If the body of a schedule for which posting has been attempted were changed, a retry could not find the post of the old body and would make a second post
- A schedule is not deleted by the revocation of a grant or of a token. It is made a failure at the point when the time comes and posting fails

**Attached files**

A schedule can have 1 to 5 files uploaded with `prepare_upload` attached with `file_ids`.

- When attaching files to a post, Mattermost does not look at the time elapsed since the upload (`AttachToPost` of `FileInfo` in v11.7.8). There is also no periodic job that deletes files not used for a post. It was confirmed with the real thing that a file whose `CreateAt` was set to 31 days earlier can be attached to a post. So the file remains until the scheduled time. The exception is the case where files are deleted by the data retention policy of Enterprise (the retention period is `FileRetentionHours`). The scheduled time is at most 31 days (744 hours) after the upload when it is created, but it can be extended with `update_scheduled_message`, so there is no upper limit on the age of a file. A file past the retention period is deleted by the scheduled time, and Mattermost posts without the file (it appears in the list as a "note")
- At the time of scheduling, the same check as `send_message` is made (the user uploaded it with `prepare_upload` within 24 hours, to the same channel as the destination of the schedule, and it has not yet been used for a post). When the time comes, the post is made not by consulting the MCP server's record of uploads (deleted after 24 hours) but with the `file_ids` stored in the schedule's row. `file_id` is not encrypted, unlike the body. This is because reading a file requires Mattermost's permission
- Schedules that are pending or posting, schedules that are posted (only the files that remained on the post; when hidden by ABAC, all the files of the schedule), and schedules that failed with a record of an attempt remaining (a failure in a retry round, and a failure of "it is unknown whether this was posted") are treated as holding files. `schedule_message` and `send_message` refuse files that another schedule holds, with the schedule ID attached. This is because Mattermost attaches the same file only to the side that posted it first, so the later side silently loses the file. Failures with a record of an attempt remaining are included because the post may have been made. A failure where Mattermost refused the first attempt, or where a re-login became necessary before a request that might have been processed was sent (a call that received only `401`; the handling of `401` in "Mattermost authentication"), is confirmed as not posted, so it does not hold files. `schedule_message` makes this check in the same transaction that creates the schedule's row. `send_message` makes it after the check for already posted, after searching for the previous post in a retry. If the previous post is found, it returns that without checking. If it checked first, a retry whose previous attempt had managed to post would be refused because of a schedule that came in afterward with the same file
- `file_ids` cannot be changed by a change. When `file_ids`, `files`, `channel` or `root_id` is passed to `update_scheduled_message`, the argument error for an argument that is not accepted (the "Tools" section) is returned with guidance to cancel and schedule again. The files of a cancelled schedule remain in Mattermost and can be used for another post within 24 hours
- `file_ids` is stored in a column of the schedule's row. For an existing DB, the column is added at startup inside `BEGIN IMMEDIATE` if it does not exist. This is so that, even if the server and an admin command open the DB at the same time, it does not try to add it twice
- An attachment whose contents are passed directly, like `files` of `send_message`, is not accepted for a schedule. To accept it, the contents would have to be stored in SQLite, or uploaded to Mattermost first at the time of scheduling. The former increases the confidential data stored and the size of the DB, and with the latter the files of a cancelled schedule remain in Mattermost and cannot be deleted. So a schedule with files is possible only for clients that can use `prepare_upload`, and not from clients that cannot run commands on the PC, such as claude.ai. When `files` is passed to `schedule_message`, the argument error for an argument that is not accepted (the "Tools" section) is returned with these points: that if the user wants to send right now 1 to 5 files whose contents can be read and whose total fits in 128KiB, `files` of `send_message` can be used, and that when scheduling and for other files, the guidance in the description of `prepare_upload` is to be followed. Some clients cannot use `prepare_upload`, so the choice between them is left to the description of `prepare_upload` ("Attaching files on the user's PC"). If `files` were recommended without conditions, the same mistake would be repeated with files that cannot be read and large files
- No limit on the size of files is added to the limit of schedules. The contents of the files are in Mattermost, and what the MCP server holds is only the `file_id`

**Execution**

- The sweep starts the next round 30 seconds after the previous round ends. Even if an exception occurs in the middle of a round, the next round is scheduled. The number of schedules that call Mattermost in one round is at most 20 in total, and the calls go through the Limiter just like requests. The refresh of a token is combined into one per user, just like requests
- The right to post is taken with `UPDATE ... SET status='sending' WHERE id=? AND status='pending' AND scheduled_at <= ? RETURNING *`, and the body is read from its return value. This is because the user can change or cancel the schedule between the sweep's selection and the taking of the right. Since there is a single process, this update is enough to prevent double execution
- To prevent a double post, the record of `send_message` (deleted after 10 minutes) is not used, and the decision is made on the schedule's row itself. This is because a retry can continue for 1 hour, and when schedules with the same body line up they cannot be told apart by the record
  - When posting is attempted for the first time, `pending_post_id` and the time of the attempt are stored in the row before posting
  - In a retry, from the posts in that channel at or after the time of the attempt, it looks for the user's post with the same `root_id` whose body matches. Posts that another schedule has recorded as posted, and posts held by the record for preventing duplicate posts of `send_message` (deleted after 10 minutes), are excluded. The posts to exclude are read after the matching. This is so as not to miss a post that was recorded during the matching. If one is found, the schedule is made posted; if none is found, it posts with the same `pending_post_id`. If all the posts whose body matches belong to other records, it does not post and makes it a failure of "it is unknown whether this was posted". This is because another record may hold this schedule's post through an error of its own matching, and resending would make a double post (the same as `send_message`). In the judgments of deletion, edit and file mismatch below, the posts held by other schedules or by records of `send_message` are not excluded either. A deleted or edited post cannot be checked by its body, and a post whose files do not match cannot be checked by its files (it may be this schedule's post from which Mattermost removed the files), so it may be this schedule's post whichever record holds it. So when another record's legitimate post is edited or deleted, or when there is a legitimate post with the same body and different files (for example, when a schedule without files and a schedule with files with the same body line up), this schedule also stops at "it is unknown whether this was posted" without posting (the side safer than a double post)
  - Even when there is no post whose body matches, if there is a deleted post of the user with the same `root_id` at or after the time of the attempt, it does not post and makes it a failure of "it is unknown whether this was posted". Mattermost returns the body of a deleted post emptied, so whether it was a schedule's post that the user deleted cannot be checked by the body, and resending would amount to posting it again. The search after 1 hour is handled the same way
  - Also when there is a post of the user with the same `root_id`, at or after the time of the attempt, that was edited and whose body does not match (whichever record holds it), it does not post and makes it a failure of "it is unknown whether this was posted", the same as for deletion. Mattermost returns the body after the edit, so whether it was a schedule's post that the user edited cannot be checked by the body. The matching of `send_message` is not changed
  - The matching for a schedule with files also requires, as in `send_message`, that the number of files match and that all of the schedule's `file_ids` are attached. A post whose files were hidden by ABAC (`file_ids` is empty and there is `metadata.redacted_file_count`) is matched only by the count, and if it matches, all the files of the schedule continue to be held as attached. If there is no post whose body and files both match, and there is a post whose body matches but whose files do not (whichever record holds it), it does not post and makes it a failure of "it is unknown whether this was posted". It may be a post from which Mattermost removed the files in the previous attempt, and resending would make a double post. The same happens even for a schedule without files, if the user posted by hand with files attached to the same body
- Handling by result
  - Success: it is made posted and the `post_id` is recorded. The files that remained on the post are recorded as used for the post in the same transaction (the same as `send_message`). If Mattermost removed files, it remains posted, and the number removed and the `file_id`s are shown in the list as a "note", and the row's `file_ids` is rewritten to those that remained on the post. This is because the removed files are not attached to this post and there is no reason to keep holding them. However, in a channel where the ABAC permission policy of Enterprise Advanced does not allow the user to download files, Mattermost empties `file_ids` in the response and puts the number of attached files in `metadata.redacted_file_count`. In this case which ones were removed is not known, so all the files of the schedule continue to be held as attached and are recorded as used for the post (`send_message` is the same). If the count is less than the schedule's files, only the number removed is shown (without the `file_id`s) as a "note"
  - A Mattermost `4xx` (archived, loss of permission, deletion of the parent post, etc.) and when a re-login is necessary: it is made a failure without retrying, and the reason is recorded in wording for the user. For a post with files, Mattermost also checks the permission to upload files and returns the same `403`, so the wording names both permissions. When a re-login becomes necessary after a request that might have been processed was sent (after a response other than `401` was received, or after the communication was cut once connected), the reason is "it is unknown whether this was posted". When it is made a failure at the first attempt (except "it is unknown whether this was posted"), the record of the attempt is deleted and the files are released. It is not deleted in a retry round. This is because this refusal does not rule out that the previous attempt had posted
  - Rate limit, cannot connect, timeout, `5xx`: it is returned to pending and retried in the next round. When a failure that certainly did not send occurs at the first attempt, the record of the attempt is deleted, and it is returned to the state in which the user can change and cancel. It is not deleted in a retry round. If it were deleted, the next round would post with a new `pending_post_id` without looking for the existing post
  - Unexpected exception: only that schedule is made a failure, and the other schedules continue. The reason is "it is unknown whether this was posted", and the record of the attempt is also kept. This is because the processing before sending returns the fact that nothing was sent with typed failures (rate limit, re-login necessary, cannot connect), and the matching of a retry also handles failures itself, so an unexpected exception, apart from a DB failure, is limited to after sending has started
- A schedule that is more than 1 hour past its scheduled time is not newly posted. This is so as not to post, many hours late, a schedule that passed while the server was stopped. For a schedule for which posting was attempted, as with a retry, it looks for the existing post; if found, it is made posted, if not found, a failure, and if it cannot be searched, a failure of "it is unknown whether this was posted"
- A schedule that has stayed "posting" for more than 30 seconds (one for which the process stopped in the middle of posting) is returned to pending and retried. On a stop signal, it only stops scheduling the next round and does not wait for the running round

**Full text of the body**: The list cuts the body at the first 200 characters, so that the full text can be obtained before `update_scheduled_message` (which replaces the whole body), passing `id` to `list_scheduled_messages` returns that one schedule without cutting the body. The heading of the body in the list is "body (full text)" if it is 200 characters or less, and "body (first 200 characters)" only when it was cut because it exceeded that (the same as the existing draft of `save_draft`). In the list, the second and later lines of the body are indented by 4 characters. If they were put at the start of the line, a line of the body could look like a schedule's heading or a line such as "status:" (the indentation width is the same as the "failure reason:" and "note:" of the same schedule, and the purpose and header of a channel). The fact that it was cut in the list is told not in a line of the body but in a separate line. If it followed the body, the guidance would enter the body when copied. When `id` is passed, the body is put last, and the body is from the line after the heading to the end. The body can be multiple lines, so if another line followed it, the range to copy would not be uniquely determined.

**How failures are made known**: Failures and their reasons can be seen in `list_scheduled_messages`. For a failure of a schedule with files, it adds that to attach them again the files must be uploaded again from `prepare_upload`. The paths that make a failure are divided among the sweep, the time-out, and the admin command for restore, so this is not put in the stored reason and is added in the display of the list. The output of `schedule_message` tells the user to check the result there.
It does not notify by DM. This MCP has no Bot, so posts addressed to oneself in the user's own name would increase.
It also does not interrupt the results of other tools with a failure.

**How to tell them apart on the screen**: A scheduled post appears as an ordinary post of the user. Marking it with props does not show on the standard screen, so it is not made distinguishable.

**Restore**: An old backup contains, still pending, schedules that were cancelled or changed afterward. So in the restore procedure, the admin command `invalidate-scheduled` makes all pending and posting schedules a failure. For schedules for which posting was attempted and schedules whose scheduled time has passed, the reason is "it is unknown whether this was posted". This is because on the lost DB they may have been posted after the backup. The users are told to schedule the other schedules again.

**Known limits**

- The matching of the body cannot distinguish the user's posts with the same destination and the same body. So they can be mistaken in the following two directions
  - If, after a schedule's first attempt, the user posts the same body to the same destination by hand (on the screen or with `send_message`), the schedule's retry regards it as the schedule's post and does not post the schedule
  - While `send_message` retries after an unknown result, if a schedule with the same body is posted to the same destination, a retry that matched before the schedule recorded that post regards it as its own post and does not post. If it matched after the record, the retry returns that it is not known whether it was posted (the "exclusion of other records' posts")
- A double post when Mattermost's processing completes later than the grace for posting (30 seconds) cannot be prevented (the same as `send_message`)
- If `send_message` and a schedule pass the check at the same time with the same file, the one that posts later loses the file (if it is the schedule, it appears in the list as a "note")
- On a server with an ABAC permission policy enabled, when Mattermost temporarily cannot get the user's own information and hides files without giving a count (a known limit of "Posts with attached files"), the first post of a schedule shows all of them as "removed by Mattermost" in the list's note and releases the files. In a retry, the files in the matching list do not match, and it stops as it is unknown whether it was posted
- If the DB, left as updated, is rolled back to an old version that does not read the `file_ids` column, pending schedules with files are posted without files. When rolling back the version, also restore the `/data` from before the update (`docs/operations.md`)
- The files of a schedule that was not attempted and was made a failure by the restore procedure are not treated as held. If they are used for another post, Mattermost removes them if the schedule had been posted before the restore (this appears in the output)
- While `send_message` has finished posting and has not yet written the post ID to its record (a record whose result stayed unknown and was not resent stays as it is for 10 minutes), the schedule's retry cannot exclude that post. If the first attempt of a schedule with the same body has not posted, the schedule takes that post as its own. It does not become a double post, but two records hold the same post
- When the saving of the refresh after a `401` loses a race, the verification post becomes a `5xx`, a timeout or a redirect, and the post is resent with the stored token (the verification post may have been processed)
  - If the resend becomes a `4xx`, it is treated as a definite failure even though it may have been posted. A schedule, if it is the first attempt, deletes the record and releases the files, `send_message` deletes the record, and an upload returns the URL to unused, so a retry can make a double post or a double upload. `mark_as_read` answers that it did not do it for items on which it may have cleared read state or mentions
  - Even in a resend with the same `pending_post_id`, in the following cases Mattermost's deduplication ("Preventing duplicate posts in `send_message`") does not work and it becomes a separate post
    - When Mattermost restarted after the verification post, or when the resend reached another node in an HA configuration (the `pending_post_id` that the deduplication remembered is, by default, in each process's memory and is not carried over)
    - When the user can no longer read the previous post (the `pending_post_id` that the deduplication remembered is ignored)
  - When the verification post had posted and the resend became a separate post and had its files removed, the files attached to the first post are also released. If a released file is used for another schedule, Mattermost removes it, and it appears in that schedule's "note" in the list

### Limiting the load on Mattermost

The MCP server is often run on the same host as Mattermost, and may share CPU, memory and disk with it.
So that an attack, a bug, a memory leak or a bloated DB does not drag Mattermost down, the following are required.

- Set limits on CPU, memory and number of processes on the MCP server's container (for Compose, `cpus`, `mem_limit`, `pids_limit`). The implementer decides the concrete values, after looking at the usage of Mattermost and PostgreSQL
- At the reverse proxy, set an upper limit on the size of request bodies on the MCP paths, and apply a per-IP rate limit (`limit_req`) to the DCR, authorization and token endpoints
- Within the MCP server, set a timeout and an upper limit on concurrent execution for calls to the Mattermost API
- Apply a rate limit to tool calls within the application (Security Considerations of Tools in MCP 2025-11-25). Requests from claude.ai come from Anthropic's shared source addresses, so the reverse proxy's per-IP limit is no substitute
  - What is counted is not the number of tool calls but the number of times the Mattermost API was actually called. When one tool call becomes multiple API calls (such as a search per team), those are counted too
  - Use two levels: a per-Mattermost-user limit and a server-wide limit
  - When the limit is exceeded, do not keep making the caller wait; return a rate limit error as the result of the tool at once
  - When Mattermost returns `429`, do not retry automatically; return it as a rate limit error with the reset time attached
  - The implementer decides the concrete values. The guideline is that they do not hinder the amount a single user normally uses in a conversation (tens of times per minute), and that, even if everyone uses up to the limit at the same time, Mattermost's response time does not visibly worsen. Confirm this by applying load locally
  - It is 300 times per minute per user and 600 times per minute overall. Going around the default 50 channels with `read_channel`, starting from `list_my_channels`, takes about 200 calls, so the per-user value is this; and the overall limit is a value for which "Load" in `docs/measurements.md` confirmed that the response time does not worsen, so even if one user's limit is raised, the maximum load put on Mattermost does not change
- Delete the state of authorizations in progress and authorization codes after a short expiry (about 10 minutes). Also periodically delete grants and tokens that were revoked or expired, and the records for preventing duplicate posts of `send_message` that are past their expiry. DCR registrations are not deleted automatically and are held down by an upper limit on the total number (see "Storage")
- Logs are written to standard output, and the limit on volume is left to the container's log driver

### Deployment

```text
Internet ── reverse proxy (443) ─┬─ /mcp, /mcp/…, /.well-known/oauth-protected-resource/mcp,
                                 │  /.well-known/oauth-authorization-server/mcp ─> MCP server
                                 └─ everything else ─> Mattermost
MCP server ──(MM_URL, HTTPS)──> Mattermost API
```

- The MCP server can be placed under `/mcp` on the same origin as Mattermost, or on a separate host. The URLs are given by environment variables (`PUBLIC_URL`, `MM_URL`, `MM_BROWSER_URL`) and are not assembled from the request's `Host` or `X-Forwarded-*`. If placed on the same origin, the URL of a team named `mcp` (`/mcp/...`) is taken by the MCP server, so that team cannot be created
- Do not expose the MCP server's port to the Internet. Make it reachable only from the reverse proxy
- From the MCP server to Mattermost's API and token endpoint, it calls with HTTPS that verifies certificates, because it sends the client secret and tokens (OAuth 2.1 and RFC 6750 require TLS)
- For the Mattermost authorization URL to which the user's browser is sent and for permalinks, use Mattermost's public URL (`MM_BROWSER_URL`)
- Do not apply the reverse proxy's settings for Mattermost (such as caching) to the MCP paths. Receive the MCP paths with dedicated settings, and disable caching and buffering
- Disable TLS 1.3 Early Data (0-RTT). A request sent with 0-RTT can be resent (replayed), which invites a double post of `send_message` and a false firing of the refresh token reuse detection through the resend of a refresh request. Mattermost's own POST carries the same danger, and the shortening by 0-RTT is only one round trip, so rather than returning `425` only on the MCP paths, disable it for the whole origin if it is the same origin as Mattermost
- Make Mattermost and the reverse proxy keep running even if the MCP server stops (for nginx, write it so that name resolution of the MCP server is not needed at startup)
- The preparation on the Mattermost side is only to enable the OAuth 2.0 service provider and create one OAuth 2.0 app on the Integrations OAuth 2.0 apps screen (`/<team name>/integrations/oauth2-apps`) or with the API (confidential, the callback URL being the MCP server's callback). Because the MCP server shows its own consent screen, "Trusted" on the Mattermost side may be set to "Yes" to avoid showing consent twice. The client ID and secret are passed by environment variables
- The procedures for deployment and operation are written in `docs/deployment.md` and `docs/operations.md`

### Operations

- Logs are written as JSON. What is recorded is the time, the Mattermost user ID, the tool name (for the schedule sweep, the state of the result for each schedule), the result (success, kind of failure) and the elapsed time. Message bodies, search terms and tokens are not recorded
- `/mcp/healthz` is used for the container's healthcheck

### Tests

- The authorization flow and the tools are tested automatically with Mattermost Team Edition set up with Docker Compose locally. No writes for testing are made to a Mattermost in use
- The Mattermost version used for tests is specified with the environment variable `MATTERMOST_IMAGE_TAG`, and if unspecified, v11.7.8, whose behavior was confirmed, is used. The behavior of token reuse, refresh races and app revocation is also checked in this test
- The behavior of Mattermost's token reuse in "Assumptions" is based on the implementation of v11.7.8. When updating Mattermost from v11.7.8, run this test against the new version before updating. If the test does not pass, stop the update of Mattermost and review the design
- The check after deployment connects from three clients with the operator's account and calls the read tools through once. The write tools (including attachments and scheduled posts) are checked only within the operator's own DM (to oneself), and no posts in other channels or of other users are touched. For scheduled posts, check that a schedule whose time was changed and a schedule that was cancelled are posted exactly once as scheduled, and that the body does not appear in the sweep's log

## Left to the implementer

- Write it in TypeScript. The choice of the runtime, the MCP SDK, the web framework, the SQLite driver and the encryption method
- The concrete values of the various expiries, the limits on counts and body length, the resource limits and the rate limits
- The look of the consent screen (it suffices to satisfy the display items and protections above)
- The concrete paths of the OAuth endpoints and the details of the tools' input and output schemas

## Designs not adopted

| Option | Reason for not adopting |
|---|---|
| Enable Mattermost's DCR and have MCP clients register directly with Mattermost | It becomes token passthrough. Public clients are not issued refresh tokens, so re-logins are frequent. The DCR registration endpoint is public without authentication, and OAuth apps can be created in Mattermost without limit |
| Have users issue a Personal Access Token and set it in the MCP client | It does not become "just add the URL and log in". Authentication by fixed headers in claude.ai is offered only in limited availability and becomes an organization-wide credential, so it does not satisfy the requirement of running with each user's own permissions. The token does not expire |
| Remember consent and omit the consent screen from the second time on | Deciding to omit it needs session management that identifies the user before sending to Mattermost. Authorization happens only when a client is added, so the burden is small even if it is shown every time |
| Store in Mattermost's PostgreSQL | See "Storage" |
