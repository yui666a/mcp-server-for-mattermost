# Mattermost リモート MCP サーバー 設計

## 目的

Claude（claude.ai とデスクトップ版）、Claude Code、Codex から、Slack Connector と同じ感覚で Mattermost のメッセージを読み書きできるようにする。
利用者は MCP サーバーの URL（例 `https://mattermost.example.com/mcp`）をコネクタとして追加し、Mattermost のアカウントでログインするだけで使い始められる。

Mattermost の公式 MCP サーバーは Agents プラグインに含まれ、外部の MCP クライアント向けの HTTP エンドポイントには Enterprise 以上のライセンスが要る。
無償の Team Edition でも使えるよう、Mattermost の外で動く独立した MCP サーバーとして作る。

## ゴール

- claude.ai のカスタムコネクタ、Claude Code（`claude mcp add --transport http`）、Codex CLI の 3 つから、URL を登録して OAuth ログインするだけで接続できる
- 各利用者は自分の Mattermost アカウントの権限で動く。本人が見られないチャンネルやメッセージは MCP からも見えない
- 次の操作ができる
  - メッセージの検索
  - チャンネルの最新メッセージ、未読の先頭、または指定した日時の範囲からの読み取りと、スレッドの読み取り
  - パーマリンクの URL か post_id を指定した、1 件の投稿の読み取り
  - 投稿に添付されたファイルの読み取り（画像は縮小版を画像として、テキストは先頭を中身として）と、ファイルの名前での検索
  - 自分が保存した（フラグを付けた）投稿の一覧
  - チャンネルとユーザーの検索、ユーザーのプロフィール参照
  - ユーザーのタイムゾーンと現地時刻、在席状況の参照
  - 参加しているチャンネルの一覧
  - チャンネルの種類、目的、ヘッダー、メンバー数、ピン留めされた投稿の参照
  - 参加しているチャンネルのメンバーの一覧
  - 自分の未読（チャンネルとスレッド）と、自分へのメンション（未読のものだけにも絞れる）の一覧
  - 自分のチャンネルとスレッドの既読化（AI が読んだ投稿まで）
  - フォロー中のスレッドの一覧と、スレッドのフォローと解除
  - チャンネルやスレッドへの投稿（小さなファイルの添付を含む）
  - 投稿への自分のリアクションの追加と削除
  - 参加しているチャンネルの投稿の保存（フラグ）とピン留めの付け外し（保存からの解除は参加を問わない）
  - リアクションやカスタムステータスに使うカスタム絵文字の、名前での検索
  - 自分の在席状況とカスタムステータスの変更
  - 自分の投稿の編集と削除
  - 本人の Mattermost の下書きとしての保存（送信は本人が画面で行う）
  - 指定した時刻にチャンネルやスレッドへ投稿する予約と、その一覧・変更・取り消し
- 一度ログインすれば、使い続けている限り、利用者が取り消すまで再ログインなしで使える（リフレッシュトークンで更新する）

## 非ゴール

- 他人の投稿の編集・削除、チャンネルの作成やメンバー管理
- システム管理系の操作（ユーザー管理、設定変更）
- Mattermost のイベントを MCP クライアントへ通知する機能（購読、通知）
- 複数の Mattermost サーバーへの対応

## 避けたいこと

- MCP サーバーを経由して、本人以外の権限で Mattermost が操作されること
- 利用者が意図しない MCP クライアントに、本人の Mattermost の権限が渡ること
- 意図しないチャンネルへの投稿
- Mattermost 本体の停止や性能劣化。MCP サーバーの障害や過負荷を Mattermost の利用に波及させない
- Mattermost のアクセストークンやメッセージ本文がログに残ること

## 前提（2026-11-01 時点で確認済み）

| 項目 | 値 |
|---|---|
| Mattermost | v11.7.8 Team Edition で挙動を確かめた。ほかの版は結合テストを通してから使う（「テスト」） |
| リバースプロキシ | TLS を終端するリバースプロキシ（例は nginx）の後ろに置く |
| OAuth 2.0 Service Provider | 有効。`/.well-known/oauth-authorization-server` を公開しており、`registration_endpoint` はない（Dynamic Client Registration は無効） |
| Mattermost の OAuth | 認可コードフロー、PKCE は `S256` のみ。public client にはリフレッシュトークンが発行されず、confidential client（`client_secret_post`）には発行される。スコープは `user` のみ |
| Mattermost のトークン再利用 | 同じユーザーと同じ OAuth アプリの組では、新たに認可しても既存のアクセストークンとリフレッシュトークンが返る。リフレッシュするとリフレッシュトークンは新しいものに替わり、使用済みのものは使えなくなる。古いアクセストークンは、ローカルの v11.7.8 での実測ではリフレッシュ後も少なくとも 826 秒は有効なまま残り、利用者がアプリの許可を取り消すと無効になった（[v11.7.8 `oauth.go`](https://github.com/mattermost/mattermost/blob/v11.7.8/server/channels/app/oauth.go)、実測の詳細は `docs/measurements.md`）。Mattermost のトークンは MCP サーバーの外に出さないため、古いアクセストークンが残ることは設計に影響しない |
| 下書きの同期 | サーバー設定 `ServiceSettings.AllowSyncedDrafts`（既定 true）が有効なときだけ、API で保存した下書きが本人の画面に届く。無効なら下書きの API は 501 を返す。導入先で有効かは、導入前に確かめる（`docs/deployment.md` の「Mattermost の事前確認」） |
| 添付の設定 | ローカルの v11.7.8 では `FileSettings.EnableFileAttachments` が true、`MaxFileSize` が 100 MiB。`EnableFileAttachments` が false だとアップロードが 403 になり、`send_message` の添付が使えない。プレビュー（`get_file` が返す縮小版）は設定ではなく、画像のアップロード時に Mattermost が作る。導入先の値は導入前に確かめる（`docs/deployment.md` の「Mattermost の事前確認」） |
| Mattermost の台数 | 下書きの一覧を読むレプリカを持たない構成を前提にする。導入先にレプリカが無いことは、導入前に確かめる（`docs/deployment.md` の「Mattermost の事前確認」） |
| 利用者 | 1 つの Mattermost につき数十人規模。世界中から利用しうる |

## 構成

### 方式: MCP サーバーが自分の認可サーバーを持ち、ログインを Mattermost に委ねる

MCP 仕様（2025-06-18 以降）では、MCP サーバーは自分宛てに発行されたトークンだけを受け付けなければならず、受け取ったトークンを下流の API にそのまま渡すこと（token passthrough）は禁止されている。
Mattermost v11.7.8 には RFC 8707 の `resource` を受け取って記録する実装があるが、REST API がトークンの宛先（audience）を検証することは確認できていない。
Mattermost のトークンを MCP クライアントに直接持たせると、その MCP クライアントが Mattermost の全 API を本人として叩ける。

そこで、MCP サーバーは次の 2 つの役割を持つ。

1. **MCP クライアントに対する認可サーバー**: MCP クライアントの登録（Dynamic Client Registration）、認可、トークン発行を自分で行う。発行するトークンは MCP サーバー宛てで、Mattermost の API には使えない
2. **Mattermost に対する OAuth クライアント**: Mattermost に confidential client として 1 つだけ登録し、利用者のログインを Mattermost の認可画面に任せる。得た Mattermost のトークンはサーバー側に暗号化して保存し、MCP クライアントには渡さない

```text
MCP クライアント ──(MCP トークン)──> MCP サーバー ──(Mattermost トークン)──> Mattermost API
       │                                   │
       └─ 認可: MCP サーバーの /authorize ──> 同意画面 ──> Mattermost の /oauth/authorize（ログイン）
```

### URL とメタデータ

ドメイン直下の `/.well-known/oauth-authorization-server` は Mattermost 自身のメタデータが使っているため、MCP サーバーの認可サーバーは issuer にパスを含め、RFC 8414 のパス挿入形式でメタデータを公開する。

| 項目 | 値 |
|---|---|
| MCP エンドポイント（リソース） | `https://mattermost.example.com/mcp`（末尾スラッシュなし） |
| Protected Resource Metadata（RFC 9728） | `https://mattermost.example.com/.well-known/oauth-protected-resource/mcp` |
| 認可サーバーの issuer | `https://mattermost.example.com/mcp` |
| Authorization Server Metadata | `https://mattermost.example.com/.well-known/oauth-authorization-server/mcp` |
| 認可、トークン、登録、Mattermost からのコールバックなどのエンドポイント | `https://mattermost.example.com/mcp/oauth/` 以下。具体的なパスは実装者が決める |

メタデータには次を必ず含める。

- Protected Resource Metadata: `resource` は MCP エンドポイントの URL と完全一致させる（claude.ai はパスまで完全一致を要求する）。`authorization_servers` は issuer 1 つだけ
- Authorization Server Metadata: `issuer`、`authorization_endpoint`、`token_endpoint`、`registration_endpoint`、`response_types_supported: ["code"]`、`grant_types_supported: ["authorization_code", "refresh_token"]`、`code_challenge_methods_supported: ["S256"]`、`token_endpoint_auth_methods_supported: ["none"]`（DCR で登録されるクライアントは public client とする）、`scopes_supported: ["mattermost"]`
- Protected Resource Metadata にも `scopes_supported: ["mattermost"]` を載せ、`401` の `WWW-Authenticate` にも `scope="mattermost"` を付ける

スコープは `mattermost` の 1 つだけとし、「この利用者の Mattermost アカウントとしてツールを使う」ことを表す。
読み取りと書き込みでスコープを分けない。書き込みの前の確認は、ツールの注釈（`readOnlyHint`）を見た MCP クライアントに任せる（「ツール」）。

- 認可要求で `scope` が省略されたときは `mattermost` を与える。`mattermost` 以外のスコープが含まれていれば `invalid_scope` で拒否する
- スコープは認可コード、grant、アクセストークン、リフレッシュトークンに結び付け、リフレッシュで広げられないようにする

認可要求とトークン要求の `resource` パラメータは必須とし、欠落しているか MCP エンドポイントの URL と完全一致しなければ `invalid_target` で拒否する。
発行した認可コードとトークンは、この 1 つのリソースにだけ使える。
対象の 3 つのクライアントは、どれも認可要求とコード交換で `resource` を送る（`docs/measurements.md` の「クライアント互換性」）。

この形式は RFC 8414 と MCP 仕様の探索手順に沿っており、3 つのクライアントがこの形式のメタデータを見つけて接続できることを実測で確かめた（`docs/measurements.md` の「クライアント互換性」）。

### 認可フロー

1. MCP クライアントが `/mcp` にトークンなしでアクセスすると、MCP サーバーは `401` と `WWW-Authenticate: Bearer resource_metadata="…"` を返す
2. MCP クライアントは Protected Resource Metadata から認可サーバーを知り、Authorization Server Metadata を取得する
3. MCP クライアントは DCR（RFC 7591）で自分を登録する
4. MCP クライアントが PKCE（`S256` 必須）付きで MCP サーバーの認可エンドポイントへ利用者を送る。MCP サーバーは `client_id`、`redirect_uri`、PKCE、`resource` を検証する
5. MCP サーバーは同意画面を出す
6. 利用者が許可すると、MCP サーバーは Mattermost の `/oauth/authorize` へリダイレクトする。このとき MCP サーバーから Mattermost への認可にも、MCP クライアントとは別に生成した PKCE（`S256`）を付ける
7. 利用者は Mattermost でログインし、許可する
8. Mattermost からコールバックに戻ると、MCP サーバーは `state` を照合し、Mattermost のトークンを取得して保存し、MCP クライアントへ認可コードを返す
9. MCP クライアントは認可コードを MCP サーバーのトークンエンドポイントで MCP トークン（アクセストークンとリフレッシュトークン）に交換する

### MCP クライアントへ発行する認可コード

OAuth 2.1 の認可コードの要件（draft-13 §4.1.2–4.1.3）を満たすため、次を守る。

- 認可コードは十分な長さのランダム値とし、サーバー側にはハッシュだけを保存する。有効期限は 1 分程度とする
- 認可コードには、Mattermost ユーザー、`client_id`、認可要求の `redirect_uri`、PKCE の `code_challenge`（`S256`）、`resource` を結び付けて保存する
- トークン要求では、`client_id`、`redirect_uri` が保存した値と一致すること、`code_verifier` が `code_challenge` と一致することをすべて確かめる。1 つでも合わなければ `invalid_grant` で拒否する。`resource` の欠落や不一致は `invalid_target` で拒否する
- 認可コードの消費とトークンの発行は 1 つのトランザクションで行い、同じコードを 2 回使えないようにする。使用済みのコードが再び提示されたら、そのコードから発行したトークンを失効させる
- MCP クライアントから受け取った `state` は、Mattermost へ送る `state` とは別に保存し、成功時もエラー時もそのままの値で MCP クライアントへ返す

### 同意画面

Mattermost 側の OAuth アプリは 1 つの固定クライアント ID で、誰でも DCR でクライアントを登録できる。
同意画面がないと、「攻撃者が登録したクライアントのリダイレクト先へ、Mattermost にログイン済みの利用者の認可が自動で流れる」confused deputy 攻撃が成立する。
MCP の Security Best Practices に従い、同意画面は次を満たす。

- 認可要求のたびに、Mattermost へリダイレクトする前に必ず表示する。同意の記憶による省略はしない。利用者が認可するのはクライアントを追加するときだけで、毎回の表示は負担にならないため
- クライアント名、登録されたリダイレクト URI の全体、要求されている権限（スコープ `mattermost` の意味として「あなたの Mattermost アカウントとしてメッセージの読み書きをする」）を表示する。クライアント名は登録者が自由に付けられるため、リダイレクト URI を名前より目立たせる
- リダイレクト URI がループバック（`localhost`、`127.0.0.1`）のクライアントには、「この端末上のアプリに権限を渡す。自分で Claude Code や Codex の接続を始めた場合だけ許可する」旨の警告を追加で表示する（MCP 2025-11-25 の Localhost Redirect URI Risks）
- 許可フォームには CSRF トークンを付ける。応答に `Content-Security-Policy: frame-ancestors 'none'` と `X-Frame-Options: DENY` を付け、他サイトの iframe に埋め込ませない
- Mattermost へ送る `state` は、利用者が許可した時点で生成する。サーバー側の認可途中の記録に、ブラウザのクッキー、Mattermost へ送る `state` と PKCE、MCP クライアントの `client_id`、`redirect_uri`、PKCE、`state`、`resource` をまとめて保存する。この記録は 1 回だけ使えて、10 分程度で期限切れにする。コールバックで `state` とクッキーが記録と一致しなければ拒否する
- DCR で登録されたクライアント名とリダイレクト URI は、登録者が自由に決めた信用できない値として扱う
  - 登録時に長さの上限を設け、制御文字を含む値を拒否する
  - 同意画面とエラーページでは、自動でエスケープするテンプレートかテキストノードとしてだけ表示し、HTML として解釈させない
  - DCR の `logo_uri` などの外部リソースは読み込まない
  - クライアント名の横に「名前は登録者の自己申告で、確認されていない」と表示する
- 同意画面とエラーページの応答には `Content-Security-Policy: default-src 'none'; style-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` 相当を付け、スクリプトを一切実行させない。同意画面はスクリプトなしで動く HTML フォームとする
- 悪意あるクライアント名やリダイレクト URI（HTML タグ、制御文字、極端に長い値）で登録し、同意画面でスクリプトが実行されず表示も崩れないことを自動テストで確かめる
- クッキーは `__Host-` で始まる名前にし、`Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/` を付け、`Domain` は付けない（MCP Security Best Practices の Confused Deputy 対策）。値はランダムなセッション ID とし、中身はサーバー側に持つ

### リダイレクト URI

DCR で登録を受け付けるリダイレクト URI は次に限る。
これに当てはまらない登録要求は `invalid_redirect_uri` で拒否する。

- `https://claude.ai/api/mcp/auth_callback`、`https://claude.com/api/mcp/auth_callback`（claude.ai とデスクトップ版。現行の [Authentication for connectors](https://claude.com/docs/connectors/building/authentication#callback-urls) が指定するのは `claude.ai` 側だけだが、Anthropic の旧ヘルプセンター記事（現在は公開終了）が、将来 `claude.com` 側に変わる可能性があるとして両方の許可を勧めていた。Anthropic 管理のドメインを完全一致で 1 つ足すだけなので両方を許可する）
- ループバック（`http://localhost:<任意ポート>/<任意パス>`、`http://127.0.0.1:<任意ポート>/<任意パス>`）（Claude Code、Codex CLI）

許可パターンは環境変数で追加できるようにする。

認可要求の `redirect_uri` は、その `client_id` に登録された URI と完全一致させる。
例外はループバックのポート番号だけで（RFC 8252、RFC 9700）、スキーム、ホスト、パス、クエリは一致させる。
`client_id` が不明な場合や `redirect_uri` が一致しない場合は、エラーをリダイレクトで返さず、MCP サーバー自身のエラーページを表示する。

### MCP のトークン

- アクセストークンは短命（1 時間程度）とする。リフレッシュトークンの期限は最後に使われてから 90 日程度とし、ローテーションのたびに期限を延ばす。発行からの絶対期限は設けない。使い続けている限り再ログインは要らず、90 日使わなかった利用者だけが再ログインする。正確な値は実装者が決める
- トークンはランダムな不透明文字列とし、サーバー側にはハッシュだけを保存する
- リフレッシュトークンはローテーションする（RFC 9700 §4.14.2）。1 回の認可から続くトークンの系列（grant）を記録し、リフレッシュでは使用済みの記録と新しいトークンの発行を 1 つのトランザクションで行う。使用済みのリフレッシュトークンが再び提示されたら、盗まれたものとみなし、その grant のアクセストークンとリフレッシュトークンをすべて失効させる
- 利用者が Mattermost の「設定 > セキュリティ > OAuth 2.0 アプリ」から MCP サーバーのアプリを取り消すと、後述の流れでその利用者の grant がすべて失効する

### Mattermost のトークン

Mattermost は同じユーザーと同じアプリの組に 1 組のトークンしか持たせないため、Mattermost のトークンは Mattermost ユーザーごとに 1 組だけ保存し、その利用者のすべての grant から参照する。
MCP クライアントごとに複製して持つと、どれか 1 つがリフレッシュした時点で他の複製が無効になる。

- アクセストークンとリフレッシュトークンは、環境変数で渡す鍵で暗号化して保存する。鍵を変えると保存済みのトークンが読めなくなり、全員が再ログインする
- Mattermost の API が `401` を返したら、まず保存済みの最新のトークンを読み直す。別の要求が既にリフレッシュしていれば、そのトークンで 1 回だけ再試行する
- リフレッシュはユーザー単位で 1 つずつ行う（同時に来た要求は 1 回のリフレッシュの結果を待つ）。新しいアクセストークンとリフレッシュトークンは 1 つのトランザクションで書き換える
- リフレッシュに対して Mattermost が `invalid_grant` を返したとき、または利用者が無効化されたときだけ、その利用者の Mattermost のトークンと MCP の grant をすべて失効させ、MCP クライアントに `401` を返して再ログインを促す
- Mattermost は無効なセッションの要求を、API のハンドラーを呼ぶ前に `401` で断る（v11.7 の `web/handlers.go`）。そこで、1 回の呼び出しで `401` しか受けていなければ、Mattermost に何も処理させていないものとして扱う。再ログインが必要になっても、投稿やアップロードは「送ったか不明」ではなく「送っていない」になる。`401` 以外の応答を一度でも受けたか、接続した後に通信が切れたら、処理されたかもしれないものとして扱う。この前提は、本体が `401` を返す API（`deleteChannel`、`deleteUser` など）には当てはまらないので、それらを使うときは見直す
- タイムアウト、接続失敗、`5xx` などの一時的な失敗では保存した情報を変えず、ツールの一時的なエラーとして返す

### 保存先

MCP サーバーは 1 プロセスだけで動かすので、保存先はボリュームに置く SQLite ファイルとする。
保存するのは、登録された MCP クライアント、認可途中の状態、MCP の grant とトークン、Mattermost のトークン、`send_message` の重複防止の記録、予約投稿である。

このうち DCR の登録は、各クライアントが接続ごとに 1 回だけ行い、得た `client_id` を使い続ける。
登録が消えると、そのクライアントは `invalid_client` になり、再ログインでは戻らない（コネクタの削除と追加し直しが要る）。
一方、DCR の登録エンドポイントは認証なしで公開されるため、第三者が登録を積み上げられる。
そこで登録を 2 つに分けて扱う。

- **認可済みの登録**（一度でも利用者が認可を完了した登録）: 自動では消さない。認可には Mattermost のアカウントが要るため第三者には増やせず、総数の上限も設けない
- **未認可の登録**: 専用の上限（数百件程度）と期限（7 日程度）を設ける。期限を過ぎたものは消す。上限に達したら、新しい登録を拒否せず、最も古い未認可の登録を消して枠を空ける。第三者が登録を積み上げても、正規の利用者が新しく接続できなくなることはない
- 未認可の登録を消されたクライアントは、認可を始めた後に 7 日以上放置した場合などに限られ、そのときはコネクタを追加し直す
- 登録エンドポイントには IP ごとのレート制限もかける（「Mattermost への影響を抑える仕組み」）。未認可の登録が上限に近づいたら警告ログを出す

MCP サーバー専用のバックアップの仕組みは持たない。
SQLite ファイルのディレクトリと暗号化鍵を、導入先のバックアップ（ファイルのコピーやディスクのスナップショット）に含める。
SQLite ファイルを失った場合は、直近のバックアップから次の手順で SQLite ファイルを戻し、DCR の登録を戻す。
バックアップより後に登録したクライアントは戻らないので、その利用者にはコネクタを追加し直してもらう。

古いバックアップから復元すると、使用済みのリフレッシュトークンの記録や失効した grant が過去の状態に戻り、ローテーション済みの古いトークンが再び有効になりうる。
そこで、バックアップからの復元は次の手順に限る。

1. 復元した SQLite ファイルで MCP サーバーを起動する前に、MCP サーバーのイメージの管理コマンドを、ネットワークなしの単独のコンテナで実行し（SQLite の `-wal`、`-shm` を含めてディレクトリごとマウントする）（`docker run --rm --network none -v <SQLite のディレクトリ>:/data <イメージ> <削除コマンド>`）、認可途中の状態、認可コード、grant、MCP のトークン、Mattermost のトークン、`send_message` の重複防止の記録をすべて削除する。登録された MCP クライアント（DCR の登録）は消さない
   続けて、待機中と投稿中の予約をすべて失敗にする（「予約投稿」の「復元」）
2. その後で MCP サーバーを起動する。ディスクのスナップショットのように、復元すると MCP サーバーが自動で起動する形で戻すときは、巻き戻った状態の MCP サーバーに届く経路ができないよう、自動起動の前に 1 を済ませる

DCR の登録を残すので、各クライアントはコネクタを追加し直す必要がなく、手元のリフレッシュトークンが `invalid_grant` で拒否された後の通常の再ログインだけで戻る。
DCR の登録は利用者の権限を持たないため、巻き戻っても実害はない。
暗号化鍵は作り直さない。Mattermost のトークンは削除するが、失敗にした予約の本文は同じ鍵で暗号化されたまま更新から 7 日残り、作り直すと一覧で本文が読めなくなるため。
この手順を運用手順書（`docs/operations.md`）に書く。

Mattermost の PostgreSQL に DB を追加する方式は採らない。
Mattermost の DB と運用（ダンプ、リストア、メジャーバージョン更新）を共有することになり、MCP サーバーの都合で Mattermost の DB に手を入れる場面を作りたくないからだ。

### MCP の転送方式

Streamable HTTP を `/mcp` で提供する。
セッションを持たない stateless モードとし、通知の購読は提供しない。
旧方式の HTTP+SSE は提供しない（3 つの対象クライアントはいずれも Streamable HTTP に対応している）。

MCP の Streamable HTTP の仕様に従い、`Origin` ヘッダーがある要求は許可リスト（既定は `https://claude.ai` と `https://claude.com`、環境変数で追加可）に含まれなければ `403` で拒否する。
`Origin` ヘッダーのない要求（CLI やサーバー間の通信）は、ベアラートークンの検証だけで受け付ける。

### ツール

すべて呼び出した利用者の Mattermost トークンで Mattermost REST API v4 を呼ぶ。
MCP サーバー自身は管理者トークンや Bot アカウントを持たない。

| ツール | 内容 |
|---|---|
| `search_posts` | 利用者が参加しているチームを対象にメッセージを検索する。Mattermost の検索構文（`from:`、`in:`、`before:`、`after:` など）をそのまま渡せる。`in:` にはチャンネルの指定（下記）を渡せる。DM は作らない。Mattermost の標準のデータベース検索はメッセージ添付の中身に当たらないため、そのことをツールの説明に書き、中身を探すなら `read_channel` で読むよう促す |
| `read_channel` | チャンネルの最新メッセージを新しい順に、件数を指定して読む。`from: "unread"` なら未読の先頭から古い順に読む。`since`（と `until`）を渡すと、その日時の範囲を古い順に読む。ページングできる。読んでも既読にしない |
| `read_thread` | スレッドの親投稿と返信を古い順に読む。ページングできる |
| `get_post` | パーマリンクの URL か post_id で指定した 1 件の投稿を、チャンネルとチーム、返信数とともに読む。返信なら親の post_id を、返信のある親投稿なら `read_thread` で続きを読めることを示す |
| `get_file` | 投稿に添付されたファイルを `file_id` で読む。画像なら Mattermost のプレビュー（幅 1920px 以内の縮小版）を MCP の image コンテンツで返す。原寸は返さない。テキスト（UTF-8、または拡張子が csv・tsv・txt・log の Shift_JIS か EUC-JP）なら中身を先頭から 10,000 文字まで返す。PDF などそれ以外は、名前、種類、大きさだけを返す |
| `search_files` | 利用者が参加しているチャンネル（アーカイブ済みを除く）、DM、グループ DM の添付ファイルを、名前と Mattermost の検索構文（`from:`、`in:`、`ext:`、`before:` など）で探す。ファイルごとに `file_id` と、投稿があれば `post_id` とパーマリンクを返し、`get_file` と `get_post` に続けられるようにする |
| `list_saved_posts` | 利用者が保存した（フラグを付けた）投稿のうち、参加しているチャンネルの投稿を新しい順に一覧する。アーカイブ済みのチャンネルの投稿も含み、そのチャンネル名に「アーカイブ済み」と付ける（送信先に選ばないように）。保存の追加と解除は `save_post` / `unsave_post` で行う |
| `search_channels` | 名前でチャンネルを探す（公開チャンネルと、利用者が参加している非公開チャンネル、DM、グループ DM） |
| `list_my_channels` | 参加しているチャンネル（公開、非公開、DM、グループ DM）を、最終投稿の新しい順に一覧する。種類で絞れる。アーカイブ済みは含まない |
| `get_channel` | チャンネルの種類、目的、ヘッダー、メンバー数、ピン留めされた投稿を読む。メンバーの一覧は `list_channel_members` で読む。ピン留めの付け外しは `pin_post` / `unpin_post` で行う |
| `list_channel_members` | 読む権限のあるチャンネル（通常は参加しているチャンネル）のメンバー（無効化されたユーザーを除く）を、ユーザー名の順に一覧する |
| `search_users` | 名前やユーザー名でユーザーを探す |
| `get_user` | ユーザーのプロフィールに、タイムゾーンと呼び出した時点の現地時刻、在席状況（オンライン、離席、取り込み中、オフライン、不在）を添えて読む |
| `get_unreads` | 未読のあるチャンネル（未読数、メンション数）と、スレッドの折りたたみ（CRT）が有効なら未読の返信があるスレッドを一覧する。既読にはしない |
| `get_mentions` | 自分へのメンション（`@ユーザー名` と通知の設定のキーワード）を新しい順に一覧する。全チームと DM が対象。`unread_only` なら未読のメンションだけにする |
| `list_followed_threads` | フォロー中のスレッドを、最終返信の新しい順に一覧する。全チームと DM が対象。スレッドの折りたたみ（CRT）が無効な利用者には使えない |
| `follow_thread` | スレッドをフォローする。すでにフォロー中なら何もしない |
| `unfollow_thread` | スレッドのフォローを外す |
| `mark_as_read` | 本人のチャンネルとスレッドを既読にする。`last_post_id`（読んだ投稿のうち最も新しいもの）より後に自分以外の投稿があるチャンネルは既読にせず、スレッドはその投稿までを既読にする。合わせて 20 件まで |
| `send_message` | チャンネルへ投稿する。`root_id` を渡すとスレッドへの返信になる。`files` でファイルを 1〜5 件、中身の合計 128KiB まで添付できる。`file_ids` で `prepare_upload` からアップロードしたファイルを 1〜5 件添付できる。同じ投稿先に本文の同じ下書きがあれば、投稿の後に消す（添付の付いた下書きは消さない） |
| `prepare_upload` | 利用者の PC にあるファイルを、MCP クライアントが `curl` で送るための使い捨てのアップロード URL を発行する |
| `add_reaction` | 投稿に自分のリアクションを付ける。絵文字は Mattermost の絵文字名で指定し、前後のコロンは外して受け付ける。別名（`thumbsup` と `+1` など）はまとめない。Mattermost 自体が別のリアクションとして扱うため。カスタム絵文字の名前は `search_emoji` で調べるよう、引数の説明と、名前が無いときのエラーで案内する |
| `remove_reaction` | 投稿から自分のリアクションを外す。他人のリアクションは外さない。Mattermost は付いていないリアクションでも成功を返すため、外したかどうかは区別しない。絵文字名の受け付け方と `search_emoji` の案内は `add_reaction` と同じ（存在しない名前の絵文字も成功になるので、案内が出るのは名前に使えない文字を渡したときだけ） |
| `save_post` | 投稿を自分の保存した投稿に加える。参加しているチャンネルの投稿だけを扱う。Mattermost は参加していない公開チャンネルの投稿も保存できるが、その保存は `list_saved_posts` にも Mattermost の画面の保存した投稿にも出ないため、保存したと報告して見つからない食い違いを作らないよう断る。既に保存済みでも成功する |
| `unsave_post` | 投稿を自分の保存した投稿から外す。投稿もチャンネルへの参加も確かめない。チャンネルを抜けた後に残った保存も外せるようにするため（投稿を消したときは Mattermost がその投稿の保存も消すが、スレッドの元の投稿を消したときの返信の保存は残り、消し損ねて残ることもある。それらも外せる）。外したかどうかは区別しない。保存していなくても成功する |
| `pin_post` | 投稿をチャンネルにピン留めする。投稿の本文は変えずにチャンネルの印を付けるだけなので、非ゴールの「他人の投稿の編集」には当たらない。参加しているチャンネルの投稿だけを扱う。Mattermost は参加していない公開チャンネルでも許すが、チャンネルの全員に見える印なので、参加していないチャンネルでは変えない。サーバーの編集の期限（`ServiceSettings.PostEditTimeLimit`）を過ぎた投稿は、Mattermost がピン留めの付け外しも断る。既にピン留めされていても成功する |
| `unpin_post` | 投稿のピン留めを外す。Mattermost はピン留めした人を記録しないため、他人のピン留めも外れる。参加しているチャンネルの投稿だけを扱う。ピン留めされていなくても成功する |
| `edit_message` | 自分の投稿の本文を書き換える。編集で足したメンションは通知されない（Mattermost が編集では通知しないため） |
| `delete_message` | 自分の投稿を削除する。削除は取り消せないので、ツールの説明で、実行の前に利用者へ確認するよう MCP クライアントに求める |
| `save_draft` | 投稿せずに、本人の下書きとして保存する。`root_id` を渡すとスレッドへの返信の下書きになる。同じ投稿先に本文の違う下書きがあれば、`overwrite` を指定しない限り上書きしない。同じ本文を `send_message` で送ると、この下書きは消える（添付の付いた下書きは消さない） |
| `schedule_message` | 指定した時刻（タイムゾーンが無ければ JST）にチャンネルやスレッドへ投稿するよう予約する。今から 1 分後から 30 日後まで、待機中の予約は 1 人 20 件まで。`file_ids` で `prepare_upload` からアップロードしたファイルを 1〜5 件添付できる |
| `list_scheduled_messages` | 本人の予約を、予定時刻の順に、状態と失敗の理由、添付するファイル、投稿済みなら `post_id` とパーマリンクとともに返す。本文は先頭 200 文字まで。`id` を渡すと、その 1 件を本文を切らずに返す |
| `update_scheduled_message` | 待機中の本人の予約の本文か予定時刻を変える。投稿先と添付は変えられない（変えるときは取り消して予約し直す） |
| `cancel_scheduled_message` | 待機中の本人の予約を取り消す |
| `search_emoji` | カスタム絵文字を名前の一部で探す。標準の絵文字は対象にしない。Mattermost に標準の絵文字の一覧を返す API が無く、一覧を持つと版ごとの差を追う必要があるため。Mattermost の検索は 200 件で打ち切られ、続きを取れないので、200 件に達したら続きがありうることを出力に明示する |
| `set_status` | 自分の在席状況（オンライン、離席、取り込み中、オフライン）を変える。取り込み中には終了時刻（タイムゾーンが無ければ JST、今から 1 分後以降）を付けられる。同じ引数で繰り返すと、取り込み中の終了後に戻る先が取り込み中になるため、冪等とはしない。不在から変えると Mattermost が自動返信を止め、MCP からは戻せないため、注釈は `destructiveHint: true` とする |
| `set_custom_status` | 自分のカスタムステータス（絵文字、文言、期限）を設定する。期限は `set_status` の終了時刻と同じく読む |
| `clear_custom_status` | 自分のカスタムステータスを消す |

- どのツールも、引数（inputSchema）に無いキーを渡されたらツールを実行せずにエラーにし、受けないキーの名前を返す。MCP の SDK の既定では知らない引数を黙って捨てるので、名前を誤った引数（`file_ids` を `file_id` とするなど）を渡すと、それが無いものとして投稿や変更をしてしまうため。ツールの登録を 1 か所（`buildServer`）で包んで、各ツールの引数の定義を strict にする。そのため、ツールに新しい引数を足すときは必ず inputSchema に書く。引数を受けないツールも inputSchema に `{}` を書く（inputSchema の無いツールは包みの対象にならない）。zod のスキーマを直接渡すツールは、自分で strict にする。入れ子のオブジェクトの中のキーは対象にしない（`mark_as_read` の `channels` と `threads` の要素は例外。「既読にする」の節を参照）
- 読み取り系のツールには MCP のツール注釈 `readOnlyHint: true` を付け、書き込み系のツール（`send_message`、`prepare_upload`、`add_reaction`、`remove_reaction`、`save_post`、`unsave_post`、`pin_post`、`unpin_post`、`edit_message`、`delete_message`、`save_draft`、`schedule_message`、`update_scheduled_message`、`cancel_scheduled_message`、`mark_as_read`、`set_status`、`set_custom_status`、`clear_custom_status`、`follow_thread`、`unfollow_thread`）には付けない。MCP クライアントが書き込みの前に利用者へ確認を求められるようにするため
- `save_post`、`unsave_post`、`pin_post`、`unpin_post` の注釈は `readOnlyHint: false`、`destructiveHint: false`、`idempotentHint: true` とする。外す側も、利用者に見える状態は付け直しで戻せる（編集の期限を過ぎた投稿のピン留めを除く。ピン留めした人は記録されないので、他人のピン留めも付け直せる。抜けたチャンネルの投稿の保存は、再参加するまで付け直せないが、その保存は Mattermost の画面の保存した投稿にも `list_saved_posts` にも出ない）。MCP の定義では `destructiveHint: false` は追加の更新だけを指すが、このサーバーは `mark_as_read` と同じく、取り消せるかどうかで付ける
- 出力は LLM が読みやすいテキストとし、投稿ごとに投稿者のユーザー名、日時、本文、パーマリンク（`https://mattermost.example.com/<team>/pl/<post_id>`）を含める。読み取り系の出力には、チャンネルとチームの ID と名前も含め、LLM が続く呼び出しで ID を使えるようにする
- チャンネルの指定は次のどれかとする。名前から候補が 2 つ以上見つかった場合は、どれかを選ばずにエラーとし、候補のチーム名、チャンネル名、チャンネル ID を返す
  - チャンネル ID（英数字 26 文字）。その ID のチャンネルが無く（404）、小文字に直した同じ文字列を名前に持つチャンネルがあれば、「チーム名/チャンネル名」の形で指定するよう案内するエラーにする。チャンネル名は小文字だけで、26 文字の英数字の名前もありうるため（Mattermost が作る ID も小文字と数字だけなので、大文字を含む 26 文字は名前の書き間違いの見込みが高い）。名前で見つかったチャンネルを ID の代わりには使わない。ユーザー ID や投稿 ID を取り違えて渡したとき、その文字列を名前にしたチャンネル（誰でも作れる）へ書き込まないため。403 は ID のチャンネルがあることを示すので名前を引かない
  - `チーム名/チャンネル名`
  - チャンネル名だけ（利用者が参加しているチームから探す）
  - `@ユーザー名`（その相手との DM）。自分のユーザー名なら、自分自身との DM（画面の自分宛てのメモと同じチャンネル）を指す。下の規則で DM を作るツールは、自分自身との DM も無ければ作る。Mattermost が自分自身との DM を正式に扱い（`POST /channels/direct` は、重複を除いて自分の ID が 1 つだけ残れば、自分自身との DM として作る）、メモや下書きの置き場として使えるため、断らない
  - `@a,b`（自分以外のメンバーとのグループ DM）。各要素の `@` は付けても付けなくてもよく、並び順は問わない。大文字は小文字に、重なった名前は 1 つにまとめ、自分の名前は落とす。空の要素はエラーにする
    - 区切りに読点（、）や全角のカンマ（，）を使い、区切った各部分がユーザー名として使える指定は、半角のカンマで書くよう促すエラーにする
    - 自分以外が 2〜7 人でなければエラーにする。Mattermost のグループ DM は自分を含めて 3〜8 人のため。1 人なら `@ユーザー名` を使うよう促す
    - ユーザーは `POST /users/usernames` で 1 回で引き、見つからない名前を並べてエラーにする
    - グループ DM は、自分を含むメンバーの ID を並べ替えて連結した sha1（Mattermost の `GetGroupNameFromUserIds` と同じ）を名前として引く。`POST /channels/group` は無ければ作るため、読み取りでは使わない
    - 出力の投稿先には、自分以外のメンバーを `@a, @b` と並べる
- チャンネルの指定のチーム名とチャンネル名は小文字に直して引く。Mattermost の名前は小文字だけで、大文字を含むと 400 で断られるため。エラー文には利用者が書いた形を出す
- `@ユーザー名` の DM と `@a,b` のグループ DM が無いとき、書き込み系のツールのうち `send_message`、`save_draft`、`prepare_upload`、`schedule_message` だけが作る（`POST /channels/direct`、`POST /channels/group`）。読み取り系のツールと `mark_as_read` は作らない。利用者が開いていない DM を、読んだだけで残さないため
  - `prepare_upload` で作るのは、アップロードしたファイルが投稿先の `channel_id` に結び付くため
  - 既存の DM は先に引く。作成の権限が無い利用者でも、既にある DM には書けるようにするため
  - `root_id` か `file_ids` を渡したときは作らない。まだ無い DM には親投稿もアップロードしたファイルも無く、作った直後に必ず失敗して空の DM だけが残るため
    - `file_ids` を渡してまだ DM が無いときは、DM が無いことより先にファイルの誤り（記録に無い、別のチャンネル、重複）を返す。まだ無い DM のファイルはありえず、本当の誤りはファイルの指定のほうのため
  - Mattermost に DM を問い合わせずに分かる失敗は、投稿先の解決（DM の作成）の前に確かめる。`prepare_upload` と `schedule_message` の上限の件数（`schedule_message` は DM を作りうるとき、つまり `@` で始まる指定で `root_id` も `file_ids` も無いときだけ。それ以外はチャンネル名やファイルの誤りを先に返し、上限は予約の行を作るときに確かめる）、`save_draft` の下書きの同期の無効（`@` で始まる指定で `root_id` が無いときは、下書きの一覧を解決の前に取る。`root_id` があるときは DM を作らないので、チャンネル宛てと同じく `root_id` の誤りを先に返す。この一覧は同期の無効とチームの有無の検査だけに使い、既存の下書きとの照合は、保存の直前に `send_message` の後の削除と直列にして取り直した一覧で行う（「`send_message` の後の下書きの削除」））
  - 無効化したユーザーとは作らない（グループ DM では 1 人でも含まれれば作らない）。Mattermost は作れるが、相手は読めず、空の DM が残るだけのため
  - グループ DM を作ることは、名前の打ち間違いが実在の別人に当たるリスクを含めて、DM と同じ水準として受け入れる。指定は利用者か AI が明示した名前の並びで、DM 以上の確認を求める根拠が無いため
  - 作った後で失敗しても（前の検査と後の検査の間に並行の要求で上限に達したとき、`send_message` の `files` を Mattermost が断ったときなど）、作った DM は消さない。Mattermost の API は DM を消せない（`DELETE /channels/{id}` は DM を断る）ため。画面で DM を開いたのと同じで、空の DM が一覧に出るだけになる
- `search_posts` と `search_files` の `in:`（`-in:`、`channel:` を含む）は、MCP サーバーがチャンネルの指定をチャンネル ID に置き換えてから Mattermost に渡す。全チームの検索では Mattermost がチャンネル名をチームなしで引くため名前が効かず、`in:@ユーザー名` を渡すと DM が作られるため
  - 名前から候補が 2 つ以上見つかった場合は、上の規則の例外として、エラーにせず候補のすべてで探し、そのことを出力に添える。`-in:` なら候補のすべてを除き、注記は付けない。`in:` は検索を絞る条件で、出力の各投稿にチーム名が付くため区別できる
  - DM が無い相手は、`in:` ではエラーにし、`-in:` では条件を落とす。どちらでも DM は作らない
  - `in:` と `channel:` は 1 回の検索で 20 個までとし、超えたら何も引かずにエラーにする。1 回の検索の中では同じ GET（参加チームの一覧、チーム、チャンネル）を繰り返さない。名前 1 つにつき参加チームの数だけ（ID の形の指定は、ID で見つからなければもう 1 回）引くので、チームが 10 なら最悪 221 回になる。参加チームが 10 以下で、同じ 1 分にほかの呼び出しが無ければ、1 利用者あたり 1 分 300 回の上限に収まる
  - 見つからないチャンネルやユーザーは、`-in:` でもエラーにし、検索しない
  - グループ DM（`@a,b`）も同じく置き換える。チャンネルの指定と同じ正規化を効かせ、見つからなければエラーにするため。Mattermost に任せると、各名前をそのまま引くので、自分を含む全員を小文字で書かないと黙って 0 件になる
  - 検索語は空白で語に分かれるため、`@a,b` のカンマの前後に空白を入れない。入れたらエラーにする。カンマの前に空白があるときは、空白の後の全角のカンマ（，）もカンマとみなす。読点（、）は、その後が空か、ユーザー名に使える文字と区切りだけのときに限ってカンマとみなす。`、議事録` のように読点で始まる検索語もあるため
- `send_message` は、投稿先が一意に決まらない場合、必ずエラーにする。`root_id` を渡したときは、その投稿が指定したチャンネルにある、返信でない親投稿であることを確かめる（`save_draft`、`schedule_message` と同じ検査）。Mattermost は返信を親にした投稿を汎用の 400 で断るので、先に理由の分かる文言で断る
- ユーザーはユーザー ID か `@ユーザー名` で指定する
  - チャンネルの指定の `@ユーザー名` で、ユーザーを引いて 400・403・404 が返れば、見つからないユーザーとしてエラーにする。ユーザーを見る制限のある利用者には、Mattermost は存在しない名前にも 403 を返し、`@all` などの予約語には 400 を返すため
  - ユーザー名は小文字に直して引く。Mattermost のユーザー名は小文字だけで、大文字を含むと 400 で断られるため
- `get_post` が受け付ける URL は、Mattermost の URL（`MM_BROWSER_URL`）とオリジンとベースのパスが一致し、userinfo を含まない `…/<チーム名>/pl/<post_id>` の形だけとする。ほかのホストのパーマリンクの post_id を、この Mattermost の投稿として読み違えないため。URL のチーム名は使わず、出力のパーマリンクは投稿の実際のチームで作る
- 1 回の応答が大きくなりすぎないよう、件数と本文の長さに上限を設ける。具体的な値は実装者が決める
- 投稿を出すツールは、添付ファイルごとに `file_id`、名前、種類、大きさ、画像なら幅と高さの行を出す。投稿の `metadata.files` が無く `file_ids` だけがある投稿（スレッドの API が返すもの）は、件数と、`get_post` で確かめられることだけを出す
- 投稿を出すツールは、`props.attachments`（メッセージ添付。Bot や webhook の通知は本文を空にして内容をここに入れることが多い）を、本文の後に `メッセージ添付（Bot などの整形表示）n/件数:` の見出しで 1 件ずつ出す。項目は作成者、前置き、タイトル（リンク）、本文、`fields`、フッター、ボタンやメニューの名前（MCP からは操作できないことを添える）の順で、値が空のものは出さない。出す項目が 1 つも無い添付も、件数が分かるよう見出しだけは出す
  - `fallback` は、前置き、タイトルかそのリンク、本文、`fields` のどれも無いときだけ要約として出す。ほかの項目と同じ内容の平文の要約のため
  - 色、画像、アイコン、作成者のリンクは出さない。MCP からは開けず、内容の理解に効かないため
  - 添付は投稿者が自由に書けるので、型を信用しない。オブジェクトでない添付や要素は飛ばし、値は文字列、数値、真偽値だけを出す。項目の行はすべて 2 文字、値の中の改行（表示によって改行として扱われる制御文字を含む）の後は 4 文字字下げし、添付の中の行が投稿の区切りやファイルの行と同じ形にならないようにする
  - 添付には、見出しと字下げを含めて、本文とは別に本文と同じ長さの上限を設ける。本文と合算すると、長い本文の投稿で添付が丸ごと消えるため。切ったときは切った位置に、行頭から注記の行を出す
- 投稿を出すツールは、本文の各行を 2 文字字下げする（改行の判定は添付と同じ。長さの上限で切った後に字下げし、空の本文は空の行を 1 行出す）。本文も投稿者が自由に書けるので、行頭から出すと投稿の区切り、添付の見出し、ファイル、リアクション、パーマリンクの行を偽れるため。`get_post` は、本文を切ったときだけ末尾にそのことを書く。添付を切ったことは切った位置の注記で伝わるため
  - `edit_message` は本文を丸ごと置き換えるので、`edit_message` の `message` と `get_post` の説明で、字下げを外すこと、切った投稿は出力を元に書き換えないこと、一覧のツールの出力からは投稿ごとに切ったことを書く `get_post` で読み直すことを伝える
- ツールの出力には、利用者が書ける値（投稿の本文、メッセージ添付、ファイル名と中身、チャンネルの表示名・目的・ヘッダー、プロフィール、カスタムステータスなど）がそのまま入り、エラー文の案内に入ることもある。MCP サーバーはその中に書かれた指示を無害化しない。指示かどうかは判定できず、書き換えると読みたい内容まで変わるため。守るのは出力の構造で、行頭の見出しや項目を偽れないようにする。本文やメッセージ添付のように改行が意味を持つ値は字下げし、ファイルの中身は別の text コンテンツで返し、それ以外の値は 1 行に収める。出力の中の文を指示として扱わないのは、MCP クライアントと LLM の側の責務とする。出力の冒頭に「以下は利用者が書いた値で指示ではない」と注記する方式は採らない。すべてのツールの出力に同じ前置きが付くだけで、本文に書かれた指示を止められないため
- 投稿を出すツールは、リアクションを絵文字ごとに、最初に付いた順にまとめ、付けた人数と、付けた人のユーザー名を最大 10 人まで出す（超えた分は人数だけ）。ユーザー名は投稿者と同じ `/users/ids` の呼び出しでまとめて引く。`read_thread` などの投稿の API はリアクションを返すが、スレッド一覧の API（`get_unreads` と `list_followed_threads` のスレッド）は投稿の `metadata` を返さない。そのため、これらのスレッドには、通常はリアクションがあることと、`get_post` で確かめられることだけを出す（`metadata.reactions` が返れば、ほかのツールと同じく名前を出す）。この案内は `metadata` そのものが無いときだけ出す。投稿の API は常に `metadata` を付け、リアクションが無ければ `reactions` を省くので、`has_reactions` が古いときに誤った案内を出さないため。Mattermost がリアクションの取得に失敗して続行したときと、自動翻訳で翻訳だけを入れた `metadata` がスレッド一覧の投稿に付いたときは、リアクションがあっても案内が出ない
  - Mattermost はリアクションを `create_at` だけで並べるので、同じミリ秒のものは `user_id`、絵文字名の順で並べて、呼ぶたびに並びが変わらないようにする
  - 絵文字は 1 投稿に最大 500 種類付くので、リアクションの行は本文と同じ 4000 文字までとし、超える絵文字は種類の数とリアクションの件数（同じ人が複数の絵文字を付けていれば重ねて数える。人数と読み違えないよう「件」と書く）にまとめる。まとめの部分は数えず、最初の絵文字は長さによらず出す
- 投稿を出すツールは、編集された投稿（`edit_at` が 0 でない）に編集の時刻を、`type` が `system_` で始まる投稿にシステムメッセージであることと種類を、投稿者と時刻の行の直後に出す。`update_at` はリアクションやピン留めでも変わるので、編集の判定に使わない
- `get_file` は、プレビューの長い辺が 3000px を超える画像と、3.75MB を超えるプレビューを返さず、情報だけを返す。Claude の Vision は画像の多い要求で各辺を 3000px 以下に抑えるよう勧めており、base64 で約 5MB になる 3.75MB は、クライアントの経路のうち最も小さい上限（Amazon Bedrock の 5MB）に収まるため。上限を超えた画像は会話の履歴に残り、その後の要求も失敗させうる。画像の種類は先頭のバイトで判定する。Mattermost はプレビューの `Content-Type` を、PNG でも常に `image/jpeg` にするため
- `get_file` は、幅と高さの無いファイルの先頭 40,000 バイトだけを `GET /files/{file_id}` に `Range` を付けて取り、テキストなら中身を返す。SVG のように幅と高さのあるファイルは画像として扱い、中身は返さない。Range を無視されても本文をその量で読み止め、大きなファイルの全体を読み込まない。判定は次のとおり
  - `mime_type` は使わない。Mattermost が拡張子から付けるため、Shift_JIS の CSV にも `charset=utf-8` が付き、拡張子の無いファイルには付かない
  - 先頭が `%PDF-` か、NUL を含むなら、テキストではない。PDF は、テキストを取り出すには依存ライブラリが要り、MCP の blob で返すとクライアントによって読めず会話の履歴も圧迫するので、対象にしない
  - UTF-8 として読めれば UTF-8（BOM は除く）。読めず、拡張子が `csv`、`tsv`、`txt`、`log`（大文字と小文字は区別しない）なら Shift_JIS か EUC-JP として読む。Excel が日本語の環境で書き出す CSV が Shift_JIS で、古い Unix の系統のデータに EUC-JP が残るため。拡張子で絞るのは、これらの復号が PDF などのバイナリの先頭も通してしまうため。UTF-16 は NUL を含むので対象外
  - Shift_JIS は 0xA1–0xDF を半角カナとして受け付けるので、EUC-JP も Latin-1 も Shift_JIS として読めることがあり、半角カナの Shift_JIS も EUC-JP として読めることがある。そこで、EUC-JP として読めてかな（ひらがなとカタカナ。長音や中黒など 1 区の記号は除く。半角カナの Shift_JIS の `｡` が EUC-JP ではそれらになるため）が出て、Shift_JIS では読めないか半角カナが出るなら EUC-JP、そうでなく Shift_JIS で読めれば Shift_JIS、そうでなく EUC-JP で読めれば EUC-JP とする。全体を取ったときに、一方だけが末尾の不完全な文字を除かないと読めないなら、そちらは読めないものとして扱う（かなの無い EUC-JP を Shift_JIS で読んだときや、長さが奇数の半角カナの Shift_JIS を EUC-JP で読んだときにそうなる）。推定は外れうるので、Shift_JIS か EUC-JP としたときは、推定であることと、化けていれば別の文字コードかもしれないことを書く。Latin-1（Windows-1252）は候補にしない。ほぼすべてのバイト列を受け付け、テキストでないファイルも読めてしまうため
  - 取った量の末尾で切れた途中の文字は捨てる。ファイル全体を取ったときの末尾の不完全な文字はファイル自身のものなので、除いたうえでそのことを書く（除くと何も残らなければ、空ではなく不完全な文字だけだったと書く）。全体を取ったかは、取ったバイト数が 40,000 バイトより少ないか（本文の終わりまで読めた）、ちょうどで情報の大きさと等しいかで決める。情報の大きさは実体と違うことがあるため
  - 全体を取ったときに、ASCII の後に末尾の 1 文字だけが欠けた UTF-8 は、末尾の欠けた 1 文字のバイトが Latin-1 や Shift_JIS の文字かもしれないので、UTF-8 と決めずに（拡張子が対象なら）Shift_JIS・EUC-JP を試し、UTF-8 のままでも推定であることを書く
- `get_file` が返すテキストは 10,000 文字（書記素で数える）まで。Claude Code は MCP の結果が 10,000 トークンを超えると警告し、既定の 25,000 トークンか 50,000 文字を超えると会話に入れずファイルに逃がすので、日本語でも会話に収まる量にする。40,000 バイトは、1 コードポイントが UTF-8 で最大 4 バイトであることから決めた。書記素の長い文書ではバイトの上限が先に効く。どちらで切っても、返した文字数とファイル全体のバイト数を書く（全体の大きさが分からないときは下限）。中身は、区切りの記号と取り違えないよう、情報とは別の text コンテンツで返す
- `get_file` は、中身の取得を Mattermost に断られても（プラグインの `FileWillBeDownloaded` による拒否、保存先に実体が無い）、情報に理由を添えて返す。保存先が S3 で実体が無いと、Mattermost は Go の `http.ServeContent` が作る平文の 500 を返す（ローカルの保存先では 404）。実体が無いときは再試行しても直らず、保存先の一時的な障害も同じ 500 になって区別できないので、テキストの中身の取得で、本文が `text/plain` で JSON でない 500（`http.Error` の形）を受けたら、両方の可能性を添えて情報を返す（プレビューは別の実体なので対象にしない）。JSON の 500（DB の障害など Mattermost 自身の一時的な障害。hardened mode では id が空になる）や、HTML などそれ以外の 500 は、ほかのツールと同じく再試行を案内する。ローカルの保存先の 404（`api.file.file_reader.app_error`）は、`os.Open` の失敗を区別しないので、実体が無いか保存先から読めないと添えて情報を返す。ABAC の方針による拒否（`api.file.get_file.abac_denied.app_error`）は情報の取得の時点で起きるので、情報も返さず、拒否の理由を伝える。中身の取得は Mattermost のダウンロードとして扱われ、監査ログの `getFile` とプラグインのフックの対象になる
- 件数が上限を超えうるツール（`search_posts`、`search_files`、`list_saved_posts`、`read_channel`、`read_thread`、`search_channels`、`search_users`、`list_my_channels`、`get_channel` のピン留め、`list_channel_members`、`get_unreads`、`get_mentions`、`list_followed_threads`）は、入力に `limit` と `cursor` を取り、出力に続きがあるかどうかと次の `cursor` を含める。続きがあるのに黙って切り捨てない。本文を長さの上限で切った場合も、切ったことを出力に明示する
- `read_channel` は既定で新しい順、`read_thread` は古い順に返す。`read_thread` の親投稿は最初のページにだけ含める
- `read_channel` の `from: "unread"` は、未読の先頭から古い順に返す。未読を読み進める用途なので古い順にする
  - CRT が有効ならルート投稿だけを返し、`get_unreads` の数え方にそろえる。CRT の判定は続きのカーソルに入れ、ページの途中で絞り込みが変わらないようにする
  - 続きのカーソルには `channel_id` も入れ、`get_channel` と同じく別のチャンネルのカーソルを拒む
  - 既読の位置が 0（参加してから一度も開いていないチャンネルや、相手から届いた DM）のときは、Mattermost が未読の先頭を返さず、先頭までさかのぼる件数にも上限が無いので、新しい順に切り替えてそう書く
  - 参加していない公開チャンネルには未読の位置が無いので、入力の誤りにする
  - 最初のページは、Mattermost の未読の API が返す未読の先頭の直前の投稿（`prev_post_id`）を起点に `after` で読み直す。未読の API は未読の先頭の投稿より厳密に後を返し、未読の先頭と同じミリ秒の別の投稿を返さないため。直前の投稿が無い（未読の先頭がチャンネルで最も古い投稿、CRT ならルート）ときと、読み直しが 0 件のとき（直前の投稿が合間に完全削除された）は、未読の API のページをそのまま使うので、同じミリ秒の投稿は抜けうる
- `read_channel` の `since`（含む）と `until`（含まない、省くと最新まで）は、その範囲の投稿を古い順に返し、CRT が有効でも返信を含める。期間に何が話されたかを読む用途で、ルート投稿に絞る理由（`get_unreads` の数え方との一致）が無いため。時刻の形と解釈は `schedule_message` の `at` と同じ（タイムゾーンが無ければ JST）。`search_posts` で代えないのは、検索がメッセージ添付の中身に当たらないため
  - 作成時刻から投稿を引く REST は無く、`since=` の API は更新時刻で並びを指定せずに 1000 件までしか返さない。そこで `page` と `per_page=200`（新しい順の位置）で、`since` より前の投稿を含む最も新しいページを、ページ番号を倍に広げてから二分探索で探す。見つけた投稿のうち最も新しいものを起点に `after` で前へ読む。起点が `since` より前でありさえすれば、探す途中の投稿の増減で起点がずれても、余分に読む件数が増えるだけで範囲の投稿は抜けない。チャンネルの最初の投稿が `since` 以降なら、最も古いページから出す
  - 起点を探す途中で投稿が消え、最後の空でないページの後ろが空に見えると、それより古い範囲の投稿が出ないことがある。チャンネルの件数が 200 の倍数の境目にあり、探索のあいだに削除が重なったときだけ起き、抜けるのは最も古い側の数件なので受け入れる。`OFFSET` で読むので深い位置ほど Mattermost のデータベースの負荷が増えるが、呼び出しは新しい方から N 件目に始まりがあるとき約 2log2(N/200) 回になる
  - カーソルには範囲を入れ、`until` を省いたときは続きのページでもページの合間に届いた投稿を出す。MCP サーバーの時計で「呼んだ時点」を決めると、Mattermost の時計との差で直近の投稿が落ちるため
- `read_channel` は、どの読み方でも Mattermost に `skipFetchThreads` を渡す。渡さないと、取得した投稿のスレッドの返信をすべて追加で引くため
- `read_channel` のカーソル（Mattermost の `before` と `after`）は `create_at` の厳密な比較で絞り込み、同じミリ秒どうしの並びも決まらない。そこで、取った limit+1 件の境目で、出す最後の投稿と次の投稿が同じミリ秒なら、そのミリ秒の投稿を次のページに回す（そのページの件数は limit より少なくなる）。日時の範囲の読みで 1 回の呼び出しの中で読み進めるときと、起点を最も古いオフセットのページから取るときも同じにする。取った件がすべて同じミリ秒のとき、または最も古いページの件がすべて同じミリ秒でそのミリ秒の投稿が隣のページにまたがるときだけは、最後の投稿を起点にするので抜けうる。1 回の呼び出しの中で読み進めるときは limit+2 件ずつ取り、末尾のミリ秒を外しても 1 回で limit+1 件がそろうようにする。表示済みの id はカーソルに持たない
  - カーソルを渡したページが 0 件なら、起点か続きの投稿の削除か、同じミリ秒の投稿の多さで続きを取りこぼした可能性があると書き、読み直し方を添える。続きがあるときだけカーソルを出すので、0 件になるのは削除か上の限界のときに限られる。起点が残っているかは確かめない（`include_deleted` を使えない一般の権限では、`GET /posts/{id}` はソフト削除でも完全削除でも 404 で、見分けられない）。読み直し方は、新しい順なら cursor を渡さずに最新から、古い順なら前のページの最後の投稿の時刻を since に渡す（出力の時刻は秒までなので、新しい順に until を案内すると同じ秒の投稿を取りこぼすため）
- `list_my_channels` の件数は既定 50、最大 200 とする。並びは `last_post_at` の新しい順（同じなら `channel_id` の順）で、ページの合間に投稿があると順序が変わる。そこで 2 ページ目以降は、最初のページの時点より後に更新されたチャンネルを本体から除き、前のページの後に更新されたチャンネルを本体の前の節にまとめて出す。こうすると、ページの合間に投稿があって前へ動いたチャンネルも抜けない。ただし、ページの合間に参加したチャンネルのように、更新時刻が進まないまま前の位置に入った行は出ないことがある。この節がページに収まらないときは、`next_cursor` を出さずに最初のページから取り直すよう促す
- `get_channel` のピン留めの件数は既定 10、最大 50 とする。Mattermost の `/channels/{id}/pinned` には件数の上限もページングもないため、全件を取って `create_at` の新しい順（同じなら post_id の順）に並べ、最後に出した投稿の `create_at` と post_id をカーソルに入れる。カーソルを渡されたときは、ピン留めの続きだけを出す。ページの合間にカーソルより古い投稿がピン留めされると、その投稿は出ない
- `get_channel` は、チャンネルを取る API の 403 と 404 を、権限がない旨とチャンネルが見つからない旨の文言に変える。参加していない公開チャンネルでは Mattermost がメンバー数を返さない（`/stats` が 403）ため、メンバー数だけを取得できない旨にして、ほかの項目は返す。403 は一時的な障害でも返るので、原因を参加していないことに言い切らない
- `get_user` のタイムゾーンは、自動設定なら自動判定の値を使い、自動か手動かを添える。空か不正な値なら未設定とし、現地時刻は出さない。在席状況が取り込み中で終了時刻があるときは、その時刻を UTC と JST で添える。在席状況の取得で Mattermost がエラーを返したら、在席状況だけを取得できない旨にしてプロフィールは返す
- `get_unreads` の件数は既定 30、最大 100 とし、チャンネルとスレッドを合わせて数える。CRT が利用者に効いているかは、サーバー設定 `CollapsedThreads` と、`default_on`／`default_off` のときだけ利用者の設定で決め、出力の先頭に書く。CRT が有効ならチャンネルの未読はルート投稿だけで数え、返信は未読のスレッドとして出す。通知を「メンションのみ」にしたチャンネルは、メンションがあるときだけ出す。スレッドの一覧はアーカイブ済みチャンネルのスレッドも返すが、チャンネルの節と基準をそろえるため、参加しているチャンネルの一覧（アーカイブ済みを含まない）に無いチャンネルのスレッドは除き、件数にも数えない。並びはチャンネル（メンションのあるものが先、その中で更新の新しい順）の後にスレッド（最終返信の新しい順）で、ページ送りは `list_my_channels` と同じく、前のページの後に更新された行を本体の前の節に出す。ただし、投稿なしで未読やメンションの有無が変わった行（「未読にする」の操作など）や、ページの合間に参加したチャンネルは、出ないことがある。チャンネルの更新時刻は、CRT が有効なら最終のルート投稿、無効なら最終投稿とする。ページの合間に CRT の判定が変わると更新時刻の定義が入れ替わるため、カーソルに判定を入れ、食い違えば最初のページから取り直すよう促す。スレッドの一覧は `before` で 50 件ずつ追う。`before` は最終返信の時刻の厳密な比較なので、次の `before` は境目より最終返信の新しいスレッドのうち最も古いものにし、境目の時刻のスレッドを取り直して重複を除く。境目と同じ時刻のスレッドが 51 件以上あるときや、取得の合間に起点のスレッドが完全削除されたり返信が削除されて最終返信の時刻が下がったりしたときは、続きが抜けうる。そこで、チームごとに取得したスレッドの数（重複を除き、表示の絞り込みの前）を、応答の `total_unread_threads` の最大値と比べ、足りなければそう書く（削除や既読は total を下げる向きにしか動かないので最大値を使う）。チームごとに 4 回の取得で打ち切り、打ち切ったうえで total に足りないときだけそう書いて total を添える。取り切っていれば打ち切りとは書かない。スレッドの一覧が 4xx を返したら、チャンネルの未読だけを返し、スレッドを取得できなかったことを書く
- `get_mentions` の件数は既定 20、最大 50 とする。Web の「最近のメンション」と同じ語で OR 検索し、database 検索が `@` の無い語にも当たるため、Mattermost のサーバーと同じ規則で本文を照合して、メンションでない投稿を落とす。Mattermost の database 検索は 100 件までしか返さず、`page > 0` では何も返さないので、100 件に達したら最も古い日を次の回に回し、`before:` を 1 日ずつ戻して検索し直す。1 日だけで 100 件を超えた日は、新しい 100 件だけを出し、そのことを書く
- `get_mentions` の `unread_only` は、Mattermost が未読のメンションを数えている場所（以下「候補」）の、既読の位置より後の投稿だけを出す。候補は、CRT が無効なら `mention_count` のあるチャンネル（位置はチャンネルの `last_viewed_at`）、有効ならルート投稿は `mention_count_root` のあるチャンネル、返信は未読のスレッドの一覧のうち `unread_mentions` のあるスレッド（位置はスレッドの `last_viewed_at`）。位置だけで判定しないのは、編集でメンションを足した投稿のように Mattermost が数えていない投稿が、ほかに候補があるかどうかで出たり出なかったりするため。フォローしていないスレッドの返信は Mattermost も数えないので出さない。自分の投稿は除くが、自分が作った Webhook の投稿は除かない。Mattermost は Webhook の投稿なら、作った本人へのメンションも数えるため
  - 位置と同じミリ秒の投稿は既読として扱う（画面の未読と同じ）。Mattermost のメンションの数え直しは位置「以降」を数えるので、その 1 ミリ秒だけ数が合わないことがある。`get_mentions` はメッセージ添付の中と `@channel`・`@all`・`@here` を数えず、DM とグループ DM では Mattermost がすべての投稿をメンションに数えるので、`get_unreads` のメンション数とも合わないことがある。そのことをツールの説明に書く
  - 候補が無ければ検索しない。あれば、候補の位置の最小値の日より前を検索しない（`after:` を足す）。未読のメンションより古い履歴を 100 件ずつ遡り続けず、探し終えたら続きなしで終わるため。位置が 0 の候補は、チャンネルなら作成時刻、スレッドならルート投稿の時刻を下限にする。一度も開いていないチャンネルや、相手から届いて開いていない DM、返信で初めてメンションされたスレッドは位置が 0 だが、その中の投稿はチャンネルやルート投稿より古くないため。DM とグループ DM は未読の投稿があれば必ず候補になるので、古い未読の DM が残っていると、下限はその DM の位置（開いていなければ作成時刻）まで遡る
  - アーカイブ済みのチャンネルとそのスレッドは候補にしない。検索がその投稿を返さず、古い位置が下限を遡らせるだけのため
  - スレッドの一覧は `get_unreads` と同じく、チームごとに 50 件ずつ 4 回の取得までにし、打ち切ったときや取り切れなかったときは、`get_unreads` と同じ注記を出す。一覧を取れなければ、返信の既読を判定できないので、ツールのエラーにする
- フォロー中のスレッドのツール（`list_followed_threads`、`follow_thread`、`unfollow_thread`）は、CRT が利用者に効いていなければ（判定は `get_unreads` と同じ）、その判定のほかは Mattermost を呼ばずに断る。CRT が無効な画面にはスレッドの一覧もフォローの表示も無く、返信の通知もフォローではなく利用者全体の設定で決まるため、フォローを変えても「通知を止めて」に応えたことにならない
- `list_followed_threads` の件数は既定 20、最大 50 とする。所属するチームごとに Mattermost のスレッドの一覧を `per_page=200` で 1 回だけ取り、DM とグループ DM は最初のチームからだけ取る。`before` でページを追わない。呼ばれるたびに全チームの一覧を取り直して最終返信の順に並べ直すので、ページを追うと 200 件を超えるチームでは呼び出しのたびにチームごとの取得が重なるため。`before` の等号を含まない絞り込みは、1 ページ全体が同じ最終返信の時刻のときを除き、`get_unreads` と同じく境目の時刻のスレッドを取り直せば避けられるので、理由にしない。`total` が取れた件数より多いチームは、止めた時刻と `total` を書く。並びは最終返信の新しい順で、ページ送りは `get_unreads` と同じく、前のページの後に返信があったスレッドを本体の前の節に出す。アーカイブ済みのチャンネルのスレッドは除かず、`channel_id` だけを出す。フォローは外せるので、整理に使えるため。返信がまだないルート投稿は、フォローしていても Mattermost が最初の返信まで返さない
- `follow_thread` と `unfollow_thread` は、スレッド内のどの投稿の post_id も受け取り、ルート投稿に直してから Mattermost に渡す。Mattermost は返信の ID でも成功を返し、一覧にも通知にも効かないフォローが残るため。チームは、チャンネルのチーム（DM とグループ DM は所属する最初のチーム）とする。フォローの API はチームを問わない
  - `follow_thread` は、参加していないチャンネルのスレッドを断る。Mattermost は成功を返すが、一覧にも通知にも出ないため。すでにフォロー中なら、フォローの API を呼ばない。Mattermost はフォローのたびにスレッドを既読にするので、呼び直すと利用者が読んでいない返信まで既読になるため。フォロー中かはスレッドの状態の取得で見るが、返信の無いルート投稿は、Mattermost が最初の返信までスレッドの状態を作らず、フォロー中でも 404 になる。そこで返信の無いルート投稿に限り、スレッドの取得（`GET /posts/{id}/thread?collapsedThreads=true`）の `is_following` で見る。返信のあるスレッドは状態の取得で判定できるので、呼び出しを増やさない。フォローしていなかったスレッドは、フォローした時点までの返信が既読になる。その前の既読の位置は API で読めないので、戻さない
  - `unfollow_thread` は、事前の確かめをせずに外す。外しても既読は変わらない。外した後も、そのスレッドでメンションされるか自分が返信すると、Mattermost は再びフォローする。そのことを出力に書く
  - DM とグループ DM のスレッドでは、Mattermost は相手の返信をすべて本人へのメンションとして扱うので、外しても相手の返信 1 件で再びフォローされ、通知も届く。外せば次の返信まで `list_followed_threads` から消えるので断らずに外し、通知は止まらないことを出力に書く
- `search_users` と `list_channel_members` には在席状況を加えない。ユーザーごとに API の呼び出しが増えるうえ、一覧から相手を選んだあとに `get_user` を呼べば足りるため
- `search_files` は、`search_posts` と同じく全チームの検索 API を 1 回呼び、日付を JST で解釈し、100 件の中をカーソルで切り出す。全チームの API は `in:` のチャンネル名をチームなしで引くため、チームのチャンネル名では黙って 0 件になり、`in:@ユーザー名` では DM を作る。そこで、`in:` と `channel:`（除外の `-` 付きを含む）の値を、Mattermost に渡す前に channel_id に置き換える。同じ名前のチャンネルが複数のチームにあればすべてを対象にしてその旨を書き、DM は既存のものだけを引く（DM が無ければ、`in:` はエラーにし、`-in:` は条件を落とす）。チームごとの API を順に呼ぶ方式は、チームの数だけ呼び出しが増え、DM の作成も防げないため採らない。名前は全文検索の語の単位で当たり、日本語の名前は空白で区切られないため、名前全体か先頭からの前方一致（`*`）でしか当たらない。このことをツールの説明に書く。ファイルの検索がサーバー設定で無効なときは、その旨と `search_posts` で探せることを返す。`in:` の解決やその後の検索語の組み立てに失敗したときは、検索語 `*` だけで問い合わせて無効かどうかを確かめてから答える。Mattermost はチャンネル名の変換より前に設定を見て、`*` だけなら何も検索しないため。無効と分かるのが解決の後になるのは、設定がクライアント向けの設定（`/config/client`）に出ないため
- `list_saved_posts` の件数は既定 20、最大 50 とする。Mattermost の保存した投稿の API は `page` を飛ばす件数として扱い、ページの合間に保存や解除があると位置がずれる。また、作成時刻だけで並べるので、同じ時刻の投稿どうしの順は問い合わせごとに変わりうる。そこで、最初は件数 + 21 件、以降は 200 件ずつ、前の問い合わせの末尾 20 件と重ねて、先頭から 1000 件まで読む。重ねた 20 件は、問い合わせの境目にまたがる同じ時刻の投稿と、1 回の呼び出しの中での解除による位置のずれとで分け合う。同じ時刻の投稿が 21 件を超えて境目にまたがるか、解除によるずれと合わせて重なりを使い切ると、まれに抜けうる。最初の小さい問い合わせが空のときは、すべてが読めない投稿だった場合に備えて 200 件で読み直す。読んだ投稿は新しい順（同じなら post_id の順）に並べ、最後に出した投稿の `create_at` と post_id をカーソルに入れる。ページが足りた時点で読むのを止め、1000 件で止めたときはその旨を書く。よく使う最初のページで Mattermost に 200 件分のメタデータを作らせないよう、最初の問い合わせは小さくする。カーソルの続きでも先頭から読み直すが、位置のずれを検出して巻き戻す仕組みは利用の頻度に見合わないため作らない
- `list_channel_members` は、メンバー数だけでは、チャンネルに誰がいて誰に聞けばよいかに答えられないため、メンバーの一覧を読めるようにする。`get_channel` のオプションにせず、独立したツールにする。`get_channel` はピン留めをカーソルで送っており、1 つのカーソルで 2 つの一覧を送れないため。メンバーが数百人いるチャンネルで `get_channel` の出力を大きくしないためでもある。件数は既定 50、最大 200 とし、Mattermost のユーザー名の順のページをそのまま送る。ページの合間にメンバーが増減すると抜けや重複が出うるが、ユーザー名の順は投稿のようには頻繁に変わらないため受け入れる。参加していないチャンネルでは、公開チャンネルでも Mattermost がメンバーを返さないため、その旨を返す。Mattermost は読む権限（通常はチャンネルのメンバーであること）で判定し、一時的な障害や、ごくまれにチャンネルを取った直後の削除でも同じ 403 を返すので、文言で原因を言い切らず、参加しているはずなら待って再試行するよう添える
- カーソルには件数と、`list_my_channels` の種類の絞り込みも入れ、カーソルを渡されたときは引数の側を無視する。ページの途中で母集団が変わらないようにするため

### 既読にする

`mark_as_read` は、読み取り系のツールのオプションにせず、独立した書き込み系のツールにする。読み取りに副作用を混ぜると、`readOnlyHint` を付けられなくなるため。呼んだ時点で既読にすると AI が読んでいない投稿まで既読になるので、項目ごとに、読んだ投稿のうち最も新しいもの（`last_post_id`）を受け取る。チャンネルではそれより前の投稿をすべて既読にするので、ツールの説明で、未読を片付けるときは `read_channel` の `from: "unread"` で未読を最後まで読んでから渡すよう求める。省いたときは、呼んだ時点までのすべてを既読にする。

- チャンネル: 未読もメンションも無ければ（CRT が有効ならルート投稿で数える）「すでに既読」とする。利用者がルート投稿をするとサーバーがチャンネルを既読にするので、「読む → 返信する → 既読にする」の流れでは「すでに既読」と返る（webhook、Bot の投稿と、CRT が有効なときのスレッドへの返信では、サーバーは既読にしない）
  - 参加していないチャンネルは入力の誤りにする。`mark_read` は参加していなくても成功を返すため
  - `last_post_id` より後に自分以外の投稿があれば、既読にしない。自分が作った webhook と Bot の投稿は自分の投稿に含めず、Mattermost が未読に数えない参加・退出の通知は数えない
  - `last_post_id` より後の 200 件がすべて自分の投稿（参加・退出の通知を含む）なら、その先を確かめられないので既読にしない
  - 既読にするのは `POST /channels/members/{user_id}/mark_read` で、チャンネルごとに確かめた直後に呼ぶ。全チャンネルを確かめてからまとめて 1 回で呼ぶと、確かめてから既読にするまでの間がツールの実行時間全体（20 件で十数秒）に延び、その間に届いた投稿が既読になるため
  - 同じチャンネルを 2 回指定した項目は、入力の誤りにする。片方が断られ、もう片方が既読にすると、結果の行が食い違うため
  - チャンネルの `last_post_at` とは比べない。編集やピン留めで進み、削除で戻らないので、新しい投稿が無くても断り続ける
  - `/channels/members/{user_id}/view` は使わない。利用者の開いているチャンネルを切り替え、通知に影響する
  - `set_unread` で位置を指定しない。既読を後ろへ戻し、CRT が無効な利用者に返信を指定するとスレッドをフォローさせる
  - 確かめてから既読にするまでの間に届いた投稿は既読になる。`mark_read` には位置を指定する手段が無いため。`last_post_id` と同じミリ秒の他人の投稿も、`create_at` の大小で絞るので見落とす
  - 前提（「Mattermost の台数」の行）を外れ、読み取りレプリカを使う構成（ライセンスが要る）では、この間がレプリカの遅れの分だけ延びる。後続の投稿の確かめはレプリカを、`mark_read` はマスターの最終投稿の時刻を読むため
- スレッド: `last_post_id` の時刻（省いたらスレッドの最終返信の時刻）の 1 ミリ秒後を書く位置にする。Mattermost は未読の返信を位置より後で、メンションを位置以降で数えるので、投稿の時刻そのものにすると、その投稿のメンションが残るため。その代わり、`last_post_id` と同じミリ秒と、その 1 ミリ秒後の他人の返信は、読まずに既読になる。今の位置より前には書かない。スレッドの API は位置を後ろへも動かすため。CRT が無効な利用者では、画面にスレッドの既読が出ないので既読にせず、チャンネルを既読にするよう返す
  - 書いた位置ちょうどの返信は、未読の返信には数えられないがメンションには数えられる。書いた後の応答で未読の返信が無いのにメンションが残れば、そのメンションは位置ちょうどの返信のものなので、もう 1 ミリ秒先を書く。位置より後の返信は無いので、これで読まずに既読になる返信は増えない。今の位置が書く位置以降で、未読の返信が無いのにメンションが残るときも、同じ理由で 1 ミリ秒先を書く
  - 今の位置が書く位置以降で、メンションも残っていなければ書かない
  - 今の位置が書く位置以降で、今の位置より後に未読の返信があるときは、メンションが残っていても書かない。同じ位置を書いても数は変わらず、後の返信を利用者が読めば Mattermost が数え直すため
  - 位置ちょうどの返信のメンションを消すための書き込み（もう 1 ミリ秒先、または今の位置が書く位置以降のときの 1 ミリ秒先）だけが失敗したときは、項目を既読として結果に書き、メンションを消せなかったことと、`last_post_id` を付けてこのスレッドを再実行すれば消せることがあることを添える。今の位置はすでに書く位置以降にあるため。`last_post_id` を省いた呼び出しのそのままの再実行は勧めない（合間に届いた返信まで既読にするため）。再ログイン・429・Mattermost の停止は、ほかの書き込みと同じくツール全体のエラーにする
  - 状態の取得から書き込みまでの間に利用者が先まで読むと、書いた位置まで戻る。スレッドの API に条件付きの書き込みが無いため避けられない。前提（「Mattermost の台数」の行）を外れ、読み取りレプリカを使う構成では、状態の取得とメンションの数え直しもレプリカを読むので、この間がレプリカの遅れの分だけ延び、遅れの間に届いたメンションが数え直しから漏れて消えうる
  - スレッドの状態が無い（フォローしていないか、返信が無いか、チャンネルに参加していない）ときは既読にしない。フォローしていなければ `follow_thread` を案内する。参加していない公開チャンネルのスレッドは、投稿は読めるのでここまで進むが、`follow_thread` が断るので案内しない。参加は状態が無く返信のあるスレッドでだけ確かめ、既読にできる経路の呼び出しは増やさない。返信の無いルート投稿は、フォローしても最初の返信まで状態ができないので案内しない
- `last_post_id` を省いた項目は、結果の行に「呼んだ時点まで」を既読にしたと書く。本人の求めでない既読（投稿の本文に仕込まれた指示に従った場合など）に、後から気づけるようにするため
- 1 件ごとの入力の誤りと Mattermost のエラーは、その項目の結果として書き、ほかの項目は続ける。既読にした項目もすでに既読の項目も無いときだけ、ツールのエラーにする。再ログイン、429、Mattermost の停止はツール全体のエラーにする。`last_post_id` を付けた呼び出しは冪等なので、失敗したらそのまま再実行してよい
- 注釈は `destructiveHint: false`（画面の「未読にする」で戻せる）、`idempotentHint: false` とする。`last_post_id` を省いた呼び出しは、再実行の合間に届いた投稿まで既読を進めるため
- `channels` と `threads` の要素の知らないキーは、引数の検証の段階で断り、どの項目も既読にしない（項目ごとの結果にはしない）。zod の `z.object` の既定のように捨てると、書き誤った `last_post_id` が無いものとして扱われ、最新まで既読にする。戻すには利用者が画面で「未読にする」を項目ごとに操作するしかないため

### `send_message` の二重投稿の防止

Mattermost が投稿を受け付けた後で MCP クライアントへの応答が切れると、クライアントや LLM は成否が分からないまま同じ呼び出しをやり直し、同じ投稿が 2 回できる。
やり直すのは LLM なので、LLM に重複防止のキーを生成させても、やり直しのときに同じキーを使う保証はない。
そこで MCP サーバー側で、同じ利用者が同じ投稿先（チャンネルと `root_id`）へ同じ本文を短い時間（10 分程度）のうちに投稿しようとしたら、同じ投稿のやり直しとみなす。

Mattermost v11.7.8 には、投稿の `pending_post_id` が同じ要求を 30 秒間まとめる重複排除がある（[`post.go` の `deduplicateCreatePost`](https://github.com/mattermost/mattermost/blob/v11.7.8/server/channels/app/post.go)。公開 API の文書には書かれていない）。
これだけでは 30 秒を過ぎたやり直しを防げないため、MCP サーバー側の記録と組み合わせる。

- 利用者、投稿先、本文のハッシュの組に一意制約を付けた記録を SQLite に置く。記録には、そのとき生成した `pending_post_id` と状態（投稿中、成功）を持たせる
- 投稿の前に記録を作る。同じ組の記録が既にあれば、新しい記録は作らない。Mattermost へは常に記録の `pending_post_id` を付けて投稿する
- 成功したら投稿 ID を記録する。Mattermost が明確に拒否したら（`4xx`）記録を消す
- 同じ組の「成功」の記録があれば、投稿せずに前回の投稿 ID とパーマリンクを返し、やり直しとして投稿しなかったことを出力に明示する
- 同じ組の「投稿中」の記録があり、作られてから Mattermost API のタイムアウト（数十秒）が過ぎていなければ、先の要求がまだ処理中とみなして投稿せず、「同じ投稿を処理中なので少し待って結果を確かめる」旨のエラーを返す
- タイムアウトを過ぎた「投稿中」の記録は、先の要求の結果が分からないまま終わったものとみなす。やり直す要求は、まず記録の更新時刻を原子的に書き換えて再試行の権利を取る（同時に来た要求のうち 1 つだけが取れ、取れなかった要求は前項と同じく処理中として扱う）。権利を取った要求は、そのチャンネル（と `root_id`）で記録の作成時刻以降にその利用者が投稿した、本文が完全に一致する投稿を Mattermost から探し、見つかればそれを成功として記録して返す。見つからなければ同じ `pending_post_id` で投稿する
  - `pending_post_id` は DB に保存されないため、探す条件には使えない。探すときは全文検索 API ではなく、時刻で絞ってチャンネルの投稿を取得する API（`GET /api/v4/channels/{id}/posts?since=`）を使う。全文検索の分かち書きやインデックスの遅れで、一致する投稿を見落とさないため
  - 「投稿中」を結果不明とみなすまでの猶予は、MCP 側の API タイムアウトに余裕を足した値にする。それでも Mattermost の処理が猶予より遅れて完了した場合の二重投稿は防げず、既知の限界とする
- 同じ本文を意図して繰り返し投稿したい場合のため、`send_message` に重複防止を外す引数（`allow_duplicate`）を設ける
- 添付ファイルがあるときは、本文に加えて各ファイルの名前と中身の SHA-256 を順序どおりに含めたもの（`[本文, [[名前, SHA-256], ...]]` の JSON）のハッシュで判定する。区切り文字でつなぐと、本文と名前と中身の境目をずらした別の入力が同じハッシュになるため。やり直しで既存の投稿を探すときは、本文に加えて `file_ids` の件数の一致も条件にする
- 添付のアップロードは、猶予（30 秒）を超えうる。その間に来たやり直しが再試行の権利を取ると、2 つの要求が両方投稿しかねない。そこで投稿の直前に、記録の更新時刻が自分の取ったときのままであることを条件に、更新時刻を書き換えて権利を取り直す。取り直せなければ投稿せず、処理中として返す
- `file_ids` があるときは、`[本文, [[名前, SHA-256], ...], [file_id, ...]]` の JSON のハッシュで判定する。`file_ids` が無いときのハッシュは変えない。更新の前に取った記録が、更新の後のやり直しと一致しなくなるため。既存の投稿を探すときの件数は、`files` と `file_ids` の合計とし、渡した `file_ids` がすべて付いていることも条件にする。同じ本文と件数で別のファイルを付けた投稿を取り違えると、投稿していないファイルを投稿に使ったと記録するため
- 自動テストで、Mattermost が投稿を受け付けた後に応答を切る障害、同じ投稿の同時要求、30 秒を過ぎてからのやり直しを起こし、二重投稿にならないことを確かめる。`pending_post_id` の重複排除は公開文書にない挙動なので、Mattermost を更新するときにもこのテストを通す

### `send_message` の後の下書きの削除

Mattermost のサーバーは、投稿を作っても対応する下書きを消さない（下書きを消すのは webapp の送信の処理と、投稿の削除だけ）。
そのため、`save_draft` で保存した下書きを `send_message` で送ると下書きが残り、本人がそれをそのまま送ると同じ投稿が 2 回になる。
そこで `send_message` は、投稿の後に、同じ投稿先（チャンネルと `root_id`）にある本文の完全に一致する下書きを消す。本文の違う下書きは、本人の書きかけかもしれないので消さない。

- 下書きは `save_draft` と同じく、投稿先のチームの一覧（DM とグループ DM は所属する最初のチーム）から探す。所属するチームが無ければ何もしない。下書きはチームごとに一覧されるので、画面にも出ないため
- 実際に投稿したときに加えて、やり直しとみなして投稿しなかったときにも消す。前の試みの削除が失敗していても、やり直しで消せるようにするため。「処理中」のときは投稿の成否が分からないので消さない
- 添付の付いた下書きは消さず、出力でそのことを伝える。消すと本人が画面で付けたファイルが失われるため
- 本人が下書きの同期を切っていたら消さず、出力でそのことを伝える。削除すると WebSocket の `draft_deleted` が届き、webapp は同期の設定を見ずにストアのそのチャンネルの下書きを空にするので、ブラウザの中にしか無い本文の違う書きかけを消してしまうため。同期の確認は、一致する下書きがあったときだけ行う。モバイルアプリは下書きの WebSocket イベントを扱わない（mattermost-mobile の `app/constants/websocket.ts` に無い）
- 優先度の付いた下書きは消し、優先度がこの投稿に付いていないことを出力に添える
- burn-on-read の付いた下書き（`type` が `burn_on_read`。webapp が付けるのは Enterprise Advanced 以上で機能を入れたときだけ）も同じく消し、この投稿に付いておらず消えずに残ることを出力に添える。残すと本人が画面から送って同じ投稿が 2 回になるため
- `save_draft` の「一覧 → 保存」と削除の「一覧 → 削除」は、MCP サーバーの中で投稿先（利用者、チャンネル、`root_id` の組）ごとに 1 本ずつ直列にする。削除が一覧を読んだ後に `save_draft` が保存した下書きを、削除が消さないようにするため。競合は 1 つの下書きの一覧と書き込みの間でしか起きないので、別の投稿先への処理は待たせない。ロックはプロセスの中の投稿先ごとの順番待ちで、前の処理が失敗しても次に進む。`save_draft` の投稿先の解決はロックの外で行う（1 回の呼び出しが数十秒かかりうるので、後ろの削除が毎回期限切れになるのを避ける）。削除はロックを待つ時間も 5 秒の期限に含め、期限が来たら待つのをやめて失敗として伝える。順番の枠は前の処理が終わるまで残し、順番が来たら何もせずに放す（すぐ放すと、後ろの処理が前の処理と重なって動く）
- 下書きの確認や削除の失敗（Mattermost のエラー、レート制限、通信の失敗、期限切れ）は投稿の成功を損なわない。投稿の結果は成功のまま、下書きが残っているかもしれないことを出力に書き、ログに残す。サーバーで下書きの同期が無効（`501`）なら下書きは存在しえないので、何も書かない。途中で Mattermost の再ログインが必要になったときは、そのことと再接続を出力で伝える。クライアントが要求を取り消したときは、出力にもログにも書かない（取り消しは削除の失敗ではなく、応答を受け取る相手もいないため）。ログには投稿先の `channel_id` を入れる
- 削除の処理全体を 5 秒で打ち切り、残りの呼び出しも止める。呼び出し 1 回の期限は数十秒で、順に最大 4 回呼ぶため、待つと投稿の成功の応答が遅れ、クライアントの時間切れで失敗に見えるため。待つのをやめるだけだと、応答を返した後に削除が届き、そのあいだに本人が書き直した下書きを消しうる。ただし、送り終えた DELETE は Mattermost が最後まで処理するので取り消せない
- 予約投稿（`schedule_message`）の投稿では下書きを消さない。`send_message` は、入力欄に本文が残ること、優先度と burn-on-read が付いていないこと、削除の失敗を出力で伝えることで削除を安全にしているが、予約は時刻が来たら巡回が投稿するので、それを伝える相手がいない。また、投稿の時刻は本人の操作と関係が無いので、本人がちょうどそのチャンネルで書いていれば、下の競合の窓に当たりやすい。同じ本文の下書きは残り、本人がそれを送ると同じ投稿が 2 回になる
- 注釈の `destructiveHint` は `false` のままにする。消すのは送った本文と同じ下書きだけで、本文の違う書きかけや添付を失いうるのは、下の競合の窓の中だけのため。優先度と burn-on-read は失うが、出力で伝える
- 既知の限界
  - 下書きの一覧を読んでから消すまでのあいだに本人が画面で書き直して保存すると、その書きかけを消しうる。Mattermost に条件付きの削除は無い。webapp はチャンネルを離れるときに保存するので、この窓は狭い
  - 送り終えた DELETE か `POST /drafts` が期限か取り消しで打ち切られると、ロックは放されるが Mattermost では処理が続く。その後の `save_draft` の保存や削除の一覧・DELETE と処理の順序が決まらず、新しい下書きが消えうる
  - 削除は、DELETE を送る直前に 5 秒の期限の残りが 1 秒未満なら送らずに、確かめられなかったとして伝える。DELETE の途中で期限が来る窓を狭めるため。ただし 1 秒は目安で、遅い Mattermost では途中で期限が来うる。DELETE が 401 を受けてトークンを更新した後の送り直しは、この検査を通らない
  - 本人がそのチャンネル（スレッド）を画面で開いていると、下書きを消しても開いている入力欄に本文が残る。webapp のエディタは、チャンネルかスレッドを切り替えるまでストアを読み直さないため。消したときの出力で、開いている場合は入力欄の本文を送らずに消すよう添える

### ファイルを添付した投稿

- `send_message` の `files` の各要素は、名前と、`content_text`（UTF-8 のテキストとしてそのまま添付する）か `content_base64`（小さなバイナリ）のどちらか一方である。SVG、CSV、Markdown、コードなど、LLM が本文として書ける形式は `content_text` で渡す
- 件数は 1〜5 件、名前は 1〜100 文字で `/`、`\`、制御文字を含まない。中身の合計（base64 は解いた後）は 128KiB まで。MCP サーバーとリバースプロキシは MCP のパスの要求を 1MB までに制限しており、テキストが JSON のエスケープで最大 6 倍に膨らんでも、最長の本文と合わせて収まる値にした。上限を上げるには両方の設定を変える
- `content_base64` は、標準の base64 で、長さが 4 の倍数で、解いて符号化し直すと元に戻るものだけを受け付ける。data URL の接頭辞や改行が付いたまま解くと、壊れた中身を黙って添付するため
- 各ファイルを `POST /files?channel_id=&filename=` で、中身をそのまま本文にして逐次アップロードし、返った `file_ids` を付けて投稿する。アップロードした後で投稿の前に失敗すると、そのファイルは消せずに残る（Mattermost にファイルを消す API も、使われなかったファイルを消すジョブも無い）。そこで、投稿先の解決と重複防止の記録を含め、すべての検査をアップロードの前に済ませる
- アップロードを Mattermost が明確に断ったら（`4xx`、レート制限、送る前の失敗）、重複防止の記録を消す。投稿はされていないため。画素数や大きさで断られたときは、ファイル名を添えて利用者向けの文言にする
- Mattermost は、使えない `file_ids` をエラーにせず黙って外す。投稿の応答の `file_ids` の件数がアップロードした件数と違えば、投稿はできているので、外れたことを出力に明示する
- 画像の種類や大きさの検査は Mattermost に任せる
- 既知の限界
  - ツールの引数はモデルの出力のトークンなので、現実に送れるバイナリは数十 KB までで、大きな画像は添付できない
  - 投稿の前に失敗したときや、やり直しで別の要求が先に投稿したときに、アップロードしたファイルが投稿に使われずに Mattermost に残る。そのチャンネルを読める人は `file_id` が分かれば取得できる
  - 前の投稿で Mattermost がファイルを黙って外していると、やり直しで既存の投稿を探すときに `file_ids` の件数が一致せず、二重投稿になりうる

### 利用者の PC にあるファイルの添付

スクリーンショット、PDF、写真のような数 MB のファイルは、AI がツールの引数に書き出して渡せない。
そこで、利用者の PC でコマンドを実行できる MCP クライアント（Claude Code、Codex CLI など）に、ファイルを MCP サーバーへ直接アップロードさせる。ファイルの中身は AI の出力を通らない。

1. AI が `prepare_upload` に投稿先のチャンネルを渡す。MCP サーバーは、その利用者とチャンネルに結びついた使い捨てのアップロード URL（`<PUBLIC_URL>/mcp/upload/<トークン>`）と、`curl -sS -F 'file=@<ファイルのパス>' <URL>` の形のコマンドを返す
2. AI が利用者の PC でそのコマンドを実行する。MCP サーバーは受け取ったファイルを、本人の Mattermost トークンで `POST /files?channel_id=&filename=` に流し、`file_id` を返す
3. AI が `send_message` に本文と `file_ids` を渡して投稿する。予約するときは `schedule_message` に渡す（「予約投稿」の「添付ファイル」）

claude.ai など、PC でコマンドを実行できないクライアントは、利用者の PC のファイルに触れないため使えない。`prepare_upload` の説明で、その場合は `save_draft` で本文を下書きにし、ファイルは Mattermost の画面から添付するよう案内させる。claude.ai のコード実行には外部のネットワークに出る設定があり（個人のプランでは承認済みのパッケージ管理サービスだけ、Team と Enterprise では owner が任意のドメインを許せる）、チャットに添付されたファイルをサンドボックスから `curl` でアップロード URL へ送れることもあるが、この経路は案内しない。出られるかは利用者や組織の設定で決まり、ツールの説明からは確かめられず、送れなかったときに利用者が原因を確かめにくいため。
`send_message` の `files` の引数の説明は、中身を読めるかと 128KiB に収まるかで使い分けを書き、読めないファイル、収まらないファイル、PC のファイルの行き先は `prepare_upload` の説明に任せる。PC のファイルを `content_base64` で渡すとツールの引数が大きくなって会話の文脈を圧迫し、中身の合計が 128KiB を超えると送れないため。チャットに添付されたファイルは、コード実行で中身を読めるときだけ `content_base64` で送れると書く。コード実行が有効な claude.ai でチャットに添付された小さなファイルを送る経路を塞がず、コード実行の無いクライアントのモデルが、画像の中身をバイト列として読めないまま `content_base64` に渡そうとするのを防ぐため。上限を超えたときのエラーでも、`prepare_upload` の説明の案内に従うよう返す。`prepare_upload` の説明は、PC でコマンドを実行できるかで分け、パスの分からないファイル（Claude Code に貼り付けた画像など）は利用者にパスを聞き、無ければ `save_draft` の案内に従うよう添える。

ツールの説明はすべての会話でクライアントの文脈に載るので、添付の使い分けは 1 か所ずつに置く。`files` で送れる条件と、それ以外を `prepare_upload` へ導く案内は `files` の引数の説明に、claude.ai などへの案内、パスの分からないファイルの扱い、`curl` の前の確認は `prepare_upload` の説明に置き、`send_message` と `schedule_message` の説明では添付の経路の名前だけを挙げる（`schedule_message` が `files` を受けない理由は「予約投稿」の「添付ファイル」）。

- アップロード URL は 10 分間、1 回の要求だけ有効にする。URL は会話の記録に残り、知っていれば誰でもその利用者として 1 回アップロードできるため。トークンは 32 バイトの乱数で、DB にはハッシュだけを置く。使われていない URL は 1 人 5 件までとする
- `/mcp/upload/` はベアラートークンも `Origin` も検査しない。PC の `curl` は MCP のトークンを持たないため、URL そのものを資格情報とする
- 1 回の要求で送れるのは、`file` という名前の欄のファイル 5 件まで、multipart の枠を含めた本文全体で `UPLOAD_MAX_BYTES`（既定 10MiB）まで。ファイル名は `send_message` の `files` と同じ規則で検査する。Mattermost の `FileSettings.MaxFileSize` は別に効き、超えたファイルは Mattermost が断る
- MCP サーバーは要求の本文とファイルをメモリに置いてから Mattermost へ送る。本文やファイルの写しが重なり、1 件で本文の約 8 倍のメモリを使うため、同時に処理するアップロードは全体で 1 件だけにする。それを超えた要求は URL を使わずに 429 で返す
- 本文を読み終える前に返す応答（URL が無効な 404、処理中の 429、上限を超えた 413）は、本文を上限に 1MiB を足した大きさまで読んで捨ててから返す。リバースプロキシは本文を送り終える前に接続を閉じられると、送信の失敗として 502 を返し、MCP サーバーの説明が利用者に届かないため。読んだ量は、413 の前に読んだ分も含めて数える。それより大きい本文は読まずに接続を閉じ、リバースプロキシの本文の上限（上限に 1MiB を足した値）で断らせる
- 本文を待つ間に 15 秒データが来なければ、打ち切って 408 を返し、URL を未使用に戻す。読み捨てる間も同じで、そのときは読み捨てをやめて応答を返す。同時に処理するのは 1 件だけなので、送信を止めたクライアントが Node の要求の期限（300 秒）まで、全利用者のアップロードを止めないようにするため
- 本文が上限を超えた、形式が違う、本文の途中で接続が切れた、本文の送信が止まった、Mattermost が明確に断ったなど、Mattermost にファイルが 1 件も届いていない失敗では、URL を未使用に戻し、同じ URL で送り直せるようにする。1 件でも届いた後や、届いたか分からない失敗（タイムアウト）、想定外の失敗では戻さない。送り直すと同じファイルが 2 回アップロードされうるため。届いたファイルの `file_id` は、エラーの応答にも並べる。再ログインが必要になったときは、その利用者の URL がすべて消えるので、発行し直す
- MCP サーバーは、アップロードしたファイルの `file_id`、利用者、チャンネルを記録する。`send_message` は `file_ids` を、この記録にあって、本人がアップロードし、24 時間以内で、投稿先と同じチャンネルで、まだ投稿に使われていないものに限って受け付ける。Mattermost は使えない `file_ids` を黙って外すため、外れる前に理由を添えて断る。予約が持つファイルも断る（「予約投稿」の「添付ファイル」）。投稿できたら、その `file_ids` に投稿 ID を記録する
- 同じ `file_id` を、本文の違う 2 つの `send_message` が同時に使うと、両方が検査を通る。Mattermost は先の投稿にだけファイルを付けるので、後の投稿は外れたファイルとして出力に明示される。投稿に使ったと記録するのは、投稿の応答の `file_ids` に残ったファイルだけにする。外れたファイルは別の投稿に付いていることがある。逆に、残ったファイルを記録しないと、次の投稿で検査を通り、Mattermost に黙って外されるため。記録した投稿 ID は上書きしない
- 送るファイルは、`prepare_upload` の出力とツールの説明で、`curl` を実行する前にファイルのパスと投稿先を利用者に示して確認を取るよう AI に求める。どのファイルを送るかを決めるのは利用者の PC で動くクライアントで、MCP サーバーからは確かめられないため
- ログには、利用者、結果、件数、合計の大きさ、時間を出し、ファイル名、中身、トークンは出さない。Mattermost の API のログは、ファイル名を含む問い合わせ文字列を落としたパスだけを出す
- 既知の限界
  - アップロードしたが投稿に使われなかったファイルは、Mattermost に残る（ファイルを消す API が無い）。MCP サーバーの記録は 24 時間で消す
  - URL はリバースプロキシのアクセスログにも残る。1 回だけ、10 分間しか使えないことで、漏れたときの影響を抑える
  - 15 秒の期限はデータが来ない間の長さで数えるので、15 秒より短い間隔で少しずつ送り続けると、Node の要求の期限（300 秒）まで処理の枠を取り続けられる。できるのは有効な URL を持つ者だけで、リバースプロキシが本文を受け終えてから MCP サーバーへ送る（nginx の `proxy_request_buffering on`）構成では起きない

### 投稿の編集と削除

Mattermost の権限では、チーム管理者は他人の投稿を削除でき、システム管理者は編集もできる。MCP からは、本人の投稿だけを扱う。

- 先に投稿を読み、`user_id` が本人でないもの、`props.from_webhook` か `props.from_bot` が付いたもの、`type` が空でないもの（システムメッセージなど）は断る。受信 webhook の投稿は `user_id` が webhook の作成者になるため、`user_id` だけでは判定できない
- `props.from_oauth_app` は見ない。この MCP が `send_message` で作った投稿にも付くので、断ると AI の誤った投稿を直せなくなる
- 編集は `PUT /posts/{id}/patch` に本文だけを送る。`PUT /posts/{id}` は、省いた `is_pinned` を外すため使わない
- 返信のあるスレッドの親投稿は消さない。Mattermost は親を消すと他人の返信もまとめて消すため。親かどうかは `root_id` が空かで判定し、`reply_count` が数値で返らなければ返信があるものとして断る。返信の投稿にもスレッド全体の `reply_count` が載るので、`reply_count` だけでは判定できない
- 既知の限界
  - 返信の有無を確かめてから消すまでのあいだに付いた返信は、親と一緒に消える。Mattermost に条件付きの削除が無いため防げない
  - 返信のない親投稿を消しても、ほかの利用者のそのスレッドへの下書きは消える。Mattermost の削除の動作で、防ぐ手段は無い

### 下書きの保存

下書きは利用者・チャンネル・`root_id` の組ごとに 1 つで、保存は上書き（upsert）になる。本人の書きかけを消さないよう、保存の前に既存の下書きを確かめる。

- 既存の下書きの本文が違えば、`overwrite: true` が無い限り保存せず、既存の本文の先頭を添えて断る。本文が同じなら保存し直さない。上書きは添付ファイルと優先度も置き換え、取り消せないため、注釈は `destructiveHint: true` とする
- `root_id` は、同じチャンネルにある返信でない投稿であることを確かめる。Mattermost は存在しない投稿や返信の ID でも保存し、画面のどのスレッドにも出ない下書きが残るため
- 利用者が「設定 > 詳細設定」で下書きの同期を切っていたら（preference `advanced_settings/sync_drafts` が `false`）、保存せずに断る。同期を切った webapp は、閉じている間に保存された下書きを読み込まず、利用者の書きかけもブラウザの中にしか無いので、既存の下書きの確認では見えないため。preference が無いときは同期が有効として扱う
- 既知の限界
  - 既存の下書きを確かめてから保存するまでのあいだに、本人が画面で書いた下書きは上書きされうる
  - 保存したときにそのチャンネルを webapp で開いていると、開いている入力欄には反映されない。そのまま本人が書いてチャンネルを切り替えると、webapp がサーバーの下書きを上書きし、保存した下書きは警告なく失われる。webapp の動作なので防げず、出力で、開き直してから編集するよう添える
  - 返信の下書きが右側のパネルにどう出るかは確かめていない。そのため、返信の下書きの出力では入力欄に入っているとは言わない
  - 同じ本文を `send_message` で送っても、添付の付いた下書き、下書きの同期を切った利用者の下書き、確認や削除に失敗した下書きは残り、そのまま送ると同じ投稿が 2 回になる。`send_message` の出力でそのことを伝える（「`send_message` の後の下書きの削除」）。予約投稿で同じ本文を送ったときも、下書きは残る

### 予約投稿

Mattermost の予約投稿の API は Team Edition では使えず（400 `api.scheduled_posts.license_error`）、`POST /posts` の未来の `create_at` は黙って今の時刻に置き換えられる。
そこで、MCP サーバーが予約を SQLite に保存し、時刻が来たら本人の Mattermost のトークンで投稿する。

**「避けたいこと」との関係**: 予約は、本人が MCP を操作していない時刻に投稿する。「意図しないチャンネルへの投稿」を避けるため、次のようにする。

- 投稿先は予約の時点で本人が指定し、`channel_id` に固定する。時刻が来たときに名前を解決し直さない。`@ユーザー名` の DM や `@a,b` のグループ DM が無ければ、予約の時点で作る。`root_id` も予約の時点で、同じチャンネルの親投稿であることを確かめる
- 本文と投稿先は、予約の時点の出力と `list_scheduled_messages` で本人が確かめられ、取り消せる
- 投稿の権限は、時刻が来た時点で Mattermost が本人の権限で改めて判定する
- 変えた予約、取り消した予約、時刻を過ぎた予約は投稿しない（下の「実行」）

**保存**

- 予約は Mattermost のユーザーに結び付ける。一覧・変更・取り消しは本人の予約に限り、他人の予約 ID には「見つかりません」と返す。予約 ID は推測できないランダムな値にする
- 本文は Mattermost のトークンと同じ鍵で暗号化して保存し、ログに出さない
  - 鍵を変えると本文を復号できなくなる。待機中の予約は投稿せずに、理由を「本文を復号できないため投稿していません。予約を入れ直してください」として失敗にする。投稿を試みた後なら「投稿されたか不明」にする
- 投稿済みと失敗の予約は、更新から 7 日で消す
- 変更と取り消しは、待機中で一度も投稿を試みていない予約だけに、条件付きの 1 文の更新で行う。投稿を試みた後の予約の本文を変えると、やり直しが古い本文の投稿を見つけられず 2 件目を投稿するため
- 予約は grant の取り消しやトークンの取り消しでは消さない。時刻が来て投稿に失敗した時点で失敗にする

**添付ファイル**

予約には、`prepare_upload` でアップロードしたファイルを `file_ids` で 1〜5 件添付できる。

- Mattermost は、投稿にファイルを付けるとき、アップロードからの経過時間を見ない（v11.7.8 の `FileInfo` の `AttachToPost`）。投稿に使われていないファイルを消す定期ジョブも無い。実物で、`CreateAt` を 31 日前にしたファイルを投稿に付けられることを確かめた。そのため、予約の時刻までファイルは残る。例外は、Enterprise のデータ保持ポリシーでファイルを消している場合である（保持期間は `FileRetentionHours`）。予約の時刻は、作るときはアップロードから最大 31 日（744 時間）後だが、`update_scheduled_message` で延ばせるので、ファイルの古さに上限は無い。保持期間を過ぎたファイルは時刻までに消え、Mattermost はファイルを外して投稿する（一覧に「注意」として出る）
- 予約の時点で、`send_message` と同じ検査をする（本人が `prepare_upload` で 24 時間以内に、予約の投稿先と同じチャンネルへアップロードし、まだ投稿に使われていない）。時刻が来たときには、MCP サーバーのアップロードの記録（24 時間で消える）を引かず、予約の行に保存した `file_ids` で投稿する。`file_id` は本文と違い暗号化しない。ファイルを読むには Mattermost の権限が要るため
- 待機中と投稿中の予約、投稿済みの予約（投稿に残ったファイルだけ。ABAC で隠されたときは予約のファイルすべて）、試みた記録が残る失敗の予約（やり直しの回の失敗と、投稿されたか不明の失敗）は、ファイルを持つものとして扱う。`schedule_message` と `send_message` は、ほかの予約が持つファイルを、予約 ID を添えて断る。Mattermost は同じファイルを先に投稿した側にだけ付けるので、後の側は黙ってファイルを失うため。試みた記録が残る失敗を含めるのは、投稿されている可能性があるため。最初の試みを Mattermost が断ったか、処理されたかもしれない要求を送る前に再ログインが必要になった失敗（`401` しか受けていない呼び出し。「Mattermost の認証」の `401` の扱い）は、投稿されていないと確定しているので持たない。`schedule_message` は、この検査を予約の行を作るのと同じトランザクションで行う。`send_message` は、投稿済みの検査の後で、やり直しで前の投稿を探した後に行う。前の投稿が見つかれば検査せずにそれを返す。先に検査すると、前の試みで投稿できていたやり直しが、その後に同じファイルで入った予約のために断られるため
- `file_ids` は変更で変えられない。`update_scheduled_message` に `file_ids`、`files`、`channel`、`root_id` を渡したときは、受けない引数のエラー（「ツール」の節）に、取り消して予約し直すよう案内を添える。取り消した予約のファイルは Mattermost に残り、24 時間以内なら別の投稿に使える
- `file_ids` は予約の行の列に保存する。既存の DB には、起動時に `BEGIN IMMEDIATE` の中で列が無ければ足す。サーバーと管理コマンドが同時に DB を開いても、2 回足そうとしないため
- `send_message` の `files` のような、中身を直接渡す添付は予約では受け付けない。受け付けるには、中身を SQLite に保存するか、予約の時点で Mattermost へ先にアップロードすることになる。前者は保存する機密と DB の大きさが増え、後者は取り消した予約のファイルが Mattermost に消せずに残る。そのため、ファイル付きの予約は `prepare_upload` を使えるクライアントに限り、claude.ai など、PC でコマンドを実行できないクライアントからはできない。`schedule_message` に `files` を渡したときは、受けない引数のエラー（「ツール」の節）に、今すぐ送るなら `send_message` を、予約するなら `prepare_upload` を使うよう案内を添える
- 予約の上限に、ファイルの大きさの制限は足さない。ファイルの中身は Mattermost にあり、MCP サーバーが持つのは `file_id` だけのため

**実行**

- 巡回は、前の回が終わってから 30 秒後に次を始める。回の途中で例外が出ても次の回を予約する。1 回で Mattermost を呼ぶ予約は全体で 20 件までとし、呼び出しは要求と同じく Limiter を通す。トークンのリフレッシュは要求と同じくユーザー単位で 1 つにまとまる
- 投稿の権利は `UPDATE ... SET status='sending' WHERE id=? AND status='pending' AND scheduled_at <= ? RETURNING *` で取り、本文はその戻り値から読む。巡回が選んでから権利を取るまでのあいだに、本人が予約を変えたり取り消したりできるため。1 つのプロセスなので、二重に実行しないことはこの更新で足りる
- 二重投稿の防止には `send_message` の記録（10 分で消える）を使わず、予約の行そのもので判定する。やり直しは 1 時間続きうるうえ、同じ本文の予約が並ぶと記録では区別できないため
  - 最初に投稿を試みるとき、行に `pending_post_id` と試みた時刻を保存してから投稿する
  - やり直しでは、試みた時刻以降のそのチャンネルの投稿から、本人の、同じ `root_id` の、本文が一致する投稿を探す。ほかの予約が投稿済みとして記録した投稿は除く。見つかれば投稿済みにし、見つからなければ同じ `pending_post_id` で投稿する
  - 本文が一致する投稿が無くても、試みた時刻以降に本人の同じ `root_id` の削除済みの投稿があれば、投稿せずに「投稿されたか不明」の失敗にする。Mattermost は削除済みの投稿の本文を空にして返すので、本人が消した予約の投稿かどうかを本文で確かめられず、送り直すと出し直しになるため。1 時間を過ぎたときの探索も同じにする
  - 試みた時刻以降に、本人の同じ `root_id` の、編集されて本文が一致しない投稿（ほかの予約が記録したものを除く）があるときも、削除と同じく投稿せずに「投稿されたか不明」の失敗にする。Mattermost は編集後の本文を返すので、本人が編集した予約の投稿かどうかを本文で確かめられないため。`send_message` の照合は変えない
  - ファイル付きの予約の照合は、`send_message` と同じく、ファイルの件数と、予約の `file_ids` がすべて付いていることも条件にする。本文もファイルも一致する投稿が無く、本文は一致するがファイルが一致しない投稿（ほかの予約が記録したものを除く）があれば、投稿せずに「投稿されたか不明」の失敗にする。前の試みで Mattermost がファイルを外した投稿かもしれず、送り直すと二重投稿になるため。ファイルの無い予約でも、本人が同じ本文にファイルを付けて手で投稿していれば同じになる
- 結果ごとの扱い
  - 成功: 投稿済みにし、`post_id` を記録する。投稿に残ったファイルは、同じトランザクションで投稿に使ったと記録する（`send_message` と同じ）。Mattermost がファイルを外していれば、投稿済みのまま、外れた件数と `file_id` を一覧に「注意」として出し、行の `file_ids` は投稿に残ったものに書き換える。外れたファイルはこの投稿に付いておらず、持ち続ける理由が無いため。ただし、Enterprise Advanced の ABAC の権限ポリシーで本人にファイルのダウンロードが許されないチャンネルでは、Mattermost は応答の `file_ids` を空にし、付いたファイルの件数を `metadata.redacted_file_count` に入れる。このときはどれが外れたかが分からないので、予約のファイルをすべて付いたものとして持ち続け、投稿に使ったと記録する（`send_message` と違う）。件数が予約のファイルより少なければ、外れた件数だけを（`file_id` を出さずに）「注意」として出す
  - Mattermost の `4xx`（アーカイブ、権限の喪失、親投稿の削除など）と再ログインが必要なとき: やり直さずに失敗にし、理由を利用者向けの文言で記録する。ファイル付きの投稿では、Mattermost はファイルのアップロードの権限も確かめて同じ `403` を返すので、文言で両方の権限を挙げる。処理されたかもしれない要求を送った後で（`401` 以外の応答を受けたか、接続した後に通信が切れた後で）再ログインが必要になったときは、理由を「投稿されたか不明」にする。最初の試みで失敗にするとき（「投稿されたか不明」を除く）は、試みた記録を消してファイルを手放す。やり直しの回では消さない。前の試みが投稿していた可能性を、今回の拒否は否定しないため
  - レート制限、接続できない、タイムアウト、`5xx`: 待機中に戻し、次の回にやり直す。確実に送っていない失敗が最初の試みで起きたときは、試みた記録を消し、本人が変更と取り消しをできる状態に戻す。やり直しの回では消さない。消すと次の回が既存の投稿を探さずに新しい `pending_post_id` で投稿するため
  - 予期しない例外: その予約だけを失敗にし、ほかの予約は続ける。理由は「投稿されたか不明」にし、試みた記録も残す。送る前の処理は、送っていないことを型付きの失敗（レート制限、再ログインが必要、接続できない）で返し、やり直しの照合も自分で失敗を扱うので、予期しない例外は DB の障害を除けば送り始めた後に限られるため
- 予定時刻から 1 時間を過ぎた予約は、新たには投稿しない。サーバーが止まっていたあいだに過ぎた予約を、何時間も遅れて投稿しないため。投稿を試みた予約は、やり直しと同じく既存の投稿を探し、見つかれば投稿済み、見つからなければ失敗、探せなければ「投稿されたか不明」の失敗にする
- 投稿中のまま 30 秒を過ぎた予約（投稿の途中でプロセスが止まったもの）は、待機中に戻してやり直す。停止の合図では次の回を予約しないだけにし、実行中の回は待たない

**本文の全文**: 一覧は本文を先頭 200 文字で切るので、`update_scheduled_message`（本文全体を置き換える）の前に全文を得られるよう、`list_scheduled_messages` に `id` を渡すとその 1 件を本文を切らずに返す。一覧で切ったことは本文の行ではなく別の行で知らせる。本文に続けると、書き写したときに案内まで本文に入るため。`id` を渡したときは本文を最後に置き、見出しの次の行から末尾までを本文にする。本文は複数行になりうるので、後ろに別の行を続けると書き写す範囲が一意に決まらないため。

**失敗の知らせ方**: `list_scheduled_messages` で、失敗と理由を見られるようにする。ファイル付きの予約の失敗には、付け直すには `prepare_upload` からアップロードし直す必要があることを添える。失敗にする経路が巡回、時刻切れ、復元の管理コマンドに分かれているので、保存する理由には入れず、一覧の表示で添える。`schedule_message` の出力で、結果をそこで確かめるよう伝える。
DM での通知はしない。この MCP は Bot を持たないので、本人の名前で自分宛ての投稿が増えるため。
ほかのツールの結果に失敗を割り込ませることもしない。

**画面での見分け**: 予約の投稿は、本人の普通の投稿として出る。props で印を付けても標準の画面には出ないため、見分けられるようにはしない。

**復元**: 古いバックアップには、その後に取り消したり変えたりした予約が待機中のまま入っている。そこで復元の手順で、管理コマンド `invalidate-scheduled` によって待機中と投稿中の予約をすべて失敗にする。投稿を試みた予約と、予定時刻を過ぎた予約は、理由を「投稿されたか不明」にする。失った DB の上では、バックアップの後に投稿されていたかもしれないため。利用者には、それ以外の予約を入れ直すよう知らせる。

**既知の限界**

- 本文の照合は、同じ投稿先と同じ本文の、本人の投稿を区別できない。そのため次の 2 つの向きで取り違えうる
  - 予約の最初の試みの後に、本人が同じ投稿先へ同じ本文を手で（画面や `send_message` で）投稿すると、予約のやり直しがそれを予約の投稿とみなし、予約を投稿しない
  - `send_message` が結果不明の後にやり直すあいだに、同じ投稿先へ同じ本文の予約が投稿されると、`send_message` のやり直しがそれを自分の投稿とみなし、投稿しない
- Mattermost の処理が投稿中の猶予（30 秒）より遅れて完了した場合の二重投稿は防げない（`send_message` と同じ）
- `send_message` と予約が同じファイルで同時に検査を通ると、後に投稿した方がファイルを失う（予約の側なら一覧に「注意」として出る）
- `file_ids` 列を読まない古い版に、更新後の DB のまま戻すと、ファイル付きの待機中の予約をファイル無しで投稿する。版を戻すときは更新前の `/data` も戻す（`docs/operations.md`）
- 復元の手順で失敗にした、試みていない予約のファイルは、ファイルを持つものとして扱わない。それを別の投稿に使うと、復元の前に投稿されていた場合は Mattermost が外す（出力に出る）
- 401 の後のリフレッシュの保存が競り負け、確かめの投稿が `5xx` かタイムアウトになり、送り直しが `429` になると、投稿されたかもしれないのに確実に送っていない失敗として扱う。`send_message` は記録を消し、予約は最初の試みなら試みた記録を消すので、やり直しで二重投稿になりうる。同じ経路で送り直しが `4xx` になった予約は、投稿されたかもしれないのに確定の失敗として記録を消し、ファイルを手放す。Mattermost の `pending_post_id` の重複排除（「`send_message` の二重投稿の防止」）は、記録を既定では各プロセスのメモリに持つので、確かめの投稿の後に Mattermost が再起動したときや、HA 構成で送り直しが別のノードに届いたときは Mattermost の記録が無い。本人が前の投稿を読めなくなったときは、Mattermost の記録が無視される。どちらでも、同じ `pending_post_id` の送り直しが別の投稿になる。確かめの投稿が投稿しており、送り直しが別の投稿になってファイルを外されたときも、1 件目に付いたファイルを手放す。手放したファイルを別の予約に使うと Mattermost が外し、その予約の一覧の「注意」に出る

### Mattermost への影響を抑える仕組み

MCP サーバーは Mattermost と同じホストで動かすことが多く、CPU、メモリ、ディスクを共有しうる。
攻撃、不具合、メモリリーク、DB の肥大で Mattermost を巻き込まないよう、次を必須とする。

- MCP サーバーのコンテナに CPU、メモリ、プロセス数の上限を設ける（Compose なら `cpus`、`mem_limit`、`pids_limit`）。具体値は実装者が決めるが、Mattermost と PostgreSQL の使用量を見てから決める
- リバースプロキシで MCP のパスの要求本文の大きさに上限を設け、DCR、認可、トークンの各エンドポイントには IP ごとのレート制限（`limit_req`）をかける
- MCP サーバー内で、Mattermost API の呼び出しにタイムアウトと同時実行数の上限を設ける
- ツール呼び出しにはアプリケーション内でレート制限をかける（MCP 2025-11-25 の Tools の Security Considerations）。claude.ai からの要求は Anthropic の共有の送信元から来るため、リバースプロキシの IP 単位の制限では代わりにならない
  - 数えるのはツールの呼び出し回数ではなく、実際に Mattermost API を呼んだ回数とする。1 回のツール呼び出しが複数の API 呼び出しになる場合（チームごとの検索など）も、その分を数える
  - Mattermost ユーザーごとの上限と、サーバー全体の上限の 2 段階にする
  - 上限を超えたら待たせ続けずに、すぐレート制限のエラーをツールの結果として返す
  - Mattermost が `429` を返したら自動で再試行せず、リセット時刻を添えてレート制限のエラーとして返す
  - 具体値は実装者が決める。目安は、利用者 1 人が会話の中で普通に使う量（数十回／分）を妨げず、全員が同時に上限まで使っても Mattermost の応答時間が目に見えて悪化しないこと。ローカルで負荷をかけて確かめる
  - 利用者 1 人あたり 300 回／分、全体で 600 回／分とする。`list_my_channels` を起点に既定の 50 チャンネルを `read_channel` で巡回すると約 200 回かかるため 1 人あたりをこの値にし、全体の上限は `docs/measurements.md` の「負荷」で応答時間が悪化しないと確かめた値なので、1 人の上限を上げても Mattermost にかかる負荷の最大は変わらない
- 認可途中の状態と認可コードは短い期限（10 分程度）で消す。失効や期限切れになった grant とトークン、期限の過ぎた `send_message` の重複防止の記録も定期的に消す。DCR の登録は自動では消さず、総数の上限で抑える（「保存先」を参照）
- ログは標準出力に出し、容量の制限はコンテナのログドライバーに任せる

### 配置

```text
インターネット ── リバースプロキシ（443）─┬─ /mcp、/mcp/…、/.well-known/oauth-protected-resource/mcp、
                                          │  /.well-known/oauth-authorization-server/mcp ─> MCP サーバー
                                          └─ それ以外 ─> Mattermost
MCP サーバー ──(MM_URL、HTTPS)──> Mattermost API
```

- MCP サーバーは、Mattermost と同じオリジンの `/mcp` 以下にも、別のホストにも置ける。URL は環境変数（`PUBLIC_URL`、`MM_URL`、`MM_BROWSER_URL`）で与え、要求の `Host` や `X-Forwarded-*` からは組み立てない。同じオリジンに置くと、名前が `mcp` のチームの URL（`/mcp/...`）が MCP サーバーに取られるので、そのチームは作れない
- MCP サーバーのポートはインターネットに公開しない。リバースプロキシからだけ到達させる
- MCP サーバーから Mattermost の API とトークンエンドポイントへは、クライアントシークレットとトークンを送るため、証明書を検証する HTTPS で呼ぶ（OAuth 2.1 と RFC 6750 は TLS を必須としている）
- 利用者のブラウザを送る Mattermost の認可 URL と、パーマリンクには、Mattermost の公開 URL（`MM_BROWSER_URL`）を使う
- リバースプロキシの Mattermost 向けの設定（キャッシュなど）を MCP のパスに適用しない。MCP のパスは専用の設定で受け、キャッシュとバッファリングを無効にする
- TLS 1.3 の Early Data（0-RTT）を無効にする。0-RTT で送られた要求は再送（リプレイ）されうるため、`send_message` の二重投稿や、リフレッシュ要求の再送によるリフレッシュトークン再利用検知の誤発火を招く。Mattermost 本体の POST も同じ危険を抱えており、0-RTT による短縮は 1 往復分にすぎないため、MCP のパスだけで `425` を返すより、Mattermost と同じオリジンなら全体で無効にする
- MCP サーバーが止まっても Mattermost とリバースプロキシは動き続けるようにする（nginx なら、起動時に MCP サーバーの名前解決を必要としない書き方にする）
- Mattermost 側の準備は、OAuth 2.0 サービスプロバイダーを有効にし、Integrations の OAuth 2.0 アプリの画面（`/<チーム名>/integrations/oauth2-apps`）か API で OAuth 2.0 アプリを 1 つ作るだけ（confidential、コールバック URL は MCP サーバーのコールバック）。MCP サーバーが自分の同意画面を出すため、Mattermost 側の「信頼済み」は「はい」にして同意の二重表示を避けてよい。クライアント ID とシークレットは環境変数で渡す
- 導入と運用の手順は `docs/deployment.md` と `docs/operations.md` に書く

### 運用

- ログは JSON で出す。記録するのは時刻、Mattermost ユーザー ID、ツール名（予約の巡回では予約ごとの結果の状態）、結果（成功、失敗の種別）、所要時間。メッセージ本文、検索語、トークンは記録しない
- `/mcp/healthz` をコンテナの healthcheck に使う

### テスト

- 認可フローとツールは、ローカルの Docker Compose で Mattermost Team Edition を立てて自動テストする。利用中の Mattermost にテストのための書き込みをしない
- テストに使う Mattermost のバージョンは環境変数 `MATTERMOST_IMAGE_TAG` で指定し、未指定なら挙動を確かめた v11.7.8 を使う。トークンの再利用、リフレッシュの競合、アプリの取り消しの挙動もこのテストで確かめる
- 「前提」の Mattermost のトークン再利用の挙動は v11.7.8 の実装に基づく。Mattermost を v11.7.8 から更新するときは、新しいバージョンでこのテストを通してから更新する。テストが通らなければ、Mattermost の更新を止めて設計を見直す
- 導入後の確認は、作業者のアカウントで 3 つのクライアントから接続し、読み取り系のツールを一通り呼ぶ。書き込み系のツール（添付と予約投稿を含む）は、作業者自身の DM（自分宛て）の中だけで確かめ、他のチャンネルや利用者の投稿には触れない。予約投稿は、時刻の変更と取り消しをした予約が予定どおりに 1 件だけ投稿されることと、巡回のログに本文が出ないことを確かめる

## 採らない設計

| 案 | 採らない理由 |
|---|---|
| Mattermost の DCR を有効にし、MCP クライアントを Mattermost に直接登録させる | token passthrough になる。public client にはリフレッシュトークンが出ず、再ログインが頻発する。DCR の登録エンドポイントが認証なしで公開され、Mattermost に OAuth アプリが無制限に作られる |
| Personal Access Token を利用者に発行してもらい、MCP クライアントに設定させる | 「URL を追加してログインするだけ」にならない。claude.ai の固定ヘッダーによる認証は限定提供で、組織共通の資格情報になるため、利用者ごとの権限で動くという要件を満たさない。トークンが失効しない |
| 同意を記憶して 2 回目以降の同意画面を省略する | 省略の判定には、Mattermost へ送る前に利用者を特定するセッション管理が要る。認可はクライアント追加時にしか起きないため、毎回表示しても負担は小さい |
| Mattermost の PostgreSQL に保存する | 「保存先」を参照 |
