# i18n とタイムゾーンの設定 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 利用者や AI が目にする文をすべて英語と日本語の表に移し、言語（`LOCALE`）とタイムゾーン（`TIME_ZONE`）をサーバー全体の設定で選べるようにする。docs も英語と日本語の組にする。

**Architecture:** `src/i18n/` に言語ごとの表（`en.ts`、`ja.ts`）と、今の言語の表を返す入口 `msg()` を置き、起動時に `setLocale` で決める。タイムゾーンは `src/zone.ts` に持ち、起動時に `setTimeZone` で決める。JST に固定していた箇所はすべて `zone.ts` を通す。

**Tech Stack:** TypeScript（Node.js 26 の型ストリップで直接実行）、vitest、`Intl`。依存は足さない。

**Spec:** `docs/superpowers/specs/2026-11-23-i18n-design.md`

## Global Constraints

- 依存を足さない（`package.json` の dependencies と devDependencies を変えない）
- `LOCALE` は `en` か `ja`、既定 `en`。`TIME_ZONE` は IANA 名、既定 `UTC`。どちらも空の文字列は既定値として扱い、不正な値は起動時に `LOCALE must be en or ja` / `TIME_ZONE must be an IANA time zone name` で落とす
- 起動のログ `listening` に `locale` と `time_zone` を出す
- `ja.ts` の型は `en.ts` から作った `Messages` に当てる。キーの抜け、余分なキー、関数の引数の違いは typecheck で落ちること
- 日本語の表には、今のソースにある日本語の文を一字一句そのまま移す（ツールの説明だけは、今の英語の説明から新しく訳す）。日本語の利用者の動作を変えないため
- AI に書き写させる項目名（`next_cursor:`、`post_id:`、`channel_id:`、`file_id:`、`user_id:` など、出力に `名前: 値` の形で出て、ツールの説明か別のツールの引数がその名前で指すもの）は訳さず、両方の言語で同じにする
- テストは `LOCALE=en`、`TIME_ZONE=Asia/Tokyo` で流す（`test/setup.ts`）
- docs は英語を `<name>.md`、日本語を `<name>-ja.md` にする。文書の中のリンクは同じ言語の文書へ張る
- コミットメッセージは日本語のプレフィックス付き conventional commits（例 `feat: …`）で、本文に Why を書く。末尾に次の 2 行を付ける

  ```
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_015hF9aamvyzwQuRcdTXrHVw
  ```
- コードコメントは Why not だけを英語で書く（既存のコメントの書き方に合わせる）

## Review Focus

- **モジュールの読み込み時に組み立てた文**：`setLocale('ja')` の後でも英語のまま残る。Task 11 のテストで、`ja` のときの全ツールの説明と代表の出力に英語の表の文が混ざらないことを確かめる
- **言語をまたいで同じでなければならない項目名**：`ja` で `next_cursor:` などが訳されると、説明が指す名前と食い違う。Task 11 のテストで、両方の言語の出力に同じ項目名が出ることを確かめる
- **`edit_message` の説明が引用する `BODY_CUT_NOTE`**：`get_post` が出す注記と、同じ言語で一字一句一致する必要がある。Task 11 のテストで両方の言語について確かめる
- **夏時間の切り替わりの現地時刻**：存在しない時刻と 2 回ある時刻を `parseWhen` に渡したとき。Task 3 のテストで確かめる
- **`TIME_ZONE=UTC` での検索の日付と出力**：オフセット 0 で `on:` の日付と `formatTime` が正しいこと。Task 3 のテストで確かめる

### Task 4〜10 の共通の手順（文を表に移す）

各 Task は、担当のファイルの日本語の文（ツールの説明を含む）をすべて表に移す。手順は次のとおり。

1. **テストを先に英語にする**：担当のテストファイルの日本語の文言の assertion を、英語の表に入れる予定の文に書き換える（マルチバイトの**データ**の assertion は変えない）。`pnpm vitest run <files>` → FAIL を確かめる
2. **表に移す**：`en.ts` の担当の入れ子に英語、`ja.ts` に今の日本語を一字一句そのまま入れる。ツールの説明は、`en` に今の英語、`ja` に今の英語からの訳を入れる。ソースは `msg().<area>.<key>` で引く。モジュールの読み込み時に文を組み立てている定数は、使う時点で引く関数か getter にする
3. **確かめる**：`pnpm test && pnpm typecheck` → PASS。`grep -nP '[\x{3040}-\x{30ff}\x{4e00}-\x{9fff}]' <担当の src ファイル>` が、例として意図して含む文（`2026年10月*` など）とコメント以外で 0 行
4. **訳のレビュー**：担当の範囲について、元の日本語・新しい英語・実装の 3 つを突き合わせるレビューを、訳した文脈から切り離したサブエージェント（`review-consistency`）に依頼する。条件の欠け、範囲の変化、安全のための案内の弱まり、項目名の訳し漏れを探させる。ツールの説明は、英語と新しい日本語の訳の対応も見させる。指摘を直し、受けない指摘は理由とともに PR の本文に残す
5. **Commit** `refactor: <範囲> の文を言語の表に移す`
